## Pull Request Services

App-scoped pull-request linking plus the `alveary_host` pull request tools. `Services/HostMCP/AGENTS.md` owns the generic handler contract (strict validation, trusted identity, source-first reads, dual name shapes, exposure) and how a feature enrolls; `Services/Git/AGENTS.md` owns the GitHub client those tools call. The rules below are what this feature adds.

### Host Tools

- **The fragment has to claim every pull request question outright.** Models answered "what needs my review" by shelling out to `gh` or searching the web, because nothing said these tools were the route. Naming those substitutes — and saying the tools run the user's own authenticated CLI — is what redirects them; `Services/HostMCP/AGENTS.md` owns the matching preamble rule.
- **That claim stops at pull requests that already exist.** Nothing here opens one, so the fragment hands creation back to the model's own `gh pr create` — otherwise "never run `gh` yourself" bans the only route — and `reopen_pr`'s description disowns it too, because its name is what an "open a pull request" ask reaches for.
- **Gate every tool on `AppSettings.pullRequestsEnabled`** as the first statement of `handle`. With the integration off, the pane the user would check the result in does not exist. The catalog stays static — exposure is all-or-nothing per turn — so the tools remain advertised and the refusal names the setting.
- **Only `propose_pr_review` needs confirmation, and it carries the whole review.** The verdict, the summary body, and every inline comment travel in that one call — there is no separate comment tool, so nothing of a review touches GitHub before the user confirms. Do not reintroduce an immediate `add_pr_review_comments`-style writer: even a private draft is GitHub state a cancelled review would leave behind. Everything else here is undoable from Alveary's pane or github.com, so it applies immediately and says so.
    - **Duplicate anchors pass the parser** — two remarks on one line are legal and can be deliberate.
- **`reply_to_pr_thread` refuses a pending thread.** GitHub accepts no reply until the review holding it is submitted, so the refusal names the state instead of failing at the wire.
- **Resolve and unresolve keep no receipt ledger, and neither do the state changes.** All six are idempotent-by-state — a replay lands on an `already_*` success — and the state itself is the record; the comment tools and the proposal record receipts through `HostToolReceiptLedger`, because posting twice is visible to everyone.
- **Automated scheduled runs may call every tool except `close_pr`.** A scheduled task acts on the user's standing instruction, each mutation is undoable, and the review proposal still waits for the user's confirmation; a closed pull request drops out of review flows, so closing alone keeps the automated-run refusal, caller-first so the refusal never reads as a state critique.
- **`close_pr` applies immediately because `reopen_pr` undoes it.** The pane styles Close as destructive, but that is about the 422 once the head branch is deleted — in the moments after a mistaken close the branch still exists, so the pair is reversible and the confirmation card stays reserved for review submission. The close message names `reopen_pr` so the model never describes closing as final; state-change preconditions mirror `PullRequestStateAction.available(for:)` (write access, merged is terminal, reopen needs `headRefExists`), so a refusal here is one the footer would have shown as a missing button.
- **`mark_pr_ready` and `mark_pr_draft` are one reversible pair, and each names the other as its undo.** Both mutations are GraphQL-only, so a detail without a node id refuses instead of acting — the same case where the footer drops both buttons; `Services/Git/AGENTS.md` owns the mutations.
- **Thread IDs are GraphQL node ids from the read tools.** No tool accepts a REST comment id — the handler resolves reply targets itself — so a model can only name a thread it actually read.
- **Keep `list_involved_prs` and the threads feature's `list_linked_prs` telling each other apart.** They list pull requests from different sources — a live GitHub search of the user's involvement versus Alveary's hand-linked bookmarks for one thread — and an earlier `list_prs` read as the generic default beside `list_linked_prs`, so models picked the wrong one for "what am I working on". Naming the sibling was not enough: `list_linked_prs` also has to refuse the generic ask in its own words, because answering it returns an empty list that reads as truth. Each description names the other, both fragments state the split, and `AlvearyHostToolCatalogTests` pins it. Any third pull-request listing tool owes the same treatment.
- **A successful mutation announces itself once, from `handle`.** The pane cannot see an agent's write, and posting per handler is a step a new tool would forget; `propose_pr_review` is excluded because it changes nothing on GitHub. `Alveary/ViewModels/PullRequests/AGENTS.md` owns what the announcement drives.
- **"Involved" is not "mine".** The reviewing buckets return pull requests other people opened that await this user's review, so no name or copy may call the results the user's own — that phrasing had the model skipping review requests when asked what needed its attention.
- **`list_involved_prs` is open *by default* and fetches just its filter's buckets.** It answers "what is on my plate", where a merged or closed pull request is noise, and unlike the screen it has no user session carrying a status choice — so an unargumented call passes `.open`. `status` overrides that with exactly one value, never a set: GitHub search qualifiers only AND, and `Alveary/Services/Git/AGENTS.md` owns why. `PullRequestHostToolListFilter.requiredBuckets` gives every narrow filter exactly one bucket, so `filter: "authored"` costs one GitHub search rather than three.
    - **Its scopes are the screen's *sections*, not its tabs.** The Reviewing tab renders both review buckets and sections them; a flat result cannot, and the merged list read as all-pending — so `reviewing` is `review-requested:@me` alone and `reviewed` is the other half. A re-request counts as pending, as it does in `Alveary/Views/PullRequests/AGENTS.md`.
    - **Every argument is optional and every default is the pre-pagination call.** `filter: all`, `status: open`, `limit: 50`, no bounds, no cursor — pinned by `testAnEmptyListCallKeepsTheDefaultsItAlwaysHad` and `testAnUnargumentedListCallFetchesExactlyWhatItAlwaysDid`, because that call is the one every model makes first.
- **The paging cursor is opaque, carries its whole query, and reaches the model in both halves of the result.** `PullRequestListCursorToken` encodes filter, status, bounds, limit, the buckets with pages left, and their positions, so `{cursor}` alone continues the search — requiring the model to re-pass the query would break naive pagination. An argument passed beside a cursor may repeat it but not contradict it; a contradiction, an unreadable token, or a newer `version` is refused with "start over without cursor". `next_cursor` rides in the structured content *and* as a trailing text line, since a text-only consumer that never sees it cannot ask for page two.
    - **Advance past the emitted prefix, not the page boundary.** Buckets are merged and only the newest `limit` rows go out, so `PullRequestListCursorAdvance` resumes each bucket after its longest consumed prefix — emitted or filter-rejected — and keeps its incoming position when nothing was consumed. Advancing every bucket to `endCursor` drops up to a page each. The accepted cost is that a never-newest bucket refetches its page until its siblings drain.
    - **The status names itself in the sentence, never in the parenthetical.** `PullRequestListWidgetParsing`'s text fallback finds the filter by matching `(<filter>)` and reads rows only from lines starting `- `, so the header stays "Found N <status> pull requests (<filter>)" and the cursor stays its own trailing line.
    - **A row's involvement rides as a phrase inside its own metadata parenthetical.** The text half has no `involvement` object, so without it a `filter: "all"` row cannot say whether it awaits review or already had it. Appending is what keeps it parsable: that parser takes the *last* `(` and the *first* comma-separated field.

### Output Bounds

- **Bound every read tool.** AgentCLIKit replaces an oversized result outright rather than truncating it, and each payload is emitted twice (text fallback plus structured content), so `PullRequestHostToolLimits` budgets half the wire. A new field that can grow without limit needs a cap there.
    - **A per-item cap is not a bound when the response holds many items.** `maxThreadComments` multiplies against `maxTimelineLimit`, so threads share one `maxResponseThreadComments` target and go shallow rather than overflowing; `threadCommentAllowance(threadCount:)` divides it once the window is known. `minThreadComments` outranks that target — the real ceiling is `max(target, 2 × threadCount)` — because a thread showing only its root cannot say whether it was already answered. A thread keeps both ends and drops its middle.
    - **`comment_count` is GitHub's `totalCount`, not the array's length.** `comments` is a page (100), so reporting its size would tell the model a thread was fully read when the newest replies never arrived; `comments_truncated` covers the fetch cap as well as this cap, and the text fallback says how many were omitted.
- **Neither read tool hides an outdated thread.** Feedback on code that has since changed is exactly what an address-feedback run must answer, and GitHub reports no `line` for most of them — so they list under their file with `is_outdated` set and no line, rather than being filtered out for having nowhere to anchor. Whether they can be *drawn* in the pane's Changes tab is a separate question (`Alveary/Views/PullRequests/AGENTS.md`); do not re-derive the tool filter from it.
- **`get_pr_diff` pages by whole file and always lists every file.** The complete map is what lets the model see the change's shape when patch text does not fit; `next_offset` resumes, `paths` narrows. A single file over budget yields whole hunks only — half a hunk mis-anchors every line number after the cut.

### Review Proposals

- **The proposal is a JSON envelope on `Conversation`, not a `@Model`.** The invariant is already one per conversation, and a new model with a `Conversation` inverse would have to be registered in every `ModelContainer` the app and its tests build. See the linked-pull-request precedent in `Alveary/Data/AGENTS.md`.
- **The envelope carries the staged comments, and its version decodes `<=`, refusing newer.** An optional field added later reads nil from an older envelope, but an envelope from a newer build is refused outright — a confirm must never submit less than the card showed. Bump `currentPayloadVersion` when adding a field a confirm acts on.
- **Confirming writes the staged comments into the viewer's pending draft, then submits it.** The draft is adopted when one exists — GitHub allows one per viewer, and submitting has always published the user's own draft comments — and `submitPendingReview` is the only publishing call, so a mid-flow failure leaves at most a private draft and the card retries. Retries dedupe staged comments against the refetched draft by anchor and trimmed body, so nothing double-posts.
    - **The pull request pane is a second confirm surface.** Its footer's Submit routes here so both sets publish as one review, passing its own summary as `bodyOverride` (nil falls back to what the model proposed). The card passes none.
- **The envelope has a second writer too: `addStagedComment`, for a comment composed in the pane.** It mirrors `removeStagedComment` — refuse while submitting, re-read the envelope before editing, no `payloadVersion` bump — but **invalidates the cached preview where removal prunes it**, because removal only subtracts while an addition may need a file or hunk the preview deliberately dropped. `maxReviewCommentsPerProposal` deliberately does not apply: it bounds one tool call's input, not what a person may write by hand.
- **Do not snapshot the pending review's node id.** It is resolved fresh at confirmation, because the draft can change on github.com between proposing and confirming.
- **Validate at propose time with the pane's own rules.** `PullRequestsViewModel.canSubmitReview` semantics plus the self-review and merged/closed refusals — and every staged comment's anchor against the live diff — so a proposal the user confirms cannot fail on a precondition the model could have seen.
    - **Anchors validate through `FlattenedDiffPreviewRows.commentAnchor(for:path:)`, the pane's own mapping**, never a raw line-number comparison. A context line carries *both* an old and a new number, so comparing `oldLineNumber` accepted a LEFT anchor on one — which the pane then could not draw, because it anchors a context line RIGHT only. LEFT therefore requires a deleted line. Sharing the mapping is what keeps a confirmable proposal renderable.
- **The pane renders *and edits* staged comments for its pull request, from any route.** The envelope is the source; `Alveary/Views/PullRequests/AGENTS.md` owns how the tabs merge, badge, add to, and submit them.
- **The user picks the verdict.** The card's picker defaults to what the model proposed and may submit a different one; the outcome marker records what was actually submitted, so resolved copy never names the wrong verdict.
- **The decision is invisible to the model.** The outcome marker is not an `isVisibleTranscriptEvent`, so confirming or cancelling sends nothing back and the model's last word stays `pending_confirmation`. The tool description and fragment must therefore say a repeated request is one to propose afresh — without that, "do not re-propose while one is pending" strands the model on a card the user already dismissed.
- **Announce the change the moment GitHub accepts, ahead of clearing the envelope.** That clear returns early on a save failure while the review is already live, so announcing after it would leave the pane showing the pre-review timeline on top of an unresolved card.
- **Clear the envelope, then write the marker, in two saves.** Folding them together lets a marker failure roll back the clear; failing between them leaves the card unresolved, never wrongly resolved — the safe direction when the alternative is a card claiming a review was submitted. `PullRequestReviewProposalOutcomeRecorder` owns the marker, mirroring scheduling's.
- **A revised proposal for the same pull request supersedes the old one**; one for a different pull request is refused while a proposal is pending, so a conversation never shows two live confirmations.

### Linking

- `PullRequestLinkService` is the app-scoped link store; `Alveary/ViewModels/PullRequests/Links/AGENTS.md` owns its split with `PullRequestLinksViewModel`, and `Services/Threads/AGENTS.md` owns the `link_pr`/`unlink_pr` tools that write through it.

### Agentic Threads

`PullRequestAgenticThreadService` spawns both footer routes. `Kind` is the whole difference between them — thread name, first prompt, and whether a checkout is resolved; add a caller by using the service, never by copying it.

- **A `.review` thread is project-less, never a project one.** Every step runs through the host tools against GitHub, so it needs no checkout — and a project worktree would have the agent reviewing whatever is checked out there rather than the pull request. `grantedRoots` stays empty for both kinds: the workspace root is the only grant either needs.
- **Seed resolution degrades, it does not refuse.** A pinned provider that is no longer ready, or a model or effort the provider retired, falls back to what a typed thread would get; only "no ready provider at all" throws. The trigger is a footer button with nowhere to explain a rejection, unlike `create_thread`, whose caller can correct itself.
- **Both routes for a job run one path, and the instructions tool is the seam.** The footer spawns a thread whose first prompt is a short request — *not* the instructions — and the agent fetches those itself, exactly as it does when the user asks in a thread that already exists. So the guidance cannot drift, both show the same card, and only the prompt differs. Do not inline the instructions here to save a round trip.
- **Answer as soon as the thread exists.** `start` returns `PullRequestAgenticThreadStart` the moment `insertTaskThread` succeeds, so the caller navigates without waiting on GitHub; linking used to precede the return and put a `gh api graphql` round trip between the footer click and the sidebar selection. Nothing may move back in front of it.
- **`dispatch` carries the rest, and links before dispatching**, best-effort, regardless of `automaticallyLinkPullRequests`. Linking first means transcript detection finds the pull request already linked and asks no redundant "link this?" question under the prompt. A GitHub hiccup must not stop the thread, and a racing auto-link resolves as `alreadyLinked`. Re-resolve the thread after that `await` rather than carrying the model across it.
    - Its only consumer is the caller's error toast — navigation already unmounted the footer that would have shown a banner. Do not give it a second consumer.
- **The pane hands over the detail it already fetched** as `knownDetail`, so the link costs no round trip on this route and the new thread does not sit empty waiting for one. Nil or naming a different pull request falls back to fetching; `Alveary/ViewModels/PullRequests/Links/AGENTS.md` owns the rule. `.addressFeedback` also reads its head branch, so a missing detail is fetched once and handed to both.

#### The Checkout Ladder

`+Workspace.swift` resolves where an `.addressFeedback` thread runs: a linked thread's checkout, then one already on the head branch, then a fresh worktree in a local project, then nothing. Its doc comment owns the ordering; these are the constraints behind it.

- **`thread.branch` stays nil on every rung, and so do `worktreePath` and `useWorktree`.** `cleanupOwnedTaskWorktree` computes `branchToDelete` from `branch` and `branch -D`s it when git still reports it on the worktree — here that is the user's live pull request head. A Task carries its checkout in the descriptor alone.
- **A borrow is `.projectLocal`, whose cleanup does nothing**, so deleting the thread leaves the lender's checkout intact. Only rung 3's own worktree is `.projectWorktreeOwned`.
- **A lender must have a source project.** A private workspace is a scratch directory rather than a checkout, and it belongs to a thread whose deletion would remove it — that filter is also what keeps the new thread from lending to itself once linking has put it in rung 1's results.
- **Branch-match must precede creating a worktree**: `git worktree add` refuses a branch already checked out elsewhere.
- **Every rung degrades rather than refuses**, silently. The thread already exists and the user is looking at it; the instructions have the agent check `git status` and its branch, so a private workspace makes it say so rather than edit the wrong tree.

### Instruction Tools

`get_pr_review_instructions` and `get_pr_address_feedback_instructions` are one pattern twice. Every rule below holds for both; each has its own editable prompt (`Alveary/Services/Settings/AGENTS.md`) and they share `PullRequestReviewPromptBuilder`'s context block, so only the user's text differs.

- **Calling one is how Alveary learns which job was asked for.** Deciding that from the wording of a message would need intent heuristics, and "I already reviewed #42" reads the same to a regex as "review #42" — so the decision stays with the model, which understands the sentence. A call made in error costs a read and nothing else.
- **The fragment is the only thing that routes to them.** It has to say, in the always-in-context text, that the user keeps standing preferences for both jobs and that these tools are the only way to read them; without that they exist and nothing calls them. It also has to say which job is which — reviewing gives new feedback and ends at `propose_pr_review`, addressing answers existing feedback and ends at `reply_to_pr_thread`/`resolve_pr_thread` — or "address the feedback" reaches the reviewing tool. The two `+…Instructions` test companions pin that wording.
- **The address-feedback name reads like a feedback reader, so its description disowns that outright** and names `get_pr_timeline` as what actually reads the comments. This is the `list_involved_prs`/`list_linked_prs` lesson applied before it cost anything: each description names its sibling, and a third instruction tool owes the same treatment.
- **They fetch the pull request rather than assuming it.** A URL naming one that does not exist fails here instead of halfway through work the model has already begun narrating.
- **One transcript card serves both**, keyed by `ReviewInstructionsWidgetContent.Kind`; `Alveary/Views/Chat/Blocks/AppKit/AGENTS.md` owns what the kind may change.
