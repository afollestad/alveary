## GitHub Pull Request Adapter

These instructions cover `Alveary/Services/PullRequests/GitHub/` — the `PullRequestsService` protocol, its `gh api` implementation, the GraphQL documents and wire shapes, the domain models, and the list cache.

This is the layer *below* the host tools and linking: dependencies run one way, so nothing here may reach `PullRequestHostToolService`, `PullRequestLinkService`, SwiftData, or MCP. `Alveary/Services/PullRequests/HostTools/AGENTS.md` and `Alveary/Services/PullRequests/AGENTS.md` own the consumer side.

**Keep a rule here only when the code that would violate it is not the code that documents it.** Mechanism whose only reader is its own file belongs in a doc comment: `PullRequestListOptions`, `PullRequestListPageInfo`, `mergeBucketOutcomes`, `listFragment`, `minimumRetryAttemptTimeout`, `PullRequestStatus.searchQualifier`, and `PullRequestURLTextScanner` each carry theirs. So does every endpoint choice in `+Mutations.swift` — which REST path a comment family takes, why both draft directions are GraphQL, why a reply needs the pull number, why `requestReview` takes logins only, and why `createPullRequest` alone runs in the worktree — and the pending-review and reviewer-composition rules on `makeReviews`, `makeReviewers`, and `PullRequestReviewThread.replyTargetCommentID`.

- **File layout.** Reads plus the shared shell/decode/error helpers live in `GitHubPullRequestsService.swift`; every write lives in `+Mutations.swift` — which is why those helpers are internal, not private.
- **Every mutation is unretried, and every call passes `standardInput: .nullDevice`.** A failed write may still have landed, so no mutation may join the read retry path. Inheriting stdin lets a credential or keychain prompt block the child until the timeout — a one-keystroke re-auth surfacing as an unexplained hang.
- Keep explicit `stdoutLimitBytes` on every call (list 4 MB, detail 8 MB, diff 5 MB matching the diff-viewer cap) and treat `stdoutWasTruncated` as `responseTooLarge`.

## Reads And Resilience

- **Never batch the buckets back into one request.** `listInvolvedPullRequests` fans out one GraphQL request per requested bucket, in parallel. GitHub runs a batched request's aliased searches *serially* — roughly one extra search's latency per added bucket — so three buckets in one request cost about three searches while three requests cost about one. The query text still aliases per bucket because each leg names exactly one.
    - **Do not read the fan-out as the proven cure for the "Host tool call timed out." failures that prompted it.** One bucket's real query measures ~4s, so serialization alone never reached the bridge's 30s budget, and that cause is still unconfirmed.
    - **A concurrent caller owes a barrier**, because applying the legs as they land settles the list twice. `Alveary/ViewModels/PullRequests/AGENTS.md` owns that rule, and why the screen keeps fanning out itself rather than handing several buckets to one call.
- **A field the list does not render stays out of the list fragment.** Every field there is computed *per row*, which is what dominates the query's cost; `listFragment`'s comment carries the measurements and names the two deliberate absences, and `GitHubPullRequestsServiceTests+List` pins both directions.
    - **`additions`/`deletions` stay despite costing ~2s**: rows render them and the host tool's list schema requires them. Removing them is the next lever if a larger account needs one, at that price.
- **`PullRequestStatusFilter` is the persisted selection, with its own `all` case** that the searched `PullRequestStatus` has no equivalent for. Narrowing is single-choice because GitHub search qualifiers only AND — `is:open is:merged` matches nothing — so a status set is not a feature to add later.
- `PullRequestsListCache` persists the buckets per status filter (JSON under app support) so the screen paints instantly on launch while the load runs behind it; treat load failures — including the retired flat file shape — as a cold cache.
- **Tolerate partial GraphQL results.** SAML-protected organizations make `gh` exit non-zero while still returning valid `data` plus per-node `FORBIDDEN` errors and `null` search nodes. Decode `data` regardless of exit code, drop `null`/empty nodes, and surface deduplicated error messages as `PullRequestListResult.warnings`, not a thrown error.
- **Retry transient 5xx on reads only.** List, detail, and diff calls retry HTTP 502-504 twice with backoff (`runGitHubCLIRetryingTransientFailures`). SAML partial failures are not retried — they carry no HTTP status and must fall through to the partial-decode path.
    - **A query GitHub *refuses to run* is `.queryTooExpensive`, never retried and never `.transport`.** It arrives as a GraphQL body error with no HTTP status, so `classify(graphQLMessage:)` runs from both null-data paths — `makeError` for stderr, `decodeGraphQL` for a body-only message, which is checked first because `makeError` cannot see the body. Retrying costs the same and fails the same way; the remedy is a cheaper query.
    - **List and detail run under a deadline the host-tool bridge sets: 20s per attempt, 25s including retries and backoff.** The bridge kills a tool call at 30s with a generic "Host tool call timed out.", so anything at or above that always lost the race and replaced every nameable failure with that message. Diff keeps 60s and no budget — it is sized for the pane, and an over-budget `get_pr_diff` is a documented gap, not an oversight.
    - **Read the HTTP status from the `HTTP` marker, not the first number present.** `gh` puts exit codes and pull request numbers on stderr too, and one landing first was returned as the status — reading a retryable 502 as a non-retryable 128.

## Review Mutations

- **Inline comments are server-side pending review comments, not a local batch.** Writing one creates (or reuses) the viewer's PENDING review on GitHub and attaches the comment immediately, so it appears on github.com and survives quitting Alveary — and, as the trade-off, cannot be drafted offline. It is all GraphQL: REST has no endpoint that adds a comment to an existing pending review, and pending comments are addressed by node id rather than the REST ids submitted comments use.
    - **One pending review per viewer per pull request**, so callers must serialize creation — see `pendingReviewCreationTasks` in `Alveary/ViewModels/PullRequests/Review/`.
    - **`submitReview` runs *only* when the viewer has no pending review**; otherwise `submitPendingReview` finishes the existing draft rather than opening a second review beside it. Inline comments never travel it — they are already attached to the pending review.
- **`addPullRequestReviewThread` shares `reviewThreadSelection` with the detail query.** The created thread must decode exactly like a fetched one so it can replace the optimistic placeholder; adding a field to only one of the two leaves freshly written pending comments missing state the UI reads.
    - **Its comment page is large and carries `totalCount`.** GitHub returns a thread's comments oldest-first with no cursor paging here, so a small page drops the *newest* replies — exactly where a thread says whether its point was already answered, which the address-feedback flow reads. `PullRequestReviewThread.totalCommentCount` keeps the count honest past the page, and `commentCount`/`hasUnfetchedComments` are what surfaces should read rather than `comments.count`.
- **Edit and delete affordances gate on GraphQL `viewerCanUpdate`/`viewerCanDelete`, never `viewerDidAuthor`** — GitHub grants collaborators those rights on other people's comments.

## Detail Query

- **The detail query surfaces the viewer's pending review and flags its comments.** GitHub only ever exposes the viewer's *own* pending review, so a hit on `pendingReview` is always their draft — including one started on github.com, which Alveary then adopts instead of creating a second. Pending threads ride the ordinary `reviewThreads` connection, so nothing local has to be merged in.
- **Reopening needs the head branch.** GitHub answers 422 once it is deleted, so the query selects `headRef { name }` (null after deletion, while `headRefName` keeps the name) and maps it to `PullRequestDetail.headRefExists` for the UI to gate on.
- The query also fetches the top-level `viewer` (login + avatar), so optimistic comments and reply placeholders carry the signed-in identity, and each thread root's `pullRequestReview { id }` (as `reviewNodeID`), so the Overview can nest threads under their review card. `timelineItems` maps in `+Timeline.swift`; unrecognized types drop.
