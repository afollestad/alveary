## Scheduled Task Host Tools

These instructions cover `Alveary/Services/Scheduled/HostTools/` — the natural-language scheduling tools scheduling enrolls on the shared `alveary_host` server, the proposal a conversation confirms, and the receipt and outcome marker that close it out. `Alveary/Services/HostMCP/AGENTS.md` owns the generic handler contract every feature inherits — strict validation, trusted identity, source-first reads, confirmation only where irreversible — and how a feature enrolls; the rules below are what scheduling adds. `Alveary/Services/Scheduled/AGENTS.md` owns execution and recovery, `Alveary/Data/Scheduled/AGENTS.md` the persisted rows, and `Alveary/Services/Agent/Transcript/HostToolWidgets/AGENTS.md` the card a proposal renders as.

**Keep a rule here only when the code that would violate it is not the code that documents it.** Mechanism whose only reader is its own file belongs in a doc comment: which actions apply without confirmation and why, `resolveSource`'s automated-run gating, the parser/service split over placement, inheriting on a `nil` placement, refusing an unregistered Project, why a drafted resolution stores the draft's Project, the dedup payload's canonical placement, and what each receipt and marker echoes each carry theirs.

- **Bind everything the model does not get to choose from trusted host state** — provider settings, permission mode, Project paths, and grants. Never expose a definition's prompt through a list result.
- **Scheduling's read surface is `list_scheduled_tasks` alone, and it takes no arguments.** An argument-taking read could be steered into probing. Placement reads borrow `list_projects` and `list_threads` from `Alveary/Services/Threads/AGENTS.md` rather than growing scheduling's own; `Alveary/Services/HostMCP/AGENTS.md` owns why pointing at another feature's tool is safe.
- **Run location stays host-bound.** No schema field reaches `workspaceStrategy` — a `localCheckout` schedule would mutate the user's real working copy unattended — and none reaches provider, model, effort, or permission mode either.
- **Store a new grant root canonically resolved**, so a symlink spelling cannot show the user one folder in the confirmation pane while granting another at run time. A root that is still inherited keeps its inherited literal. `Alveary/Services/Threads/AGENTS.md` cites this for its own grants.
- **Keep one FIFO proposal per source conversation.** Assign persisted positive enqueue ordinals so tied timestamps still order; `Alveary/Data/Scheduled/AGENTS.md` owns the pre-field `nil` case, and `Alveary/Services/HostMCP/AGENTS.md` the shared exact-retry key and receipt ledger every mutating feature uses.
    - **Persist a `pending_confirmation` receipt before returning it**, so consuming or rejecting that proposal cannot let a delayed exact retry open another. Run now additionally carries the proposal ID into occurrence identity, so a cleanup retry cannot launch duplicate work.
- **Write the `host_tool_outcome` marker in its own save, immediately after the save that consumed or deleted the proposal.** `ScheduledTaskProposalOutcomeRecorder` documents why folding it into that transaction traps inside SwiftData; the ordering is the precedent any future confirmation feature follows.
