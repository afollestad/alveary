## Git And Worktree Services

These instructions cover the services under `Alveary/Services/Git/`, including worktree management (`DefaultWorktreeManager`), the GitHub CLI adapter, and low-level git invocations.

## Worktree Lifecycle

- Worktree roots are namespaced by canonical project path under the user-configurable `AppSettings.worktreesBaseDirectory` (default `~/Documents/worktrees`); preserve that namespacing so sibling clones with the same repo folder name cannot collide. `DefaultWorktreeManager.projectWorktreesDirectory(for:worktreesBase:)` reads the expanded base via `AppSettings.expandedWorktreesBaseDirectory`, and `create` / `createFromBranch` must `ensureWorktreeParentDirectoryExists` before invoking `git worktree add` so a fresh base directory is populated.
- `AppSettings.branchPrefix` is literal. Include the separator in the setting/default (for example `alveary/` or `af-`) instead of injecting `/` in `DefaultWorktreeManager`.
- `DefaultWorktreeManager.validateCreation` mirrors predictable `create` prerequisites before a scheduled occurrence is claimed: the namespaced destination must have a writable/searchable existing ancestor and no configured-base/namespace symlink, the literal branch prefix must form a valid branch, and the resolved base must identify a commit.
- Scheduled worktree creation is identity-aware and write-ahead. Persist the intended target/branch before creating the target, then persist its captured identity before awaiting `git worktree add` and proven branch ownership before setup. Capture the namespaced target-parent identity and revalidate its canonical chain after the write-ahead recorder returns, both immediately before and after creating the target. Recheck source/worktree identities around every awaited Git/setup boundary and carry them through ownership registration and rollback; never fall back to the unchecked overload for an automated run.
- Worktree lifecycle scripts from `.alveary.json` have stable defaults and rollback behavior. `scripts.setup` runs in the new worktree with a default 300-second timeout unless `scripts.setupTimeoutSeconds` overrides it; `scripts.teardown` runs during removal with a 60-second timeout; both receive `ALVEARY_THREAD_NAME`, `ALVEARY_PROJECT_PATH`, `ALVEARY_WORKTREE_PATH`, optional `ALVEARY_BRANCH_NAME`, and `ALVEARY_PORT_SEED`. If `scripts.setup` fails, the manager must attempt to remove the new worktree and delete the rollback branch before surfacing the error.
- Preserved-file copying during worktree creation defaults to `.env`, `.env.local`, and `.env.development` when `.alveary.json` omits `preservePatterns`. Custom `preservePatterns` replace that default list.
- `DefaultWorktreeManager.create()` and `createFromBranch()` are self-cleaning on any failure after `ensureWorktreeParentDirectoryExists`, including task cancellation that interrupts `git worktree add` itself (which can leave an empty target directory behind when SIGTERM arrives mid-add). The internal catch runs `detachedCleanupAfterFailedCreate` as a `Task.detached` so the caller's cancellation cannot abort the removal shell commands; the ViewModel's `rollbackFailedWorktreeCreation` therefore does not need to know about partially-created worktrees. `createFromBranch` passes `rollbackBranch: nil` because it reuses an existing branch.
- `DefaultWorktreeManager.removeWorktree` must always follow `git worktree remove --force` with a checked `FileManager.removeItem` on the exact thread worktree path — even when the git command fails — because git leaves the directory behind both when untracked content/filesystem quirks interfere and when it never registered the worktree at all. Propagate removal errors and verify that no directory or symlink entry remains; never remove the shared parent directory.
- Branch deletion requires the exact ref OID proven while the branch is still associated with its owned worktree. Reject it before invoking Git unless it is a full nonzero ASCII-hex SHA-1 or SHA-256 object ID. Use atomic `git update-ref -d -- <ref> <expected-old-oid>`; a missing OID or changed/recreated ref must leak rather than fall back to name-only deletion. Treat only `git show-ref` exit 1 as absent when diagnosing a failed atomic delete, and expose a retryable error only when the exact expected ref is proven to remain.
- Project deletion cleans exact persisted thread worktrees only. Do not call `removeAll(projectPath:)`: projectless Task worktrees and user-created worktrees can share the same source repository and must survive unrelated Project deletion.
- Task-owned worktree cleanup must validate both the owned worktree record and its recorded source-project directory identity before invoking Git. If the source path is missing, replaced, or now a symlink, remove only an identity-matching owned worktree directory/sidecar and never run Git against the replacement source. A retry may treat cleanup as complete only when both the canonical persisted worktree path and its sidecar are absent; `lstat`-style path-entry checks must treat broken symlinks as replacements and preserve them.

## GitHub CLI

- `gh auth login --web` does not auto-open the browser without a TTY. GitHub auth flows in the app must continue parsing the emitted URL/code and opening the browser explicitly.
- **A failed attachment upload is usually a privacy grant, not a sign-in.** The extension reads the browser cookie store, and a spawned child inherits *Alveary's* TCC grants, not the shell's — so Safari (cookies in a TCC-protected container) fails from the app while succeeding from a Terminal that has Full Disk Access. Chrome instead needs the login-Keychain "Chrome Safe Storage" item, which prompts once and grants far less than Full Disk Access. Keep `.sessionUnavailable`'s copy pointed at those two remedies rather than telling the user to sign in again; the pull-request UI surfaces that failure as a guidance sheet, not a toast (see `Alveary/Views/PullRequests/AGENTS.md`).
- **`GitHubAttachmentAccessGuide` owns the Full Disk Access remedies.** macOS has no prompt API for Full Disk Access, so the guide can only probe and deep-link: `canReadSafariCookieStore()` attempts the same cookie-store read `gh image` performs (a denied attempt still registers Alveary in the Full Disk Access pane's app list, making the grant a single toggle), and `openFullDiskAccessSettings()` uses the same dual-URL System Settings fallback as `AppShotPermissionRequester` with the `Privacy_AllFiles` anchor. Do not add a drag-grant overlay here — the probe registration makes it unnecessary, unlike the AppShots permissions whose debug-build rows go stale.
- **`GitHubAttachmentImageURLResolver` mints anonymously fetchable attachment-image URLs.** `github.com/user-attachments` assets are served only to a signed-in browser session — always in private repositories, and even public ones until the embedding content is saved and propagated — so the app cannot fetch them directly. `gh api /markdown` with a repository `context` rewrites such URLs to `private-user-images.githubusercontent.com` links carrying a ~5-minute JWT that downloads with no credentials (without `context` no rewrite happens). The resolver tries recently registered repositories most-recent-first (PR panes register on open), caches mints for 3 minutes, and feeds `AppMarkdownImageStore.remoteFallbackURLProvider`; bytes then persist in the shared disk cache under the original URL's key, so the mint happens at most once per asset.
- **Comment attachments need a browser session, so they go through `gh image`.** `GitHubAttachmentUploadService` runs `gh image --repo owner/repo -- <files>` (the `--` guards dash-leading filenames) and maps stdout lines to markdown references one-per-file, failing with `.incompleteOutput` when the counts disagree. GitHub's web upload endpoints accept only the `user_session` cookie — a `gh` token is ignored, not merely under-scoped — so there is no token-based alternative to add here; see the attachment bullets in `Alveary/Views/PullRequests/AGENTS.md`. Classify failures by stderr (`unknown command` → extension missing, `UserAsset`+`size` 422 → too large, session/cookie wording → sign-in needed), keep `standardInput: .nullDevice` so a prompt cannot hang the upload, and keep the timeout upload-sized rather than metadata-sized. `GitHubAttachmentSizeLimit` pre-flights GitHub's per-kind attachment limits (images 10 MB, videos 100 MB, other files 25 MB) before invoking the extension, so an oversized file fails instantly with a clean message instead of the policy endpoint's HTML-laden 422; the stderr classification backstops files that slip past the pre-flight.

## Pull Requests

- **`PullRequestURLTextScanner` matches URLs only**, unlike `PullRequestURLParser`, which also accepts the `owner/repo#123` shorthand: in free-form message text that shape is far more often an issue reference. Trimming trailing punctuation off each candidate is load-bearing — the parser rejects a number segment with any trailing non-digit.
- **File layout.** Reads plus the shared shell/decode/error helpers live in `GitHubPullRequestsService.swift`; every write lives in `+Mutations.swift` — which is why those helpers are internal, not private. GraphQL query text, node-to-model mapping, and wire shapes split across `+GraphQL.swift` / `+GraphQLMapping.swift` / `+GraphQLNodes.swift`; detail-side models live in `PullRequestModels.swift`, `PullRequestListPaging.swift` keeps the paging and date-bound inputs, and `PullRequestsService.swift` keeps the protocol, list models, and error type.

### Reads And Resilience

- **Fetching is bucket-demand-driven, one request per bucket.** `listInvolvedPullRequests(buckets:status:options:)` takes the involvement buckets the caller renders (`author:@me`, `review-requested:@me`, `reviewed-by:@me`) and fans out one GraphQL request per bucket in parallel, merged via `PullRequestListMerge`. Fetching *fewer* buckets is still the point — a tab rendering one involvement pays for one search, and one bucket skips the fan-out entirely. `Alveary/ViewModels/PullRequests/AGENTS.md` owns which tab needs what and how buckets are reused.
    - **`PullRequestListOptions` carries the page size, per-bucket `after:` cursors, and `updated:` bounds, and every default reproduces the pre-pagination call.** `.firstPage` is 50 rows per bucket, no cursors, no bounds — so a caller that passes it cannot change what goes on the wire. `resolvedPageSize` clamps into GitHub's 1–100 `search` ceiling; the `$<bucket>After` variable is declared on every leg but given a value only for a bucket that has one, so the document text is identical for a first page and a resumed one. The `updated:` qualifiers ride into `searchQuery` at day granularity in UTC (`PullRequestSearchDates`), matching what the host tool's schema advertises.
    - **The list selects `edges { cursor node }`, not `nodes`.** `PullRequestListPageInfo.rowCursors` aligns index-for-index with that bucket's summaries — an edge that maps to nothing contributes neither — so a caller that emitted only a *prefix* of a page can resume from the row it stopped at. Advancing to `endCursor` instead would silently drop everything it did not emit; `Alveary/Services/PullRequests/AGENTS.md` owns the host tool's use of that.
    - **Never batch the buckets back into one request.** GitHub runs a batched request's aliased searches *serially* — roughly one extra search's latency per added bucket — so three buckets in one request cost about three searches while three requests cost about one. Do not read the fan-out as the proven cure for the "Host tool call timed out." failures that prompted it: one bucket's real query measures ~4s, so serialization alone never reached the bridge's 30s budget and that cause is still unconfirmed. The query text still aliases per bucket because each leg names exactly one.
    - **A multi-bucket call degrades to a partial result; only every bucket failing throws.** `mergeBucketOutcomes` leaves a *failed* bucket **absent** from `summariesByBucket` and names it in `warnings`, which is what distinguishes it from the SAML-forbidden bucket below — that one decodes as null and stays keyed as loaded-and-empty. All legs failing throws the first failure in `allCases` order, so completion order cannot change the error.
    - **The invariant on the screen side is one *settle*, not one request.** What must never happen is applying the legs as they land: per-bucket *publishes* made the list settle in multiple UI invalidations, which read as loading twice. The screen keeps fanning out itself rather than passing several buckets here, because it needs per-bucket failure attribution for `bucketFailures`; a concurrent caller owes a barrier, and `Alveary/ViewModels/PullRequests/AGENTS.md` owns that rule.
    - **Keep `statusCheckRollup` out of the list query** — the list never renders check state, and rollup is the field that makes GitHub's GraphQL search slow and 502-prone; the detail query still fetches it.
    - **Key the result by the buckets that were *requested*, not the ones that returned nodes.** A SAML-forbidden bucket decodes as `null` and must still read as loaded-and-empty, or the caller treats it as never fetched and asks again on every pass. Its `pageInfoByBucket` entry is `.exhausted` for the same reason — more-pages-unknown would have a caller page a bucket GitHub will never answer.
    - `PullRequestsListCache` persists the buckets per status filter (JSON under app support) so the screen paints instantly on launch while the load runs behind it; treat load failures — including the retired flat file shape — as a cold cache.
- **`status` narrows every requested bucket, and the selection is single-choice because GitHub search has no `OR`.** Qualifiers only AND, so `is:open is:merged` matches nothing; `PullRequestStatus.searchQualifier` owns the per-status text, and `PullRequestStatusFilter` is the persisted selection with its own `all` case. Two qualifiers are not obvious and must not be "simplified": drafts are open pull requests, so open-only needs `draft:false`, and `is:closed` alone counts merged ones, so closed-only needs `is:unmerged`.
- **Retry transient 5xx on reads only.** List, detail, and diff calls retry HTTP 502-504 twice with backoff (`runGitHubCLIRetryingTransientFailures`); review submission never retries because it is not idempotent. SAML partial failures are not retried — they carry no HTTP status and must fall through to the partial-decode path.
    - **List and detail run under a deadline the host-tool bridge sets: 20s per attempt, 25s including retries and backoff.** The bridge kills a tool call at 30s with a generic "Host tool call timed out.", so anything at or above that always lost the race and replaced every nameable failure with that message. `nextRetryAttemptTimeout` shortens or abandons a retry that would not fit; a thrown timeout never retries, so attempts cannot compound. Diff keeps 60s and no budget — it is sized for the pane, and an over-budget `get_pr_diff` is a documented gap, not an oversight.
- **Every `gh` call here runs with `standardInput: .nullDevice`, the default on `runGitHubCLI`.** Nothing feeds `gh` on stdin, and inheriting it lets a credential or keychain prompt block the child until the timeout — a one-keystroke re-auth surfacing as an unexplained hang. `createPullRequest` still passes it explicitly, as documentation.
- **Tolerate partial GraphQL results.** SAML-protected organizations make `gh` exit non-zero while still returning valid `data` plus per-node `FORBIDDEN` errors and `null` search nodes. Decode `data` regardless of exit code, drop `null`/empty nodes, and surface deduplicated error messages as `PullRequestListResult.warnings`, not a thrown error.

### Review Mutations

- **Inline comments are server-side pending review comments, not a local batch.** Writing one creates (or reuses) the viewer's PENDING review on GitHub and attaches the comment immediately, so it appears on github.com and survives quitting Alveary. All GraphQL, because REST has no endpoint that adds a comment to an existing pending review, and because pending comments are addressed by node id rather than the REST ids submitted comments use: `addPullRequestReview` **without** `event` opens the pending review (omitting `event` is what leaves it pending), `addPullRequestReviewThread` adds one anchored comment and returns the created thread, `updatePullRequestReviewComment` / `deletePullRequestReviewComment` edit and delete one, `deletePullRequestReview` discards an emptied draft, and `submitPullRequestReview` publishes it. GitHub allows **one pending review per viewer per pull request**, so callers must serialize creation — see the `pendingReviewCreationTasks` bullet in `Alveary/ViewModels/PullRequests/AGENTS.md`. The trade-off is that inline comments can no longer be drafted offline.
- **`addPullRequestReviewThread` shares `reviewThreadSelection` with the detail query.** The created thread must decode exactly like a fetched one so it can replace the optimistic placeholder; adding a field to only one of the two leaves freshly written pending comments missing state the UI reads.
    - **Its comment page is large and carries `totalCount`.** GitHub returns a thread's comments oldest-first with no cursor paging here, so a small page drops the *newest* replies — exactly where a thread says whether its point was already answered, which the address-feedback flow reads. 100 covers every realistic thread; `PullRequestReviewThread.totalCommentCount` keeps the count honest past it, and `commentCount`/`hasUnfetchedComments` are what surfaces should read rather than `comments.count`.
- **`submitReview` is summary-only.** It runs *only* when the viewer has no pending review, posting `event` + `body` to `POST .../reviews` as plain `-f` pairs like every other mutation here; otherwise `submitPendingReview` finishes the existing draft rather than opening a second review beside it. Inline comments never travel this endpoint — they are already attached to the pending review, so nothing here needs a JSON body any more (this used to encode a batch to a temp file passed via `gh api --input`, because `ShellRunner` has no stdin-data mode; that path and its injectable writer are gone).
- Keep explicit `stdoutLimitBytes` on every call (list 4 MB, detail 8 MB, diff 5 MB matching the diff-viewer cap) and treat `stdoutWasTruncated` as `responseTooLarge`.
- Comment edit/delete affordances gate on GraphQL `viewerCanUpdate`/`viewerCanDelete`, never `viewerDidAuthor` — GitHub grants collaborators those rights on other people's comments. Review-thread comments PATCH/DELETE `pulls/comments/{id}`; top-level conversation comments are issue comments and PATCH/DELETE `issues/comments/{id}`; review summary bodies PUT `pulls/{number}/reviews/{id}` and have no delete — GitHub only deletes *pending* reviews. Reactions use the `addReaction`/`removeReaction` GraphQL mutations addressed by the subject's node `id` (issue comments, reviews, and thread comments all take them); thread replies POST `pulls/{number}/comments/{rootID}/replies` (the pull number is required — `pulls/comments/{id}/replies` 404s even though the shorter form works for GET/PATCH/DELETE), and resolution uses `resolveReviewThread`/`unresolveReviewThread` with the thread's node id. Like every mutation here, none retry.

### State Changes And Creation

- **Close and reopen are a `state` PATCH on the pull itself.** `setPullRequestClosed(_:closed:)` sends `state=closed` / `state=open` to `repos/{owner}/{repo}/pulls/{number}` — the same endpoint the description edit uses — and never retries. Reopening needs the head branch: GitHub answers 422 once it is deleted, so the detail query selects `headRef { name }` (null after deletion, while `headRefName` keeps the name) and maps it to `PullRequestDetail.headRefExists` for the UI to gate on.
- **`createPullRequest` is the second non-`api` `gh` invocation here (after `pr diff`), and the only one that runs in the worktree.** GitHub's `createPullRequest` GraphQL mutation needs a repository node id the caller does not have, while `gh pr create` resolves the repository from the working directory — so `runGitHubCLI` takes an optional `in directory:` that only this call passes — and prints the new URL, parsed by `parseCreatedPullRequestIdentifier` (last URL-shaped stdout line; none ⇒ `.decodingFailed`). `--title`/`--body` ride argv because `ShellRunner` has no stdin-data mode. A mutation: never retried.
- **Both draft directions are GraphQL, not REST.** GitHub publishes no REST endpoint for either, so `markPullRequestReadyForReview(nodeID:)` and `convertPullRequestToDraft(nodeID:)` run the mutations of the same names against `PullRequestDetail.nodeID` (already fetched for PR-body reactions), following the `reactionArgs` / `threadResolutionArgs` shape. Like every mutation here neither retries, and a caller without a node id must not offer the action at all.

### Detail Query

- **The detail query surfaces the viewer's pending review and flags its comments.** `pendingReview: reviews(first: 1, states: [PENDING])` maps to `PullRequestDetail.pendingReviewNodeID` — GitHub only ever exposes the viewer's *own* pending review, so a hit there is always their draft, including one started on github.com, which Alveary then adopts instead of creating a second. Thread comments select `state`, mapped to `PullRequestComment.isPending` (`PullRequestReviewThread.isPending` derives from the root comment); pending threads ride the ordinary `reviewThreads` connection, so nothing local has to be merged in. `makeReviews` **drops** `.pending` reviews: a draft is not activity and must never render as a timeline review card or a reviewer verdict. `PullRequestReviewThread.replyTargetCommentID` skips pending comments — GitHub takes no reply until the review is submitted.
- The detail query also fetches the top-level `viewer` (login + avatar) so optimistic pending comments and reply placeholders carry the signed-in identity, and each thread root comment's `pullRequestReview { id }` (surfaced as `PullRequestReviewThread.reviewNodeID`) so the Overview can nest threads under their review card, and `timelineItems` covers draft/ready, closed/reopened/merged, pushed commits, force pushes, and review-request changes (mapped in `GitHubPullRequestsService+Timeline.swift`; unrecognized types drop). `makeReviewers` sets `canReRequest` only for human reviewers with a submitted review — `POST .../requested_reviewers` only accepts user logins, so app/bot reviewers (Copilot, Codex) must never offer re-request.

## Ahead Commits

- The ahead-of-base family lives in `CLIGitService+AheadCommits.swift`: count, details, the unpushed check, and their shared ref helpers. `GitService.hasUnpushedCommits`'s distinction from `commitsAheadOfBase` is documented on the protocol.
- `GitService.commitsAheadOfBase` and `commitsAheadOfBaseDetails` must share the same compare-ref resolution, and it is anchored on the **resolved default branch**, not the caller's `baseBranch`:
    - Resolve the remote with `effectiveRemoteName`, then the default branch with `resolvedDefaultBranch`. Prefer `<remote>/<default>` when its remote-tracking ref is known to exist, otherwise the local default branch.
    - Only when nothing resolves does the caller's `baseBranch` come into play: `<remote>/<baseBranch>`, then the local `baseBranch`, then the current branch upstream, then `baseBranch` as-is.
    - **Treat `baseBranch` as a hint, never the authority.** It comes from `Project.baseRef`, which `SidebarViewModel.resolveBaseRef` captures once at project import and falls back to whichever branch was checked out then — there is no re-detection and no override UI. A project imported on a feature branch used to make this resolve to the current branch's upstream, which turned the Commits tab into "commits not yet pushed". A Task thread carries no project and so no `remoteName` at all, which hit the same path.
    - **On the default branch the answer is still the unpushed commits**, because the compare ref is the remote-tracking form; off it, the list is everything the default branch does not have yet. Both are wanted.
    - Keep count and detail behavior aligned so contextual actions and commit views agree about which commits are ahead.

## Default Branch

- `CLIGitService+DefaultBranch.swift` owns default-branch resolution; its doc comments cover the resolution order, `hasRemoteTrackingRef`, and the `effectiveRemoteName` fallback. The conventional `<remote>/main`/`<remote>/master` probes are load-bearing, not paranoia — only `git clone` writes `refs/remotes/<remote>/HEAD` and plenty of working clones lack it.
- The `refs/remotes/<remote>/HEAD` parsing is deliberately duplicated in `SidebarViewModel.parseRemoteHead`. That view model holds a `ShellRunner` rather than a `GitService`, so sharing would mean injecting a new dependency and churning the import-invocation assertions in `SidebarViewModelTests`.
- **`GitServiceTests+Commits.swift` asserts exact `MockShellRunner` invocation sequences.** Any probe added or removed here shifts those indices, so update the enqueued results and the asserted argv together.

## Diff Stats

- `GitService.diffStats(in:knownStatuses:)` (consumed by `DiffWorkspaceStore`):
    - **Use `git diff --numstat`.** Keep parsing machine-readable numstat output instead of localized shortstat text.
    - **Include both scopes.** Sum unstaged `git diff --numstat --` and staged `git diff --cached --numstat --` output so the toolbar reflects all tracked current changes.
    - **Include readable untracked files.** Since Git omits untracked files from `diff --numstat`, add Git-style new-file line counts from porcelain status for small readable untracked files.
    - **Reuse status rows.** When a caller already loaded `status(in:)`, pass those rows into `diffStats(in:knownStatuses:)` instead of running another porcelain status scan.
    - **Share synthetic new-file logic.** Keep untracked toolbar stats and `syntheticAddedDiff(for:in:)` using the same helper so the toolbar and lower-pane preview agree. Match Git intent-to-add behavior: a final newline terminates the last line, it does not add another blank line.
    - **Skip binary rows.** Numstat reports binary files as `-\t-`; ignore those rows rather than guessing line counts. Apply the same skip behavior to untracked files that are binary, too large, or unreadable.

## Image Blobs

- **Keep blob reads binary-safe and bounded.** Image preview loading uses `GitService.imageBlob(source:maxBytes:in:)`; preserve raw stdout bytes for git objects and reject oversized source blobs before decode.
- **Open worktree images directly.** Worktree image sources already exist on disk and should not be copied to temp files for Preview. Commit, parent, HEAD, and index sources still need temp materialization.
