## Pull Request Link View Models

These instructions apply to files under `Alveary/ViewModels/PullRequests/Links/`. Detection of links in a transcript is a separate concern — see `Alveary/ViewModels/Conversation/AGENTS.md`.

- **Links belong to `PullRequestLinksViewModel`, not `PullRequestsViewModel`.** The split is the `ModelContext`: the browsing view model owns list state and pane sessions with no context, while the link store owns the context and writes the owner's `linkedPullRequests` through `PullRequestLinkOwner` (thread or project — see `Alveary/Data/PullRequests/AGENTS.md`). Do not give `PullRequestsViewModel` a context to shorten the path.
- **The durable half is `PullRequestLinkService`**, app-scoped, because the `alveary_host` `link_pr`/`unlink_pr` tools have no window to route through. This view model keeps only the UI half — `isLinking`, error copy, the Git-settings route — and delegates; its typed outcomes are what let one caller show "already linked" while a silent race stays silent.
- **Validate by fetching.** `link(urlText:owner:)` parses through `PullRequestURLParser` and funnels into `link(_:owner:)`, which proves the pull request exists with `service.fetchDetail(_:)` — the same call producing the stored snapshot — so an opened pane always has a real summary. The identifier overload is the create-pull-request flow's entry point.
    - **A caller holding a fresh copy may hand it over instead of the fetch.** The pane's agentic threads pass the detail they just fetched as `detail:`; `link_pr` passes a recent `list_involved_prs` row as `summary:`, read from the app-scoped `PullRequestSummaryHandoff`. The invariant is that a link never snapshots something unreachable, not that `link` is personally the fetcher; a handover naming a different pull request is ignored and the fetch runs.
- **Open panes through the browsing view model** (`PullRequestsViewModel.requestDetails(_:)`); this store owns no pane state. Its identifier overload is for callers with no summary — a transcript unlink card names a pull request that is deliberately not linked. It is synchronous: a listed row supplies a summary, and otherwise the session opens with `summary == nil` and `loadDetail` backfills it from the detail it already fetches. Everything reading `PullRequestPaneSession.summary` must therefore tolerate nil until that lands, and the backfill stays nil-only — overwriting a real snapshot would replace an involvement-search `isAuthored` with one derived from a possibly-absent `viewerLogin`, loosening the review footer's verdict gate.
- **Keep detected links off the popover's state.** `linkDetectedPullRequest(_:threadID:)` in `+DetectedLinks.swift` never writes `isLinking` / `linkErrorMessage` — a background link would otherwise disable the popover's button or show an error where nobody is looking — and it throws instead, for the app root to surface. It clears matching pending prompts in the same save as the link.
