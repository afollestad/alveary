## Pull Request View Models

These instructions apply to files under `Alveary/ViewModels/PullRequests/`. The link store has its own scope in `Links/`, transcript link detection is in `Alveary/ViewModels/Conversation/AGENTS.md`, the pane session/generation contract is in `Alveary/ViewModels/AGENTS.md`, and `Alveary/Views/PullRequests/AGENTS.md` owns the user-facing half.

### List Loading

- **The list loads per tab, one request per bucket, and `items` is derived.** `PullRequestsViewModel+Loading.swift` keeps a `PullRequestBucketState` per involvement bucket and fetches only `PullRequestsFilter.requiredBuckets` for the visible tab, skipping buckets in flight or fetched within `refreshInterval`. Rows reach `items` only through `bucketStates` and `rebuildItems()`; `items` keeps a private setter to enforce that, so `applyStatus(_:toRow:)` writes through every bucket holding the row.
- **A tab's buckets fetch concurrently and land on one barrier.** `fetchConcurrently` issues a request per bucket; `apply(_:)` is the single pass that writes them, because publishing per leg settles the list — and writes the disk cache — once per bucket, which reads as loading twice. Apply successes before failures: a healthy sibling clears its own `bucketFailures` entry, and the `hasLoadedData` check choosing between a banner and `.unavailable` must see the rows just landed. Dedupe the legs' `warnings`, one SAML message per bucket. `Alveary/Services/Git/AGENTS.md` owns why the split is worth it.
- **A cancelled load applies nothing, including the legs that succeeded** — that would stamp a half-loaded tab with a fresh `fetchedAt`, and the freshness throttle would then suppress the load meant to complete it. Check `Task.isCancelled` at the barrier, not the thrown type; shell teardown wraps cancellation in a `PullRequestsServiceError`.
- **A tab still settles once.** The accepted cost is that switching tabs paints the buckets already held and merges late ones in — legible because the All tab is sectioned, so a late bucket appends rather than reshuffles. Do not "fix" this back into an eager fetch of everything.
- **`loadPhase(for:)` and `isRefreshing` are derived, never stored.** Anything loaded renders, so a bucket that failed beside a healthy one shows the error banner over rows, a tab whose buckets all failed is `.unavailable`, and a cancelled load leaves no trace at all.
- **A status change marks every bucket stale rather than dropping it** — `markAllBucketsStale()`, which a remote-change announcement also runs, because the mutation may have moved rows in buckets the visible tab does not render. Rows stay so the client-side status filter narrows them instead of blanking a correct list; the visible tab reloads at once, the others when next shown. A load finishing after the filter moved discards its result and re-drives, since the buckets it held were skipped as in-flight.
- **Keep the client-side status comparison alongside the search qualifier.** It is what leaves the qualifier only ever able to make the list *sparse* rather than *wrong*: `items` still answers the previous search between a status change and its reload, and `applyStatus` has no reload behind it.
- **`prefetchAtLaunch()` and the screen's own `.task` are one loading path, not two.** Both go through `refreshForScreen()` and share the freshness throttle, so the launch warm makes the first visit issue nothing rather than race it. Gate any new automatic trigger on `AppSettings.pullRequestsEnabled` the same way, and delegate rather than reaching `load` directly.
    - **Accepted:** a failed prefetch opens the screen on `.unavailable` for a frame before its own load retries — the failure records no `bucketStates` entry, so the throttle never suppresses that retry.

### Search

- **The field's query and the list's are separate properties.** `searchQuery` is the field's, republished per keystroke; `activeSearchQuery` is what `visibleRows(for:)`, `matchesSearch`, and `hasActiveNarrowing` read, committed once `searchDebounce` elapses and trimmed there rather than per row per pass. Point new search-derived state at the committed one, or the rows and the empty-state copy disagree mid-debounce.
- **`searchDebounce: .zero` commits synchronously, with no `Task` hop.** That is the seam tests and snapshot fixtures rely on; a fixture left on the production duration renders the unnarrowed list.

### Detail Pane

- **Only the open pane keeps its loads.** `PullRequestsViewModel+PaneLoading.swift` stores each target's detail/diff `Task` in `paneLoadTasks`; `openPane` cancels every *other* entry, and both `deactivatePane(_:generation:)` and `dismissPane` cancel their own. Keying that off `activePaneTarget` would miss the route-only `deactivatePane()`, which nils the active target while deliberately leaving loads running.
- **Cancellation is the concurrency bound — do not add a semaphore or numeric cap.** One live pane means at most two requests in flight and a list load at most three (`requiredBuckets`, deduped by `inFlightBuckets`), so no cap scoped to pane loads could bind first. Anything bounding PR traffic more broadly belongs at `GitHubPullRequestsService.runGitHubCLI`, which the host tools and proposal coordinator also pass through.
- **A cancelled load must leave the session untouched.** Both `catch` blocks check `Task.isCancelled` before writing, because shell teardown wraps cancellation in a `PullRequestsServiceError`. That is also what makes the session *detectably incomplete*, which is how `resumeIncompleteLoads` tells "interrupted" (restart on reopen) from "failed" (keep the banner) and "loaded" (stay cached).
- **A failed leg is retried only by `retryDetailLoad()` / `retryDiffLoad()`, never by reopening.** Reopening restarts interrupted work silently, which is safe; doing the same for failures would refetch a pull request that reliably 404s every time. The Overview's error banner and the Changes tab's empty state carry the buttons; `.tooLarge` gets none, because an identical request cannot pass a fixed cap.
- **Completion cleanup matches on `PullRequestPaneLoad.token`, not the task or generation.** A restart reuses the session's generation, so without the token a cancelled load's cleanup clears its replacement's handle and the next reopen starts a duplicate fetch.
- **A pull request changed outside the pane reaches it through `.pullRequestChangedOnGitHub`.** Nothing in `PullRequestDetail` or the list's review-requested bucket is derived locally, so a review confirmed on the transcript card and every `alveary_host` mutation land only as a refetch.
    - **Observe it synchronously (`queue: nil`)**, which is what makes the `pendingReview.isSubmitting` skip deterministic: the pane's own footer Submit holds that flag across `confirm` and its epilogue, while an async stream would resume after it and refetch twice.
    - **Debounce the refetch and register it in `paneLoadTasks`.** One agent turn answers and resolves several threads, and this can fire for a *retained* session — the case `cancelPaneLoads(except:)` exists to bound.
    - **A background reload passes `reportsFailure: false`.** The Overview's error banner offers no dismiss because it is written for a first load with nothing to show; a flaky network must not strand it over a detail that still renders.
    - **Do not make `openPane` refetch a retained session instead.** Reopening stays instant, and refetching there would also retry a failed leg, which only `retryDetailLoad()` may.

### Comments And Review Proposals

- **Inline comments are optimistic *and* server-owned.** `PullRequestsViewModel+PendingComments.swift` inserts a placeholder thread (local `nodeID` from `PullRequestDetail.placeholderThreadNodeID()`, no comment ids, so no menu) and closes the composer, then swaps GitHub's copy in by that id. Failure withdraws the placeholder and reopens the composer with the text intact — no local fallback bucket, so GitHub stays the single source of truth. Insert and swap are idempotent upserts keyed by node id, because a concurrent `loadDetail` can land mid-flight.
- **Serialize pending-review creation.** GitHub allows one pending review per viewer per pull request, so two quick saves must not each `addPullRequestReview` — the second is rejected and its comment lost. The first caller stores its create in `pendingReviewCreationTasks[target]` and the rest await that same `Task`; a failure clears the slot so the next attempt may retry. Do not poll session state for this — a spin loop burns the main actor for the whole round trip.
- **`PullRequestsViewModel` holds the review-proposal coordinator, and that is not the `ModelContext` it does without.** The coordinator owns its own private context, so the split with `PullRequestLinksViewModel` stays intact. `pendingReviewProposal(for:)` resolves through it on every read rather than caching a presentation — that is what drops a proposal resolved anywhere out of the pane, with no observer to keep in sync.
- **`PullRequestReviewProposalCoordinator.removeStagedComment` prunes, it never refetches.** Removal only subtracts, so it rewrites the envelope and narrows the already-loaded `PullRequestReviewProposalPreview` in place; refetching would put a `fetchDetail` plus `fetchDiff` and a loading flash behind a click, and re-deriving would mean retaining the parsed diff the coordinator drops on purpose. It signals through `.reviewProposalCardStateChanged`, never the lifecycle notification — nothing resolved and no transcript record moved. Its sibling `addStagedComment` shares every rule but that one; `Alveary/Services/PullRequests/AGENTS.md` owns why an addition invalidates instead.
    - **Whoever cancels a preview task also clears its handle.** `addStagedComment` cancels an in-flight load, so `ensurePreview`'s task clears `previewTasks` only *after* its cancellation guard; clearing on the way out would wipe the handle of the reload that replaced it.
- **A pending proposal reroutes the pane's composer and its Submit.** `saveComposerComment` stages into the envelope rather than posting a pending comment, and `submitReview` delegates to `confirm(bodyOverride:)` so both sets publish as one review, then runs the same `loadDetail` + `requestRefresh` epilogue the GitHub-draft path does. `submittableCommentCount(for:session:)` is the single count both the footer and `submitReview`'s guard read; it takes the session rather than looking one up, so the footer resolves for the session it was handed.
