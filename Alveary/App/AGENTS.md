## App Lifecycle And Root Layout

These instructions cover the app entry point, `AppDelegate`, and the root `ContentView` scaffolding under `Alveary/App/`.

## macOS Lifecycle and Concurrency

- Keep `NSApplicationDelegate` implementations such as `AppDelegate` on `@MainActor`.
- When Swift 6 strict concurrency and AppKit interop fight in lifecycle code, prefer small explicit seams: injected dependencies for startup/shutdown behavior, and `@preconcurrency import AppKit` only where needed to bridge sendability gaps.
- `.appWillTerminate` is an early shutdown contract, not a best-effort hint. Observers owning teardown required before process exit (file watchers, debounce tasks) must complete synchronously on the main actor, not behind `Task` hops.
- Flush app-scoped conversation controllers synchronously before `AgentsManager.beginShutdown()` tears down provider runtimes.
- Shutdown paths that must finish before process exit should not rely on queued `Task { @MainActor ... }` cleanup; prefer synchronous main-actor teardown ahead of blocking termination waits.
- To hop to the main actor from a delegate callback not guaranteed to run on main (for example `UNUserNotificationCenterDelegate`), use `Task { @MainActor in ... }` — never `DispatchQueue.main.async` plus `MainActor.assumeIsolated`. `assumeIsolated` remains right inside callbacks already delivered on main, such as `NotificationCenter` observers registered with `queue: .main` or synchronous `deinit` work on a `@MainActor` type.

## Layout And Launch Restore

### Right-Pane Lane And Routing

- The app layout is a two-column `NavigationSplitView` with one shared contextual right-pane lane. `RightPaneDestination` gives matching Skills, MCP, or Scheduled targets precedence over a requested Diff Viewer; never mount two right panes or switch back to native three-column `NavigationSplitViewVisibility` control on macOS 26.
    - **A pull-request pane is scoped to the surface that opened it.** `RightPaneDestination.resolve` maps `targets.pullRequest` for `.thread`, `.project`, and `.pullRequests` selections. Scoping happens where `ContentView.rightPaneDestination` *builds* `RightPaneContextualTargets`: `scopedPullRequestPaneTarget` asks `PullRequestsViewModel.activePaneTarget(for:)` with the origin matching the current selection (`PullRequestPaneOrigin` mirrors `PullRequestLinkOwner` plus `.screen`), so a screen-opened pane cannot follow the user onto an unrelated thread or project. Keep `resolve` a pure function of its inputs — an origin check inside it makes the routing untestable. The helper also withholds the target while `AppSettings.pullRequestsEnabled` is off, and `ContentView` deactivates the pane when the setting flips false.
- Keep the Diff Viewer request root-scoped across project and thread selection changes (the lane's width is shared and root-scoped too). Repeated show requests are idempotent so navigation cannot replace the active pane presentation identity or replay its entrance animation.
    - Re-evaluate Diff Viewer routing when the root selection identity changes. Observe a mounted conversation's live working directory separately so a changed worktree on the same thread also switches targets without dereferencing a SwiftData selection token during body evaluation.
    - **Route from one composite keyed task.** `DiffViewerRoutingKey` (route selection + rendered scope + draft refresh revision) drives a single `.task(id:)`. Do not re-add routing to `onAppear`, selection/bookmark observers, or a right-pane destination observer; each puts a SwiftData resolve plus a Git switch on the click-to-highlight frame.
    - **Normalize Settings to its bookmark.** `DiffViewerRoutingSelection` maps `.settings` onto the preserved project/thread route so opening Settings from a project produces the same key and the task does not re-run.
    - **Yield before resolving.** `DiffViewerRouteRunner` suspends first, then guards the current key before resolving and again before clearing or switching. A superseded route applies nothing — in particular a stale no-target route must not clear a newer pane. `DiffWorkspaceStore`'s generation guards still own already-admitted Git work.
    - **Initialize watching separately.** `setWatchingEnabled(_:)` follows `isDiffViewerRendered` through its own observer; it is not part of routing.
- `AppSettings.lastActiveProjectPath` persistence runs through `LastActiveProjectRecorder`, not inline in the selection observer. Skills/MCP/Scheduled/Settings selections take no sequence number, and a job consumes its sequence only when it writes, so a Task selection cannot discard a pending project write and a stale job cannot overwrite a newer one.
- Commit-message generation ownership is fetch-free and exactly-once. `AppState.CommitMessageGenerationRequest` carries both `threadID` and the explicit `conversationID` (stored into `selectedConversationIDs` when requested) so selection and conversation-map changes validate synchronously. Every success, failure, replacement, and cancellation goes through `completeCommitMessageGenerationRequest(id:result:)`; a stale conversation task is a no-op and can never resume a continuation twice.
- Keep the native titlebar separator disabled; `AppSeparatorHairline` surfaces render the same explicit one-physical-pixel tint.
    - **Keep the root divider unconditional.** The root toolbar hairline stays visible for every selection; a mounted multi-conversation tab strip also draws its own bottom `.paneHeader` hairline, producing two separators around the strip.
- **Clamp right-pane width to rendered space.** `RightPaneWidthPolicy` reserves main-pane width plus its resize handle; the lane persists one `AppSettings.rightPaneWidth` for every destination, only on resize completion. `RightPaneDestination.feature` names which feature session a command deactivates — it is not a width key, and the lane must not resize when the destination changes.
- **Restore focus only when the lane closes.** Root dismissal completion decides whether the captured contextual pane may restore its invoking control; a Diff Viewer or contextual replacement keeps focus ownership.

### Diff Viewer Toolbar Button

- The button owns the visible changed-diff summary:
    - **Keep stats in the button.** Green `+N` / red `-N` stay inside the button — transcript or composer chrome for changed files alters composer height, which can invalidate lazy transcript row hit testing and leave stale bottom space.
    - **Drive width from the status slot.** Animate the trailing status slot and stat-label widths directly; the toolbar group derives its width from that child rather than running a separate parent-width animation.
    - **Clip stats during reveal.** Animate the slot's real width and clip to it before fading in stats text so it cannot render under neighboring buttons.
    - **Match toolbar icon styling.** Render the leading glyph through `Label(...).labelStyle(.iconOnly)` so it inherits the shared icon treatment. It is a vendored Primer Octicon (`OcticonImage`) on an explicit `PrimaryToolbarMetrics.octiconSize` frame — fixed artwork, not font-sized — so its color must come from the button style, never a local `foregroundStyle` that would freeze it through hover and disabled states.
        - **The pull-request button's status glyph is the one exception.** With exactly one linked pull request it renders that status's octicon in that status's tint through `PullRequestStatusGlyph` — an explicit `foregroundStyle` the button style no longer modulates. The status *is* the information (a neutral glyph cannot say merged versus closed), and the hover selector circle still renders. Do not generalize to other toolbar glyphs.
            - **Draft is the one status whose artwork the toolbar does not use.** Primer's dashed draft glyph reads as a gap beside the solid glyphs, so the toolbar substitutes the plain `PullRequestOcticon16` shape with the `.secondary` tint — unique among the statuses and clearly lighter than the unlinked state, so color alone still says draft. `PullRequestRow` keeps the dashed artwork, where it has room and a text label.
    - **Keep pane modes independent.** The pane may switch between current changes and commits; the button's stats, loading, and visibility summarize working-tree changes only.
    - **Keep stats alive while the pane is hidden.** Hidden-pane selection changes still switch the diff view model with `scope: .toolbarStatsOnly`; do not clear the view model on hide. Full pane payloads load when the pane shows.
    - **Use the resolved route for lifecycle.** Only a rendered `.diff` route enables filesystem watching or `.full` loads; the raw request may be masked by a contextual pane and must not drive labels, animation, or heavy loading.
      - Async child flows call a root-lived scope resolver immediately before switching diff targets; a render-time visibility Bool can go stale across suspensions.

### Primary Toolbar Group

- The top-right toolbar is one custom SwiftUI `ToolbarItem` for project actions, terminal, diff viewer, pull requests, and settings, left to right:
    - **Hide shared toolbar chrome.** Keep `.sharedBackgroundVisibility(.hidden)` so AppKit does not draw one large hover pill around the group.
    - **Own the container background.** `PrimaryToolbarButtonGroup` draws the theme-aware capsule fill and border itself, after the container inset.
    - **Preserve the inset.** `8` points horizontal, `4` vertical around the capsule. `PrimaryToolbarMetrics.buttonSpacing` (`4`) is no longer a spacing the row uses — it is the nominal same-width-glyph gap the optical values derive from, and it still spaces the main-pane header.
    - **Space every boundary optically, not uniformly.** A gap is read glyph edge to glyph edge, so with every box at `iconButtonSize` the visible gap is `iconButtonSize + spacing - (inkA + inkB) / 2`. Glyph ink varies widely at this size (measured in the rendered 18pt glyph box: `terminal` `18.5`, `gearshape` `17.0`, `FileDiffOcticon` `16.0`, `PullRequestOcticon16` `15.0`, `safari` `16.0`, `hammer` `20.0`), so a uniform gap looks uneven. `PrimaryToolbarOpticalSpacing` holds the per-boundary values that even the row to ~`15`; `octiconSize` is `18` rather than `16` so those values stay non-negative. Boxes, hover selectors, and hit targets all stay at `iconButtonSize` — never shrink a box or overlap spacing to buy room.
        - **Re-derive from ink columns, not a screen ruler.** Measure the recorded `primary_toolbar_button_group_*` baselines by thresholding pixel columns; a screen tool drops the pull-request glyph's small trailing circle and over-reports that gap by ~`2.5` points. Changing a toolbar glyph, `octiconSize`, or `iconFont` means redoing this.
        - **Project actions derive their spacing at runtime** — their glyphs are unknown until a project loads, and SF Symbols vary by ~`4` points of ink at this size. `PrimaryToolbarGlyphInk` measures the rendered mark and `PrimaryToolbarGroupWidth` spaces each boundary from it, holding every gap at ~`15`.
            - **Measure through `ImageRenderer`, never `NSImage(systemSymbolName:)`.** The latter over-reports thin round strokes (`safari` `18.0` against the `16.0` SwiftUI draws) — and that `2` point error is the whole size of the defect. `ImageRenderer` renders the view SwiftUI ships and matches the baselines within `0.25` points, asserted by `ContentViewProjectActionsTests+ToolbarMetrics`.
            - **Keep rendered padding and reserved width in step.** `PrimaryToolbarProjectActionsSlot` pads each button and `PrimaryToolbarGroupWidth.projectActionsSlotWidth` reserves the total; both walk the same symbol list.
    - **Anchor the trailing edge.** Reserve the target group width immediately and trailing-align the animated capsule inside it so the right edge never moves.
    - **Reveal project actions through the leading slot** (`PrimaryToolbarProjectActionsSlot`, shared metrics); raw conditional siblings fight the diff status width animation.
    - **Give every conditional button its own animated slot.** `coreToolbarButtonCount` covers only the three always-mounted buttons (terminal, diff viewer, settings). A button that comes and goes — currently pull requests, gated on a selected thread/project plus `AppSettings.pullRequestsEnabled` — rides a slot like `PrimaryToolbarPullRequestSlot`, a width term in `PrimaryToolbarGroupWidth.groupWidth` animated on `PrimaryToolbarMetrics.statusAnimation`; bumping the fixed count would reserve width for an absent button and shift the trailing edge. Because the row spaces per boundary, the slot carries its own leading spacing *inside* the animated frame and reserves it in that width term, so collapsing takes the spacing with it.
    - **Keep loaded actions rendered across thread switches.** While `refreshToolbarProjectActions()` resolves a newly selected thread, previously loaded actions stay visible and keep targeting `projectActionsThreadID` (the thread they loaded for) so same-project switches do not collapse and re-expand the slot. Do not re-bind in-flight action buttons to the newly selected thread.
    - **Share icon and progress sizing** through the shared primary-toolbar button style and progress slot; keep icon font sizing separate from diff status text sizing, and keep selector circles anchored to the leading icon footprint even when a label grows (the diff stats button).
    - **Coordinate animation timing.** Curves stay centralized in `PrimaryToolbarMetrics` so diff text, diff width, terminal status, hover, and press feedback do not drift.
    - **Prefer failed project-action completion.** The terminal toolbar completion icon shows failed while any failed project-action terminal tab remains open, even if the latest batch succeeded. Shell exits stay visible in their tabs but never drive the toolbar completion state.

### Window Title And Header

- The visible main-pane title is a custom leading `.navigation` toolbar item. Keep the scene's `Window("Alveary", id: "main")` title intact, remove only the default visual title, and derive the visible title from `AppState.selectedSidebarItem`.
    - **Keep the app-owned items split.** Preserve the stable header/action toolbar IDs and the flexible spacer between them; `AppWindowToolbarConfigurator` corrects `NavigationSplitView` placing that spacer before its system items.
    - **Keep the toolbar uncustomizable.** App-owned items draw their own chrome, so the system customization menu breaks the layout. The configurator clears `allowsUserCustomization` and `allowsDisplayModeCustomization` (emptying the menu so AppKit stops showing it) and forces `displayMode` back to `.iconOnly` so a previously customized toolbar does not stay label-showing. Keep both policies on that one toolbar observer.
    - **Match transcript edges without changing height.** Complete the system edge inset with horizontal-only padding so app-owned content lands on `transcriptScrollLeadingInset` / `transcriptScrollTrailingInset`; no vertical padding or height frame on the header.
    - **Keep title typography native-sized.** Plain destinations and Project names render semibold `.title3`; thread names render through `AppMarkdownInlineLabel` at the same style and weight.
    - **Keep conversation creation thread-scoped.** The title-adjacent `+` uses the mounted `ThreadDetailView`'s focused-scene `newConversationAction`, stays hidden before initial setup, and remains visible-but-disabled while creation is blocked.

### Launch, Restore, And Cleanup

- Launch-time "re-open last thread and conversation" restore is exact-match and best-effort: restore only when both persisted `lastOpenThreadID` and `lastOpenConversationID` resolve to the same live, unarchived pair; otherwise clear the saved IDs and fall back to the empty selection state.
- Delete stale draft threads and their attachment directories at launch, before selection restoration or activity backfill. A mounted draft must not overwrite the last-open real thread; materialization persists its thread and main-conversation IDs after the first durable save.
- App-hosted unit tests run the real `AppDI.component` and lifecycle against `AppRuntimeProfile.current`'s isolated Application Support root and defaults suite. Keep app-owned writable service paths derived from `AppStorageProfile`, suppress only automatic/restored app-owned windows, and do not make the hosted lifecycle inert or point it at production storage.
- Stale Task-draft cleanup snapshots its workspace descriptor before the database commit and removes only marker-verified Alveary-owned roots after it; granted folders are never cleanup targets.
- Private-workspace orphan cleanup retains valid prepared markers from nonterminal scheduled runs and terminal runs still linked to a Task, even when recovery withholds the Task's workspace descriptor.

### Render-Time SwiftData Discipline

- Treat `AppState.selectedSidebarItem` thread references as selection tokens, not proof the backing SwiftData row is readable. Re-resolve with `ModelContext.resolveThread(id:)` and fetch live conversations before reading thread relationships for toolbar actions, notification routing, diff actions, or launch-selection persistence.
- Do not gate render-time UI state in `ContentView` body on fetch-backed resolution. Plain `ModelContext.fetch` reads are not observation-tracked, so a body-computed boolean derived from them latches until an unrelated tracked mutation re-renders. Gate on observation-tracked state and defer fetch-backed resolution to the action handlers.
- Diff Viewer action buttons use observation-tracked gates: `Commit` enables for selected threads or projects, and the pane footer's Create PR / View PR gates read `selectedPullRequestLinks` (model relationship reads) plus `canCommitDiffChanges`. No project/thread fetches in the render-time gate; handlers re-resolve backing rows.

### Transcript Card Routing

- **A transcript's thread card selects its thread through `.threadOpenRequested`.** `ChatTranscriptView` owns neither the sidebar selection nor the model context that says whether the thread is still live, so the card posts its main-conversation id and `handleThreadOpenRequest` routes. Selection is app-wide, so unlike the pull-request pane the request carries no originating thread. An archived thread has no sidebar row to select and lands on `.archived`, which is why the root resolves the thread rather than calling `openConversation(with:)` blind — that helper silently ignores archived and draft threads.

### Pull-Request Flows

- **The Git changes footer's pull-request panes get a back stack; nothing else does.** `openLinkedPullRequest(_:preservingDiffViewer: true)` skips `appState.hideDiffViewer()`, so the pane opens over the still-active Diff Viewer request (contextual targets only *mask* it) and its X resolves `.diff` again — the footer's View PR and the post-create open in `ContentView+CreatePullRequest.swift` are the only `true` callers. Every other opener clears the request, so closing a toolbar- or screen-opened pane does not surface a Diff Viewer the user never asked back for.
- **A transcript's link card opens its pull request through `.pullRequestPaneRequested`.** `ChatTranscriptView` reaches neither the browsing view model nor the Diff Viewer request, so the card posts and `handlePullRequestPaneRequest` routes, refusing a request whose thread is no longer the selection because the pane is origin-scoped. A still-linked pull request takes `openLinkedPullRequest` (which also refreshes the stored snapshot); an unlink card names one that is deliberately not linked, so it falls to the identifier overload, which opens the pane on the click's own cycle with no summary and lets the pane load its own detail. Keep it that way: pre-fetching a summary to open with cost a second identical `fetchDetail`, made the card carry a spinner for the wait, and turned a failure into a toast with no pane instead of the pane's own banner.
- **Create PR links automatically and reuses the commit target resolution.** `presentCreatePullRequestModal()` builds its context from `activeDiffCommitTargetSnapshot()` plus `selectedPullRequestLinkOwner`; on success `handleCreatedPullRequest` links via `PullRequestLinksViewModel.link(_:owner:)` *before* opening the pane (so the footer already reads View PR), opens only when the selection still matches the originating owner, and surfaces a failed link fetch as an app-level error because the pull request already exists on GitHub. The sheet is the root's third `.sheet`, hosted by the lifted `createPullRequestSheetHost` (type-check budget).

### First Appear And Root Modals

- On first appear, sync the dock badge with `notificationManager.refreshBadgeCount()`; do not also call `handleAppVisibilityChanged()` — mark-read of the restored conversation is driven by `ThreadDetailView`'s selection task (see `Alveary/Views/Chat/AGENTS.md`), and the extra call duplicates it plus an extra chained badge task.
- Root modal priority: onboarding, then image preview. Scheduling proposals are **not** modal — they are confirmed in their own transcript widget, which is why `ScheduledTaskProposalQueueCoordinator` reaches the chat surface through the environment rather than the root. Do not reintroduce a root proposal modal.

## Command Dispatch

`handlePendingCommand(_:)` in `ContentView+Commands.swift` wraps every `AppState.CommandRequest` branch in one `Task { @MainActor in … }` with a shared `defer` that clears `appState.pendingCommand` only if its id still matches the captured `commandID`. Do not clear `pendingCommand` inline inside a branch — even for synchronous work — or stale-id semantics diverge and racing commands can nil out a newer one. New `CommandRequest` cases delegate async work to a helper that takes the captured `commandID` and re-checks it after each `await` before mutating `appState.selectedSidebarItem` or surfacing errors.

- A voice-model preparation modal can appear while an app command is suspended. Re-check `isModelPreparationModalPresented` after every `await` before changing selection or presenting another modal; the blocking overlay stays mounted until its own Cancel or Continue closes it.

## Keyboard Shortcuts

App-wide modifier-key shortcuts live in `KeyboardShortcut+Alveary.swift` as static extensions on `KeyboardShortcut`. The **Focus And Keyboard Coordination** section in `Alveary/Views/AGENTS.md` owns the placement rule (menu registration beats toolbar-button registration); this section covers how to define and reference a shortcut so the binding and its tooltip cannot drift.

- App-shot capture is the exception to menu-owned shortcuts because it must work while Alveary is backgrounded. Keep its global registration in the app-shot coordinator: system hot-key registration for regular key chords, event taps only for legacy modifier-only shortcuts, and missing permissions routed through `AppShotPermissionRequester`/`AppShotPermissionDragGrantAssistant`, not composer banners. The default stays a regular key chord, currently `⌃⇧S`, because `⌘⌘` conflicts with Codex's trigger; regular chords need no Input Monitoring, the modifier-only `⌘⌘` path does.
    - The global shortcut is not the only capture source: the composer `+` menu's "Attach <app>" row calls `AppShotCoordinator.requestCapture()`. Every source funnels through `triggerID`, so `ContentView` stays the sole trigger observer and destination router; new affordances raise that trigger rather than calling the capture controller.
    - `AppShotTargetTracker` publishes the pre-capture candidate as `attachableApp`, gated on `appShotsEnabled`, republishing only when the app identity changes — app activation fires on every switch, and an unguarded assignment re-renders every observer. Icons come from `NSRunningApplication.icon`, never a LaunchServices lookup on a user-interaction path.
- `ContentView` is the sole app-shot trigger observer and destination router. Resolve and revalidate a persistent-ID destination before storage, let project/no-thread routes create or reuse the provisional draft only after capture preparation succeeds, and never redirect a capture once storage begins — if selection changes mid-storage, finish staging into the claimed conversation without navigating back.
- App-shot failures before storage use app-level feedback; storage and staging failures use the selected conversation's `lastTurnError` only while it is mounted, else stay app-level so they cannot hide in an unmounted runtime state.
- **Define each shortcut once as a `static let` on `KeyboardShortcut`** (`static let toggleDiffViewer = KeyboardShortcut("d", modifiers: [.shift, .command])`). Reference the constant from the `CommandGroup(...)` menu entry and the matching toolbar button's tooltip — no hand-written `KeyEquivalent` + `EventModifiers` literals — so rebinding touches one line.
- **Register the shortcut on a menu entry in `AlvearyApp.commands`, not the toolbar button.** The button's `.help(...)` tooltip only renders the binding; also attaching `.keyboardShortcut(...)` gives the shortcut two owners.
- **Build tooltips with `KeyboardShortcut.displayString`** — `"\(label) (\(KeyboardShortcut.toggleDiffViewer.displayString))"` renders `"Hide Diff Viewer (⇧⌘D)"` — so the displayed literal derives from the active binding (special keys via `KeyEquivalent.displaySymbol`).
- **Route menu shortcuts through `FocusedValues+Alveary.swift` when the action depends on view-local state.** Two qualifying cases:
    - **Context-scoped shortcut** — applies only while a specific view is mounted (⌘T "New Conversation" needs a `ThreadDetailView`); `.disabled(action == nil)` greys the item out otherwise.
    - **App-wide shortcut whose action reads view-local state** — always enabled, but the closure captures `@State` the scene menu cannot reach (⇧⌘T "Show/Hide Terminal" must set up a shell session before flipping `appState.isTerminalPaneVisible`, and `terminalManager` is `ContentView`'s `@State`). Calling the `AppState` mutator directly skips the pre-flip setup; an `.onChange` observer runs it after the pane re-renders.
    - **How to apply**, in order:
        1. Add a `FocusedValueKey` whose `Value` is the action closure (`@MainActor () -> Void`).
        2. Publish it via `.focusedSceneValue(\.<name>, { ... })` from the owning view.
        3. Wrap the `Button` inside `AlvearyApp.commands` in a small private `View` struct reading `@FocusedValue`.
        4. If the title tracks a mutable flag ("Hide Terminal" vs "Show Terminal"), give the struct a plain `var appState: AppState` — not `@Bindable`; see the field comment on `ToggleTerminalPaneCommandButton`.
        5. Keep the focused value a closure; do not carry label state through it.
        6. Do not inspect `appState.selectedSidebarItem` at the menu layer or duplicate the view's private logic (`ThreadDetailView.createConversation()`, `ContentView.toggleTerminalPane()`).
- **A focused value read inside the window tree must be `Equatable` with stable identity — never a bare closure.** Bare closures are fine when only scene menu commands read them, but the moment an ancestor of the publisher reads one (`ContentView` reads `newConversationAction` for the toolbar `+`), every publisher body evaluation produces a "changed" value, invalidating the reader, re-rendering the publisher, republishing — a frame-rate render loop across the whole window. Wrap the closure in a struct whose `==` compares a stable identity and excludes the closure, like `NewConversationAction` (thread identity) and `DiffViewerCommand` (title); give it `callAsFunction` so call sites stay `action?()`.
