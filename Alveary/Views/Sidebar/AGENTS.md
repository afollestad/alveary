## Sidebar Interaction Patterns

These instructions cover sidebar-specific view code under `Alveary/Views/Sidebar/`.

> **READ FIRST:** Focus and keyboard rules are centralized in **Focus And Keyboard Coordination** in `Alveary/Views/AGENTS.md`. The sidebar bullets below stack on top of that parent contract — they are not a replacement for it.

## Rows

- `SidebarProjectRow`'s leading icon `Button` is load-bearing for click-to-expand:
    - **Action:** toggles expansion, never project activation. `onToggleExpanded` stays the sole action; activation lives on the sibling content affordance plus the row's transparent background tap target, so dead space inside selected-row chrome still opens the project.
    - **Stationary animated toggle:** keep the explicit expansion animation for child reflow and caret rotation, and keep drag-geometry modifiers structurally stable across expansion — conditional geometry changes only its emitted preference value, because adding or removing the modifier makes SwiftUI `List` transition the header itself.
    - **Fixed icon:** always render the folder glyph; never swap it for a disclosure chevron.
    - **Inline disclosure:** `SidebarDisclosureCaret` after the title, shared with `SidebarSectionHeaderRow`; its fixed slot stays reserved while hidden so visibility never shifts truncation. The project row passes no `SidebarDisclosureCaretToggle` — the caret is a state indicator here, never hit-testable, so every click in the title cluster reaches `onActivate` and expansion stays with the folder button and the keyboard. Do not give it a tap gesture again.
    - **Collapsed keeps its caret:** a collapsed row shows the caret unconditionally — it is the only sign the row hides content, and drag suppression does not reach it because every toggle path is drag-guarded. Hover, the flash, and drag suppression govern the expanded state alone.
    - **Flash on unattended toggle:** an expansion change with the pointer away shows the caret briefly, then fades it, so keyboard and programmatic toggles are not silent; hover-driven toggles already show it, and drag suppression outranks the flash.
    - **Hit region:** keep the fixed 16×16 frame with `.contentShape(Rectangle())` — a `.plain` `Button` otherwise hit-tests the SF Symbol's intrinsic outline, and edge clicks miss.
    - **Accessibility:** explicit `.accessibilityLabel` (`Expand <project>` / `Collapse <project>`); VoiceOver otherwise reads the raw symbol name.
- `SidebarSectionHeaderRow` collapses its whole section when given a `SidebarSectionHeaderDisclosure`:
    - **Two sections, in memory.** `Projects` and `Tasks` collapse; `Pinned` passes no disclosure and stays inert. `SidebarView.collapsedSections` is session-scoped `@State` like `expandedProjects`, seeded for fixtures through `initialCollapsedSections`. Collapse both list layouts — the sticky `Section` header when `Pinned` is empty, the inline row when it is not — and never let a collapsed `Projects` hide the `Tasks` header.
    - **The whole row is the target.** Title, the gap after it, the caret, and the dead space all toggle — deliberately unlike a project row, where only the folder toggles and everything else activates the project, because a section header has nothing to activate. This is the one caret that takes clicks. The tap is the title row's own `contentShape`, never a backing rectangle — `Text` hit-tests its own frame, so a background layer never sees a click on the title — and it stops at the title row so a click in the section gap above it does nothing. The caret and the trailing action button are children and keep their own clicks; the `+` button must never toggle.
    - **Reveal explicitly.** Every path that means "show me what is inside" goes through `revealProject`, which reopens `Projects` unless the project is pinned; `syncExpansionWithSelection` reopens the section a routed selection landed in through `sidebarSectionToExpand`, and the drop finalizer reopens the section a drop landed in. Unlike `sidebarProjectPathToExpand`, selecting a project row *does* reopen its section — traversal can rest on a collapsed row but never inside a collapsed section.
    - **Accessibility:** the title carries `.isHeader` plus `.isButton` and a dynamic `Collapse <title>` / `Expand <title>` label; the caret owns the tooltip.
- `SidebarProjectRow`'s trailing new-thread button: hidden and non-hit-testable until row hover (even while selected); only pointer hover over the button itself shows the circular background; keep its center aligned with `SidebarSectionHeaderRow`'s add-project button; hide the hover-only icon from accessibility and keep `New Thread` as a named custom action on the always-present activation element.
- Project rows are single-line — do not reintroduce branch/path/local subtitles — and share `SidebarRowMetrics.topLevelAndThreadContentHeight` with thread rows; no extra vertical padding.
- Anything row-mounted that lines up with a `List` section header's leading edge adds `SidebarProjectListMetrics.plainRowLeadingCorrection`: the `Pinned`/`Projects`/`Tasks` headers, their placeholders, and the top-level rows' icon column. Do not retune one of them alone.
- Provisional draft threads never render as rows, counts, or pinned items. While a draft is mounted, its project row is the effective selection for highlighting and keyboard navigation; every New Thread entry point reuses that draft and may reassign its project in place.
- Async sidebar actions must re-check the voice-model modal after suspension before selecting, restoring, or falling back; work started before the blocking modal appeared must not navigate underneath it.

### Rename And Cleanup

- Thread rename is inline (Finder-style `TextField` swap in `SidebarThreadRow`), tracked by an `editingThreadID` binding.
- The "Rename..." context-menu entry and VoiceOver rotor action are gated on `editingThreadID == nil`, matching the keyboard path in `renameThreadID(for:editingThreadID:)` — swapping the editing target mid-edit left the target row stuck without an input field because the TextField unmount/mount within one SwiftUI update pass did not converge. Users finish the in-flight rename (Enter / Escape / click away) first.
- Threads attached to a scheduled definition or active run keep Unpin, Archive, and Delete visible but disabled, explained with the shared settings-style hover tooltip; hovering the cleanup target directly replaces the glyph with `nosign`.
- `SidebarThreadRow` renders on a single line; do not reintroduce a branch or worktree subtitle.
- `SidebarThreadRow` status indicator layout:
    - Keep the trailing status slot size-locked and center-aligned with the project/header action buttons, the row framed to `maxWidth: .infinity`, and the invisible leading slot so thread titles align with project names.
    - `.busy` uses a spinner in the same fixed frame as the colored dot (`8×8` today) so status changes cannot change row height or nudge the label.
    - Task threads created by a scheduled run show the scheduled glyph before the worktree glyph and status/cleanup control, matching the worktree glyph's size, color, and hover-help styling, with a `Scheduled task` accessibility label.
    - Threads with `useWorktree` show a rotated branch glyph before the status/cleanup frame with a 6pt explicit gap; its hover tooltip shows the worktree path, or `Worktree path not created yet`.
    - Keep the title gap, glyphs, and status/cleanup frame in a fixed-width trailing cluster so long names ellipsize before the glyphs shift.
- `SidebarThreadRow` cleanup action overlays the status dot:
    - Show the archive/delete button only while the row is hovered or confirmation is armed; only pointer hover over the button itself shows the circular background — separate from selected-row and row-hover backgrounds.
    - The red `Confirm` pill is icon-height, expands left from the status column, and the whole rounded pill is the hit target; a timeout after hover leaves collapses the width without a fade.
    - **Never co-render the glyph and `Confirm`.** `sidebarThreadCleanupButtonVisibility` is the single source for which one renders and hides the glyph for the whole collapse. The `onHover` re-entry branch must clear `isCleanupControlCollapsing` (not only `isCleanupControlCollapsingToHidden`), or re-entry shows an empty hover circle for up to 180ms. Both `cleanupButtonContent` branches carry `.transition(.identity)` because the sibling width `withAnimation` in the same update pass governs the `ZStack` child's removal — `withTransaction(disablesAnimations:)` on the chrome flag alone left `Confirm` painted under the glyph for the full 0.18s.
    - **Dismiss instantly on confirm:** `clearCleanupConfirmation(forCommit: true)` drops the pill with no animation, because `onConfirmCleanup` removes the row and an animated collapse lags behind the `List` pulling the row out. The width-reset `Task` still runs so a failed archive/delete restores the hover glyph; the timeout path keeps its animation. The state machine lives in `SidebarView+ThreadRowCleanupConfirmation.swift`, which is why the `@State` it drives is internal on `SidebarThreadRow`.
    - Pause the confirmation timeout while the pointer is over the pill or pressed on it; resume when the press ends outside with hover gone.
    - Keep the 8pt title gap identical with and without the cleanup icon so hover does not change truncation.
- Thread names render via the shared `AppMarkdownInlineLabel`, which keeps plain rows and rows with inline-code or `@mention` chips at a uniform height (`testSidebarThreadRowChipAndPlainShareHeight`; mention chips snapshot-locked by `testSidebarThreadRowMentionTitleRendersChip`).
- Chip colors always use the `.standard` palette — uniform fill across selection transitions is the product decision. Do not reintroduce selection-aware chip swapping here by reaching past the label into `AppMarkdownInlineCodeChip(style: ...)`.
- Deleting the selected thread keeps focus within the project: previous visible thread, else next, else the project row.

## Pinned

- Pinned items render as a shared top-level group under `Scheduled` and above `Projects`:
    - Render the `Pinned` header when pinned projects or standalone pinned threads exist, matched with the `Projects` header styling and insets.
    - Thread pinning changes only sidebar placement; `AgentThread.project` still owns cleanup, diff actions, project deletion, and restore behavior.
    - Pinning a project clears pins on its unarchived children, which render only inside the pinned project's expandable list via `SidebarViewModel.activeThreads(for:)`. Standalone pinned threads must not render separately when their parent project is pinned, and nested child context menus omit `Pin`/`Unpin`.
    - Pinned projects and standalone pinned threads share the dense `pinnedSortOrder` namespace; activity, name, and stable ID are deterministic legacy/backfill fallbacks only — later activity must not move a top-level pinned item.
    - Standalone pinned thread rows have no leading icon or reserved spacer; their title starts at the top-level row inset. Pinned project rows use the normal project row layout.
    - A Task placed in a Project renders as one of its children but stays a Task: its own workspace keeps driving working directory, cleanup, and diff routing, and placement follows Project-mode child rules. **Placing a Task in a Project clears its pin** — `moveTaskIntoProject` always resets `isPinned`/`pinnedSortOrder`, because a leftover pin renders the Task in two places and makes the drop look like a no-op. Pinning afterwards promotes it back out.

## Drag & Drop

- Sidebar drag reordering treats project rows and their expanded children as atomic groups:
    - **Limit sources.** Project title/dead space, standalone pinned Project-thread and Task titles, unpinned Task rows in the Tasks section, and nested child rows are the drag sources; folder, New Thread, rename, worktree/status, and cleanup controls keep their existing actions. A nested Task row drags as `.unpinnedTask`; a nested Project-mode row drags as `.projectThread`, whose only destination is `Pinned` — a project's child list has no manual order. Children of pinned projects are not sources (the pinned parent absorbs child pins; `projectChildDragConfiguration` withholds the source, `resolveUnpinnedProjectThreadForOrdering` and the commit validity check are backstops).
    - **Expose outer boundaries only.** A project target exists only at its real header or real terminal row; middle child rows never publish target geometry, and header/terminal geometry stay distinct so virtualization cannot invent a midpoint. Top-level rows publish only `.topLevelTerminal`, from whichever row ends the visible group per `sidebarTopLevelRowItems(showsPullRequests:hasArchivedThreads:).last`, measured before trailing spacing.
    - **Choose the placed section-header frame, never the union.** A `List` section header publishes its geometry twice — the placed frame and an unplaced copy at the content origin that comes and goes, which made the drag appear to work and then stop. Every `.projectsHeader` read goes through `sidebarPlacedSectionHeaderFrame`, which takes the lowest frame (the real header can never sit at the content origin because `Skills`/`MCP`/`Scheduled` render above it). Only this role needs it — `Pinned` and `Tasks` head their sections with ordinary rows — but any new role backed by a `Section` header needs the same treatment.
    - **Center shared boundaries.** Measure project header content before its inter-project top spacing. When adjacent top-level items share a logical insertion boundary, keep source-valid semantic anchors but render them at one Y halfway between the two real visible outer edges, and extend each anchor's hit region to that midpoint so crossing the gap does not blink the line.
    - **Keep target semantics source-specific.** Projects may cross `Pinned`/`Projects` only through section edges or project-anchored boundaries; standalone pinned threads stay inside `Pinned` and may target any top-level pinned boundary. One visual line may carry different anchors for the two source types.
    - **Keep targeting local and stable.** Activate an outer boundary only from that boundary row, never from an expanded group's visible union. Coalesce transient `List` preference maps and use only a short, non-resetting geometry-miss grace so frame churn neither blinks the line nor preserves a vanished target.
    - **Reject inverted geometry.** If transient preferences place a boundary above its owning section start or logical predecessor, omit it and let the grace retain the previous valid line; a raw inverted candidate must never surface above `Pinned` or `Projects`.
    - **Trust logical section visibility.** Use `Pinned` header geometry only while the logical pinned order is nonempty; during animated last-item removal, stale header preferences can overlap the sticky `Projects` header, whose upper edge remains the sole hidden-pinned target.
    - **Give the hidden-pinned target real area.** With `Pinned` empty, `sidebarPinnedSectionEndCandidate` extends the hit region from the `Projects` header's upper half up to `.topLevelTerminal`'s midpoint and opts out of the indicator-proximity gate via `SidebarDropCandidate.ignoresIndicatorProximity`, because nothing else publishes there — otherwise the drop silently no-ops. **Widen only the hit region, never the line:** the indicator stays at the header's top edge, where `SidebarSectionHeaderRow` draws the `Projects` divider. Keep `sidebarPreviousDropBoundaryEndpoint` returning `nil` for empty `Pinned` so coalescing cannot move the line, and fall back to the header's upper half alone when `.topLevelTerminal` is missing or inverted. Once `Pinned` has items this is an ordinary section end with neither extension nor exemption.
    - **Let a collapsed section shrink its targets.** Collapsing unmounts the section's rows, so their `.projectHeader`/`.projectTerminal`/`.tasksTerminal` frames stop publishing and the per-project boundaries and `.into` reparent containers inside it disappear. The section's own start survives — `.projectsHeader` and `.tasksHeader` always publish — and the Tasks container falls back to its header row. Toggling is drag-guarded, so geometry cannot vanish mid-drag.
    - **Keep the root authoritative.** Sidebar-level drag state, the AppKit window-filtered event monitor, and autoscroll outlive virtualized source rows; row disappearance must not cancel a drag. Escape, mouse-up, source deletion, window loss, or root teardown own cancellation/finalization.
    - **Keep pointer spaces explicit.** SwiftUI only crosses the drag threshold. Translate monitor-local points by the measured viewport origin before comparing with named-space geometry, keep raw monitor-local points for autoscroll, and resolve the final monitor mouse-up point before freezing the candidate.
    - **Respect AppKit scroll bounds.** Constrain proposed autoscroll clip bounds with `NSClipView.constrainBoundsRect(_:)`; never derive a zero-based range from document and viewport heights — `List` content insets can give a short document a legitimate negative resting origin.
    - **Keep rows stationary.** Render the indicator in the list overlay and fade the active source group without mutating persisted order until mouse-up; preserve selection and expansion across moves and cancellation.
    - **Lines mean insertion; borders mean containers.** `SidebarDropCandidate.kind` picks the affordance: `.boundary` targets an ordered insertion point and renders the 2pt accent line (every `Projects` target and `Pinned` reorder target); `.container` accepts a drop anywhere inside its frame, renders a rounded accent border, skips the indicator-proximity gate, scores distance 0 while the pointer is inside, and is excluded from boundary coalescing. Draw both in the list overlay from named-space geometry; never attach a border to a row, because `listRowBackground` hoisting misaligns it. A container may stand in for a whole ordered section when the source is choosing membership rather than position.
    - **Scope pinned Task targets.** The distinct `.pinnedTask` source may reorder against any mixed Pinned item, never sees Projects targets, and additionally sees the Tasks-section target — a `.container` spanning `.tasksHeader` through `.tasksTerminal`, because Tasks is activity-sorted with no insertion positions; dropping there unpins. A Task placed in a project sees the same target (gated on `projectIDByTaskID`) and dropping removes it from the project, unpinning first when pinned, while keeping its workspace grants — revoking access could break in-flight work. Pinned sources are further gated on `SidebarDragLogicalOrder.unpinnableTaskIDs` so scheduled-attached Tasks never see it; `setThreadPinned`'s guard is the commit backstop.
    - **Grant Task folder access through `.into` targets.** Task sources see a `.container` over every project group in both sections, encoded as `SidebarDropPlacement.into`; its hit frame unions the project's header and terminal geometry, banded away from the group's outer edges and trimmed by the sticky `Projects` header's occlusion. Reserve the band only where a boundary actually competes for it: a Task source sees `Pinned` insertion boundaries only while `sidebarSourceCanHoldStandalonePin` holds, so that case reserves each boundary's own half-row (the regions `sidebarBoundaryHitFrame` gives them); everywhere else keep the flat `SidebarDropTargetingMetrics.containerEdgeBand`, and a collapsed group (one frame for both roles) falls back to it too. Dropping moves the Task into that project's child list and grants folder access; the Task stays a Task with its own workspace. `.into` never reaches the ordering commit — `sidebarOrder`, `sidebarInsertionIndex`, and `sidebarLogicalDropBoundary` reject it, `commitSidebarDrop` routes it to the owning-project unpin arm, and `finalizeSidebarDrag` routes access grants to `requestTaskProjectAccessDrop` for confirmation.
        - The confirmation dialog authorizes new folder access, so it is skipped when the Task can already reach the folder — that drop is pure placement, and dragging back out undoes it. When shown it quotes and bolds the Task name, bolds the project name, and states nothing is moved or deleted. Build the copy by interpolating `Text` values — not Markdown, which a name could inject, and not `AttributedString`, whose `inlinePresentationIntent` renders nothing while an explicit `font` attribute replaces the dialog's inherited size. Never name a section in the copy; a pinned Task sits under `Pinned`, not `Tasks`.
        - Ineligible Tasks still show the target and explain on drop rather than hiding it — except a Task's own project, never a reparent destination: for an unpinned Task it publishes nothing, for a pinned Task it carries the unpin drop instead. `sidebarTaskProjectAccessDrop` excludes own-project drops so the grant dialog can never claim an unpin.
    - **Drop a pinned thread onto its owning project to unpin it.** Pinned sources see exactly one `.into` group — their owning project — where dropping unpins in place, mirroring context-menu Unpin. Non-owning projects publish nothing to a `.pinnedThread`; a `.pinnedTask` keeps reparent containers on every other project and only its own flips to the unpin. Gating mirrors the `Tasks` container: `SidebarDragLogicalOrder.owningProjectIDByPinnedThreadID` (built in `makeRenderContext`, scheduled-attached threads withheld) scopes `.pinnedThread`, `unpinnableTaskIDs` gates a pinned Task's own project, and `setThreadPinned`'s attachment guard backstops the commit. The drop rides the synchronous commit — `commitSidebarDrop`'s `.into` arm calls `commitSidebarDropToOwningProject`, which re-validates ownership and leaves `AgentThread.project` untouched — and the finalizer expands the owning project so a collapsed group does not swallow the landed row.
    - **Drag unpinned Tasks and nested Project-mode threads only into Pinned.** `.unpinnedTask` and `.projectThread` may target only `Pinned`. Arriving from outside is a membership choice, so while `Pinned` is visible the whole section is a single `.container` targeting `.end` (built through the shared `sidebarSectionContainerFrame`) and the drop appends. `sidebarPinnedSectionIsContainerTarget` decides this for both sources, and every publisher of a `Pinned` boundary must suppress it when that holds. The container takes priority `3` so a nested `.into` group (priority `2`) still wins its own drop; without the tie-break a pinned project could never accept a reparent. While `Pinned` is empty the hidden-pinned boundary above the `Projects` header stands in. Sources already inside `Pinned` keep their insertion boundaries. `.projectThread` additionally sees no `Tasks` container and no `.into` project targets (it already lives in its project). Neither source is ever a drop target or geometry publisher, and both stay in the mid-drag cancellation set — `.unpinnedTask` from `activeTaskThreads` plus `projectIDByTaskID`, `.projectThread` from each ordered project's Project-mode children.

## Tasks

- The Tasks section renders below Projects:
    - **Route New task to Task composition.** Its header action starts the native Task-mode composer flow, never Scheduled.
    - **Keep empty semantics exact.** An empty Tasks body carries a secondary placeholder from `sidebarTasksPlaceholderLabel`: `No tasks` when none exist anywhere, `No tasks here` when every Task is pinned or placed in a project. Either placeholder publishes `.tasksTerminal` so the drop container keeps covering the label region.
    - **Route removal fallback by placement.** Removing a selected projectless Task prefers the next visible Task, then the previous; if none remains, request a blank Task composer with no selected sidebar row. A Task placed in a project uses the project-child fallback instead — previous sibling, next sibling, then the project row.

## Keyboard And Top-Level Rows

- The top-level rows (`Skills`, `MCP`, `Scheduled`, `Pull Requests`, `Archived`) are one group with variable membership. **`sidebarTopLevelRowItems(showsPullRequests:hasArchivedThreads:)` in `SidebarView+Selection.swift` is the single ordered source of truth** — adding, removing, or hiding a row means changing that function, never re-deriving the group's shape per row.
    - **Gate visibility on render-context flags.** `Pull Requests` follows `SidebarRenderContext.showsPullRequests` (from `AppSettings.pullRequestsEnabled`), `Archived` follows `hasArchivedThreads`; both are computed once in `makeRenderContext()`. Row builders must not read the settings service or run a fetch.
    - **Derive trailing spacing and `.topLevelTerminal` from the list's last element, computed once per body.** The terminal row takes `0` spacing and publishes the drag role; every other row takes `topLevelRowSpacing`. Do not add a second "is this the last row" predicate or gate on one row's own condition — the previous pairwise rule left `Scheduled` carrying trailing spacing and publishing no drag role once both conditional rows hid together, which silently no-ops the empty-`Pinned` drop.
    - **Keep the geometry modifier applied and flip only its value.** Every top-level row calls `.sidebarDragGeometry(.topLevelTerminal, isEnabled:)` unconditionally; applying/removing the modifier makes `List` transition the row and can leave a stale frame published mid-drag.
    - **Traverse from the same list.** `buildNavigableItems(...hasArchivedThreads:showsPullRequests:)` seeds its prefix from `sidebarTopLevelRowItems`, and both arrow-direction predicates treat every top-level row alike; a hidden row is simply absent.
    - **Clear a selection the hidden row would strand.** A row hideable while selected must drop both `appState.selectedSidebarItem` and the Settings `previousSelection` bookmark — `handlePullRequestsVisibilityChange(showsPullRequests:)` plus `sidebarSelectionAllowingHiddenPullRequests(_:showsPullRequests:)` in `MiddlePane.swift` — or dismissing Settings restores a screen with no sidebar row to leave it by.
- The `Archived` row sits under `Pull Requests`, conditional on content: `SidebarView` owns a `fetchLimit: 1` existence probe reaching render code and traversal as `SidebarRenderContext.hasArchivedThreads`. Do not fetch the archived rows here — `ArchivedThreadsViewModel` owns the real fetch.
- Horizontal arrows deliberately reuse the vertical traversal path for non-project rows; left collapses an expanded project row and right expands a collapsed one before either moves. The traversal lives in `buildNavigableItems()` / `navigateVertically()` in `SidebarView+KeyboardNavigation.swift`.
- Changing the selection must not expand a project — `sidebarProjectPathToExpand` returns nil for `.project`, or traversal could never rest on a collapsed row and every left-arrow collapse would be undone by returning to it. Reveal explicitly instead, as row activation, draft flows, pin/unpin, and the drop finalizer do.
- `buildNavigableItems` drops a collapsed section's rows and their children entirely; `Pinned` always traverses. Section headers are not navigable items, so a selection stranded inside a collapsed section behaves like one under a collapsed project — the next ↓ restarts from the top.
- When adding top-level sections or changing visibility/expansion behavior, update `sidebarTopLevelRowItems`, the keyboard-navigation functions, and their tests together.

## Render Snapshot

- Sidebar rendering is snapshot-driven, not fetch-driven:
    - **Build one snapshot per body.** `SidebarView.body` calls `makeRenderContext()` exactly once, grouping the `@Query`-backed projects and unarchived threads into a `SidebarRenderSnapshot` keyed by persistent ID, paired with the thread-order animation and drag logical order in a `SidebarRenderContext`.
    - **Route every render read through the context.** Sections, project children, placeholders, expanded counts, keyboard traversal, and drag-start ordering all take `SidebarRenderContext`. Do not call `SidebarViewModel.activeThreads(for:)`, `pinnedItems(projects:)`, `fetchedPinnedItems()`, or `activeTaskThreads()` from render code — each is a `FetchDescriptor` on the click-to-highlight frame.
    - **Keep authoritative fetches for post-mutation fallbacks.** Deletion, archive, and Task-removal selection recovery still use the fetch-backed reads in `SidebarView+Selection.swift`, which run after a commit where a snapshot would be stale. Placeholder emptiness has no fetch-backed sibling — `hasAnyActiveThreads(for:)` and `hasAnyActiveTaskThreads` exist only on the snapshot, reached in tests via `SidebarTestFixture.renderSnapshot()`.
    - **Never cache models in `@State`.** The snapshot is ephemeral by contract and its inputs are observation-backed `@Query` results. Do not filter `project.threads` in render code; stale relationship entries can trap during `List`/`ForEach` refreshes.
    - **Include drafts in the query, exclude them in the snapshot.** The thread query filters only `archivedAt == nil` so draft changes stay observation-tracked; `SidebarRenderSnapshot` drops drafts from rows, counts, and pinned items.
