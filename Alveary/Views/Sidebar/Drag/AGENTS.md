## Sidebar Drag & Drop

These instructions cover `Alveary/Views/Sidebar/Drag/` — drag sources, target geometry and candidate scoring, the AppKit event monitor and autoscroll, and the Task-into-project access grant.

**Keep a rule here only when the code that would violate it is not the code that documents it.** Mechanism whose only reader is its own file belongs in a doc comment: `sidebarPlacedSectionHeaderFrame`, `sidebarSectionContainerFrame`, `sidebarPinnedSectionEndCandidate`, `sidebarPinnedSectionIsContainerTarget`, `sidebarSourceCanHoldStandalonePin`, `sidebarTaskProjectAccessDrop`, `requestTaskProjectAccessDrop`, `projectChildDragConfiguration`, `SidebarDropCandidateKind`, `SidebarDropCandidate`'s `ignoresIndicatorProximity`/`containerFrame`, and `SidebarDragLogicalOrder`'s `unpinnableTaskIDs`/`projectIDByTaskID` each carry theirs. So do `SidebarDragMonitor`'s root ownership and pointer spaces, `sidebarAutoscrollOriginY`'s AppKit clamp, and the grant dialog's copy rules across `SidebarTaskProjectAccessMessage` and `sidebarTaskProjectAccessConfirmation{Message,Text}`.

Sidebar drag reordering treats project rows and their expanded children as atomic groups.

- **Limit sources.** Project title/dead space, standalone pinned Project-thread and Task titles, unpinned Task rows in the Tasks section, and nested child rows are the drag sources; folder, New Thread, rename, worktree/status, and cleanup controls keep their existing actions. **Every source withholds itself while `editingThreadID != nil`** — an inline rename must not be draggable out from under its own `TextField` — so a new source carries that guard too, or delegates to one that does. A nested Task row drags as `.unpinnedTask`; a nested Project-mode row drags as `.projectThread`, whose only destination is `Pinned` — a project's child list has no manual order. Children of pinned projects are not sources, for the reason `projectThreadDragConfiguration` gives inline; `resolveUnpinnedProjectThreadForOrdering` and the commit validity check are the backstops.
- **Expose outer boundaries only.** A project target exists only at its real header or real terminal row; middle child rows never publish target geometry, and header/terminal geometry stay distinct so virtualization cannot invent a midpoint. Top-level rows publish only `.topLevelTerminal`, measured before trailing spacing, from the row `sidebarTopLevelRowItems` ends on — `Alveary/Views/Sidebar/AGENTS.md` owns that list.
- **Every `.projectsHeader` read goes through `sidebarPlacedSectionHeaderFrame`**, which documents why a `List` section header's two published frames must never be unioned. Only this role needs it today, but any new role backed by a `Section` header rather than an ordinary row needs the same treatment.
- **Center shared boundaries.** Measure project header content before its inter-project top spacing. When adjacent top-level items share a logical insertion boundary, keep source-valid semantic anchors but render them at one Y halfway between the two real visible outer edges, and extend each anchor's hit region to that midpoint so crossing the gap does not blink the line.
- **Keep target semantics source-specific.** Projects may cross `Pinned`/`Projects` only through section edges or project-anchored boundaries; standalone pinned threads stay inside `Pinned` and may target any top-level pinned boundary. One visual line may carry different anchors for the two source types.
- **Keep targeting local and stable.** Activate an outer boundary only from that boundary row, never from an expanded group's visible union. Coalesce transient `List` preference maps and use only a short, non-resetting geometry-miss grace so frame churn neither blinks the line nor preserves a vanished target.
- **Reject inverted geometry.** If transient preferences place a boundary above its owning section start or logical predecessor, omit it and let the grace retain the previous valid line; a raw inverted candidate must never surface above `Pinned` or `Projects`.
- **Trust logical section visibility.** Use `Pinned` header geometry only while the logical pinned order is nonempty; during animated last-item removal, stale header preferences can overlap the sticky `Projects` header, whose upper edge remains the sole hidden-pinned target.
- **Widen the hidden-pinned target's hit region, never its line.** `sidebarPinnedSectionEndCandidate` documents why an empty `Pinned` claims area above the `Projects` header and sets `SidebarDropCandidate.ignoresIndicatorProximity`. The indicator stays at the header's top edge, so keep `sidebarPreviousDropBoundaryEndpoint` returning `nil` for empty `Pinned` — otherwise coalescing moves the line.
- **Let a collapsed section shrink its targets.** Collapsing unmounts the section's rows, so their `.projectHeader`/`.projectTerminal`/`.tasksTerminal` frames stop publishing and the per-project boundaries and `.into` reparent containers inside it disappear. The section's own start survives — `.projectsHeader` and `.tasksHeader` always publish — and the Tasks container falls back to its header row. Toggling is drag-guarded, so geometry cannot vanish mid-drag.
- **Keep the root authoritative.** Sidebar-level drag state, the monitor, and autoscroll outlive virtualized source rows; row disappearance must not cancel a drag. Escape, mouse-up, source deletion, window loss, or root teardown own cancellation/finalization — `SidebarDragMonitor` documents why it cannot live on a row.
- **Keep rows stationary.** Render the indicator in the list overlay and fade the active source group without mutating persisted order until mouse-up; preserve selection and expansion across moves and cancellation.
- **Draw both affordances in the list overlay from named-space geometry**, and never attach a container's border to a row, because `listRowBackground` hoisting misaligns it. `SidebarDropCandidateKind` documents which sections take a line and which take a border; what it cannot show is that `.container` scores distance 0 while the pointer is inside and is excluded from boundary coalescing, so it may stand in for a whole ordered section when the source is choosing membership rather than position.
- **Scope pinned Task targets.** The distinct `.pinnedTask` source may reorder against any mixed Pinned item, never sees Projects targets, and additionally sees the Tasks-section target — a `.container` spanning `.tasksHeader` through `.tasksTerminal`, because Tasks is activity-sorted with no insertion positions; dropping there unpins. A Task placed in a project sees the same target (gated on `projectIDByTaskID`) and dropping removes it from the project, unpinning first when pinned, while keeping its workspace grants — revoking access could break in-flight work. Pinned sources are further gated on `SidebarDragLogicalOrder.unpinnableTaskIDs`; `setThreadPinned`'s guard is the commit backstop.
- **Grant Task folder access through `.into` targets.** Task sources see a `.container` over every project group in both sections, encoded as `SidebarDropPlacement.into`; its hit frame unions the project's header and terminal geometry, banded away from the group's outer edges and trimmed by the sticky `Projects` header's occlusion. Reserve the band only where a boundary actually competes for it: a Task source sees `Pinned` insertion boundaries only while `sidebarSourceCanHoldStandalonePin` holds, so that case reserves each boundary's own half-row (the regions `sidebarBoundaryHitFrame` gives them); everywhere else keep the flat `SidebarDropTargetingMetrics.containerEdgeBand`, and a collapsed group (one frame for both roles) falls back to it too. `moveTaskIntoProject` documents what the drop grants and what the Task keeps. **`.into` never reaches the ordering commit**: every ordering entry point rejects it, and `commitSidebarDrop` / `finalizeSidebarDrag` split it between the owning-project unpin arm and `requestTaskProjectAccessDrop`.
    - Ineligible Tasks still show the target and explain on drop rather than hiding it — except a Task's own project, never a reparent destination: for an unpinned Task it publishes nothing, for a pinned Task it carries the unpin drop instead.
- **Drop a pinned thread onto its owning project to unpin it.** Pinned sources see exactly one `.into` group — their owning project. Non-owning projects publish nothing to a `.pinnedThread`; a `.pinnedTask` keeps reparent containers on every other project and only its own flips to the unpin. `SidebarDragLogicalOrder.owningProjectIDByPinnedThreadID` (built in `makeRenderContext`) scopes it, `unpinnableTaskIDs` gates a pinned Task's own project, and `commitSidebarDropToOwningProject` carries the synchronous commit. The finalizer expands the owning project so a collapsed group does not swallow the landed row.
- **Drag unpinned Tasks and nested Project-mode threads only into Pinned.** `sidebarPinnedSectionIsContainerTarget` documents the whole-section `.container` both sources get and the boundary suppression every `Pinned` publisher owes it. The container takes priority `3` so a nested `.into` group (priority `2`) still wins its own drop; without the tie-break a pinned project could never accept a reparent. While `Pinned` is empty the hidden-pinned boundary stands in, and sources already inside it keep their insertion boundaries. `.projectThread` additionally sees no `Tasks` container and no `.into` project targets. Neither source is ever a drop target or geometry publisher, and both stay in the mid-drag cancellation set.
