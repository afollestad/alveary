## Sidebar Drag & Drop

These instructions cover `Alveary/Views/Sidebar/Drag/` — drag sources, target geometry and candidate scoring, the AppKit event monitor and autoscroll, and the Task-into-project access grant.

**Keep a rule here only when the code that would violate it is not the code that documents it.** Mechanism whose only reader is its own file belongs in a doc comment: `sidebarSectionContainerFrame`, `sidebarCustomSectionDropCandidates`, `sidebarSectionReorderCandidates`, `sidebarSectionReorderAnchor`, `sidebarSectionFollowingPinnedHeaderFrame`, `sidebarPinnedSectionEndCandidate`, `sidebarPinnedSectionIsContainerTarget`, `sidebarSourceCanHoldStandalonePin`, `sidebarTaskProjectAccessDrop`, `requestTaskProjectAccessDrop`, `projectChildDragConfiguration`, `SidebarDropCandidateKind`, `SidebarDropCandidate`'s `ignoresIndicatorProximity`/`containerFrame`, and `SidebarDragLogicalOrder`'s `unpinnableTaskIDs`/`projectIDByTaskID` each carry theirs. So do `SidebarDragMonitor`'s root ownership and pointer spaces, `sidebarAutoscrollOriginY`'s AppKit clamp, and the grant dialog's copy rules across `SidebarTaskProjectAccessMessage` and `sidebarTaskProjectAccessConfirmation{Message,Text}`.

Sidebar drag reordering treats project rows and their expanded children as atomic groups.

- **Limit sources.** Project title/dead space, standalone pinned Project-thread and Task titles, unpinned Task rows in the Tasks section, and nested child rows are the drag sources; folder, New Thread, rename, worktree/status, and cleanup controls keep their existing actions. **Every source withholds itself while `SidebarView.isSidebarInlineEditingActive`** — an inline rename must not be draggable out from under its own `TextField` — so a new source carries that guard too, or delegates to one that does; `Alveary/Views/Sidebar/Rows/AGENTS.md` owns what that flag covers. A nested Task row drags as `.unpinnedTask`; a nested Project-mode row drags as `.projectThread`, whose only destination is `Pinned` — a project's child list has no manual order. Children of pinned projects are not sources, for the reason `projectThreadDragConfiguration` gives inline; `resolveUnpinnedProjectThreadForOrdering` and the commit validity check are the backstops.
- **A drag source's row needs a zero-distance gesture to claim the mouse-down.** `sidebarDragSource`'s 3pt drag can still fail, so `NSHostingView` forwards the press to `-[NSTableView mouseDown:]`, whose tracking loop then eats every later drag *and* the mouse-up — one update, no end, and the sidebar wedged in a drag nothing can finish.
    - **Keep that claim on a view the source wraps, never the same one.** Beside `highPriorityGesture`'s 3pt drag a zero-distance gesture wins outright and no drag ever starts. Rows inherit the claim from `appSelectableRow`; `SidebarSectionHeaderRow.rowToggleGesture` owns the headers' and documents both halves.
- **Expose outer boundaries only.** A project target exists only at its real header or real terminal row; middle child rows never publish target geometry, and header/terminal geometry stay distinct so virtualization cannot invent a midpoint. Top-level rows publish only `.topLevelTerminal`, measured before trailing spacing, from the row `sidebarTopLevelRowItems` ends on — `Alveary/Views/Sidebar/AGENTS.md` owns that list.
- **Every section header is an ordinary row, so each publishes one frame.** Backing one with a SwiftUI `Section` header instead would publish two — the placed frame plus an unplaced copy at the content origin — and unioning them stretches the header across the rows it heads. `SidebarView.body` renders one flat `Section` to keep that impossible.
- **Center shared boundaries.** Measure project header content before its inter-project top spacing. When adjacent top-level items share a logical insertion boundary, keep source-valid semantic anchors but render them at one Y halfway between the two real visible outer edges, and extend each anchor's hit region to that midpoint so crossing the gap does not blink the line.
- **Keep target semantics source-specific.** Projects may cross `Pinned`/`Projects` only through section edges or project-anchored boundaries; standalone pinned threads stay inside `Pinned` and may target any top-level pinned boundary. One visual line may carry different anchors for the two source types.
- **Keep targeting local and stable.** Activate an outer boundary only from that boundary row, never from an expanded group's visible union. Coalesce transient `List` preference maps and use only a short, non-resetting geometry-miss grace so frame churn neither blinks the line nor preserves a vanished target.
- **Keep published geometry in `SidebarDragGeometryStore`, never `@State`.** Rows republish their frames every layout pass, so an observed write rebuilds the whole render snapshot on each animation, scroll, and resize frame. `SidebarView.body` reads only the mirrored `sidebarDragViewportFrame`; every other consumer stays in an event handler.
- **Reject inverted geometry.** If transient preferences place a boundary above its owning section start or logical predecessor, omit it and let the grace retain the previous valid line; a raw inverted candidate must never surface above `Pinned` or `Projects`.
- **Trust logical section visibility.** Use `Pinned` header geometry only while the logical pinned order is nonempty; during animated last-item removal, stale header preferences can overlap the `Projects` header, whose upper edge remains the sole hidden-pinned target.
- **Widen the hidden-pinned target's hit region, never its line.** `sidebarPinnedSectionEndCandidate` documents why an empty `Pinned` claims area above the section that follows it and sets `SidebarDropCandidate.ignoresIndicatorProximity`. The indicator stays at that header's top edge, so keep `sidebarPreviousDropBoundaryEndpoint` returning `nil` for empty `Pinned` — otherwise coalescing moves the line.
    - **Resolve that neighbour from the live order, never as `Projects`.** Sections reorder, so `sidebarSectionFollowingPinnedHeaderFrame` walks `SidebarDragLogicalOrder.sectionOrder` — which keeps a hidden `Pinned`'s slot precisely so this lookup can find what comes after it.
- **Let a collapsed section shrink its targets.** Collapsing unmounts the section's rows, so their `.projectHeader`/`.projectTerminal`/`.tasksTerminal`/`.customSectionTerminal` frames stop publishing and the per-project boundaries and `.into` reparent containers inside it disappear. Every section header keeps publishing, so a collapsed membership container falls back to its header row and a section reorder still finds every boundary. Toggling is drag-guarded, so geometry cannot vanish mid-drag.
- **Keep the root authoritative.** Sidebar-level drag state, the monitor, and autoscroll outlive virtualized source rows; row disappearance must not cancel a drag. Escape, mouse-up, a pointer released without one, source deletion, window loss, or root teardown own cancellation/finalization — `SidebarDragMonitor` documents why it cannot live on a row, and `startEscapeWatch` why the poll covers the button as well as the key.
- **Keep rows stationary.** Render the indicator in the list overlay and fade the active source group without mutating persisted order until mouse-up; preserve selection and expansion across moves and cancellation.
- **Draw both affordances in the list overlay from named-space geometry**, and never attach a container's border to a row, because `listRowBackground` hoisting misaligns it. `SidebarDropCandidateKind` documents which sections take a line and which take a border; what it cannot show is that `.container` scores distance 0 while the pointer is inside and is excluded from boundary coalescing, so it may stand in for a whole ordered section when the source is choosing membership rather than position.
- **Scope pinned Task targets.** The distinct `.pinnedTask` source may reorder against any mixed Pinned item, never sees Projects targets, and additionally sees the Tasks-section target — a `.container` spanning `.tasksHeader` through `.tasksTerminal`, because Tasks is activity-sorted with no insertion positions; dropping there unpins. A Task placed in a project sees the same target (gated on `projectIDByTaskID`) and dropping removes it from the project, unpinning first when pinned, while keeping its workspace grants — revoking access could break in-flight work. Pinned sources are further gated on `SidebarDragLogicalOrder.unpinnableTaskIDs`; `setThreadPinned`'s guard is the commit backstop.
- **Grant Task folder access through `.into` targets.** Task sources see a `.container` over every project group in both sections, encoded as `SidebarDropPlacement.into`; its hit frame unions the project's header and terminal geometry, banded away from the group's outer edges. Reserve the band only where a boundary actually competes for it: a Task source sees `Pinned` insertion boundaries only while `sidebarSourceCanHoldStandalonePin` holds, so that case reserves each boundary's own half-row (the regions `sidebarBoundaryHitFrame` gives them); everywhere else keep the flat `SidebarDropTargetingMetrics.containerEdgeBand`, and a collapsed group (one frame for both roles) falls back to it too. `moveTaskIntoProject` documents what the drop grants and what the Task keeps. **`.into` never reaches the ordering commit**: every ordering entry point rejects it, and `commitSidebarDrop` / `finalizeSidebarDrag` split it between the owning-project unpin arm and `requestTaskProjectAccessDrop`.
    - Ineligible Tasks still show the target and explain on drop rather than hiding it — except a Task's own project, never a reparent destination: for an unpinned Task it publishes nothing, for a pinned Task it carries the unpin drop instead.
- **Drop a pinned thread onto its owning project to unpin it.** Pinned sources see exactly one `.into` group — their owning project. Non-owning projects publish nothing to a `.pinnedThread`; a `.pinnedTask` keeps reparent containers on every other project and only its own flips to the unpin. `SidebarDragLogicalOrder.owningProjectIDByPinnedThreadID` (built in `makeRenderContext`) scopes it, `unpinnableTaskIDs` gates a pinned Task's own project, and `commitSidebarDropToOwningProject` carries the synchronous commit. The finalizer expands the owning project so a collapsed group does not swallow the landed row.
- **A custom section is a membership container, like `Tasks` and `Pinned`.** `sidebarCustomSectionDropCandidates` offers one `.container` per section to every eligible Task except its own members — including a plain `Tasks` row, which has no other membership target. Its threads are activity-sorted, so the drop is always `.end`. Eligibility mirrors the `Tasks` container (`sidebarCustomSectionEligibleTaskID`): Task-shaped sources only, a pinned one only while `unpinnableTaskIDs` allows the unpin. The empty placeholder publishes `.customSectionTerminal`, so an empty section stays droppable.
    - The commit is `SidebarSectionService.moveThread`, shared with the `Tasks` drop: both are membership changes, and `Tasks` is simply the placement with no membership at all.
- **Section headers drag to reorder the sections themselves.** `SidebarDragItem.section` targets only `SidebarDropSection.sectionList`: one `.before` boundary per visible section plus one `.end`, never a container, and never a row-domain target. Built-ins drag too; a hidden empty `Pinned` has no header to grab and keeps its slot regardless.
    - **Refuse `.section` explicitly in every source predicate that opens with a `guard`.** `sidebarSourceCanHoldStandalonePin` returns `true` on fallthrough, so an unrefused section would collect every `Pinned` insertion boundary.
    - The drop resolves through `sidebarSectionReorderAnchor` against the order captured at drag start, so `SidebarView+DragLifecycle` commits it directly; `commitSidebarDrop` has no view of section order and treats `.sectionList` as inert.
- **Drag unpinned Tasks and nested Project-mode threads only into Pinned.** `sidebarPinnedSectionIsContainerTarget` documents the whole-section `.container` both sources get and the boundary suppression every `Pinned` publisher owes it. The container takes priority `3` so a nested `.into` group (priority `2`) still wins its own drop; without the tie-break a pinned project could never accept a reparent. While `Pinned` is empty the hidden-pinned boundary stands in, and sources already inside it keep their insertion boundaries. `.projectThread` additionally sees no `Tasks` container and no `.into` project targets. Neither source is ever a drop target or geometry publisher, and both stay in the mid-drag cancellation set.
