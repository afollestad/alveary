## Scheduled Task Management

- Keep editor state in value snapshots. Re-resolve definitions and Projects through `ScheduledTasksViewModel` when the user commits an action.
- Route create, edit, pause, resume, delete, and Run now preparation through `ScheduledTaskMutationService`; never mutate `ScheduledTask` rows from a view.
- Treat edits and deletion as future-definition changes. Active runs continue from their immutable snapshots.
- **Saving a schedule never changes its target's placement**, and the option list carries no pin note: everything `AgentThread.isEligibleScheduledTaskTarget` offers already renders somewhere openable, a pinned project's child included. Archiving or deleting it switches the schedule to `Same thread each time` (`Alveary/Data/Scheduled/AGENTS.md`).
- The Section row renders only for the two new-thread destinations with no Project (`workspaceKind == .privateWorkspace`) and only while custom sections exist — a Project-backed thread nests under its Project and `AgentThread.customSection` renders solely for projectless task-mode threads. It seeds creation and never moves an existing thread.
- Keep recurrence fields structured and hide timezone input. Treat the persisted IANA identifier as a derived cache of the Mac's current zone, and rebase future wall-clock occurrences when the system zone changes.
- Scheduled editor menu controls wrap their selected value at normal widths and compress with tail truncation inside narrow panes. Date fields inherit the host view's timezone so production follows the Mac while snapshots can inject a deterministic timezone.
- Keep folder grants as native folder selections and display their full paths in accessibility help.
- Keep the Scheduled screen's filters in a `ResponsivePaneHeader`: filter chips leading, a trailing primary create action that folds to an icon-only `plus` once its label stops fitting. Keep list content on the header's horizontal insets by using `PaneHeaderLayout.leadingInset`/`.trailingInset` in the content padding. Do not restore a redundant screen title or explanatory subtitle.
- The selected tab is view-model state, not screen `@State`: `ScheduledTasksViewModel.selectedFilter` restores from `AppSettings.scheduledTasksSelectedTab` and persists only through `selectFilter(_:)`. The header keeps its plain `Binding` parameter (snapshots pass `.constant`); the screen bridges it to the view model.
- **Never build a `DateFormatter` per call in `ScheduledTaskPresentationFormatting`.** Every card formats its recurrence and next occurrence on each body pass, and a weekday schedule names one day per formatter; the type caches by locale and time zone behind `LockedState`. Card reads are hoisted above the screen's `GeometryReader` and `ScheduledTaskCard` is `Equatable` — see **Render Cost** in `Alveary/Views/AGENTS.md`.
- **The Scheduled card face carries no action buttons.** Run now, Pause/Resume, and Delete live in its `AppOverflowMenu`; a footer button row doubles the card's height. The card itself opens the editor pane — see the `appSelectableCard(...)` and card-grid bullets in `Alveary/Views/AGENTS.md`.
    - A menu row shows no tooltip, so an unavailable Run now names its reason in the row's own title rather than the `.help(...)` the buttons carried.
- **The empty state offers suggestions, not a create button** — the header's create action already covers a blank task. `ScheduledTasksViewModel.firstTaskSuggestions` gates its pull-request slot on `AppSettings.pullRequestsEnabled`, since that prompt's host tools refuse while the integration is off; keep the count at three so the layout does not follow a setting.
    - Every suggestion's focus ID must also reach `visiblePaneTriggerFocusIDs`, or dismissing the pane one opened restores focus to the header instead of the card.
- Reuse `ScheduledTaskEditorContent` for manual panes and create/edit proposals. The proposal modal wrapper owns its own draft/error state and submits through the proposal queue; it must never clear or mutate cached manual pane sessions. Root-overlay editors must compress inside a 640-point window; destructive/action-only proposals use the root confirmation overlay and disable confirmation when their captured revision or Project is stale.
- Keep the shared editor section order Task, Schedule, Workspace, then Agent. Existing-thread destinations omit Agent while preserving the same leading section order.
- Provider refresh completion may normalize the bound editor draft only for modal surfaces. The Scheduled screen uses `loadForScreen()` to normalize its active manual session without clearing its local error; proposal presentation uses plain `load()` so it cannot mutate a cached manual session.
- Natural-language proposals are confirmed from their transcript widget, not a root modal. `ScheduledTaskPaneTarget.proposal(sourceConversationID:)` opens the shared editor pane through `requestProposalReview(_:originThreadID:)`, and `submitActivePane` consumes the session's `proposalID` in the same save as the definition mutation. The pane is scoped to the thread that opened it (`activeProposalPaneTarget(forThreadID:)`), mirroring pull-request pane origin scoping; the Scheduled screen withholds `.proposal` targets so a transcript's review cannot follow the user there.
    - **A transcript can open a proposal review or an existing task's editor.** `RightPaneDestination.resolve` accepts any scheduled target except `.create` for a thread selection; restricting it to `.proposal` silently swallows the widget's Edit and View actions. Origin scoping stays where the targets are built.
    - **Refresh providers from the pane itself.** The pane opens from a transcript, where nothing else calls `load()`. Without provider status, `ThreadDefaultResolver.modelOptions` has nothing to return and the Agent section degrades to a single raw-id model option — and an edit target has no task row for the footer's Pause/Resume toggle; the plain `load()` is the right one here because it must not normalize a cached manual session.
    - **Assume the task can be gone.** A transcript card outlives the task it names, so `requestEdit(definitionID:)` reports whether it opened — it refuses a deleted definition and retires any cached session for it — and the widget's View action falls back to the Scheduled screen instead of no-opping.
    - **Key the target by conversation, not proposal.** A follow-up prompt supersedes the proposal being reviewed; keying by conversation lets `refreshActiveProposalPaneIfNeeded()` swap the draft inside the same session and generation, so the pane updates in place instead of animating a second presentation. It runs off `.scheduledTaskProposalsChanged`, and closes the pane when the proposal is gone — unless that session is already submitting or pending dismissal, which would race the pane's own confirm.
