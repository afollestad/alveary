## SwiftUI View Composition

These are view-layer defaults for files under `Alveary/Views/` unless a narrower `AGENTS.md` overrides them. Settings form rows are `Alveary/Views/Settings/AGENTS.md`'s.

- In SwiftUI, prefer extracted `View` types over `some View` extension properties. Keep trivial one-off stacks inline, and only extract when it clarifies composition.
- When an extracted child view is used by another view, place it in the same folder with `Parent+Child.swift` naming such as `DiffViewerPane+Header.swift`.
- **Take a button's chrome from `Components/ActionControls.swift`.** Visible-text buttons use `primaryActionButtonStyle()`, `secondaryActionButtonStyle()`, or `destructiveActionButtonStyle()` by emphasis; icon-only buttons use `iconActionButtonStyle()` or `destructiveIconActionButtonStyle()`, and the former's doc comment owns the sizes and states they share. Reserve `.plain` and `.borderless` for low-emphasis affordances, and never give an icon-only button capsule text-button chrome.
    - **Signal an active state through the style's `foregroundColor:` parameter, never a local `foregroundStyle`.** The style modulates the colour it is handed, so a locally tinted glyph freezes through hover and disabled.
    - A control that already carries a *resting* fill — a reaction chip, the add-reaction button — deepens that fill on hover instead. The shared style's circle appears only on hover, so adopting it would erase the resting chrome those controls need to look clickable.
    - For icon-bearing buttons on the prominent styles, use `ActionButtonLabel` (`Alveary/Views/Components/AGENTS.md`) rather than a `Label`; on macOS the shared style can render `Label` as text-only in some contexts.
- **Every icon-only interactive control needs `.help(...)` and an `.accessibilityLabel`** — not just `iconActionButtonStyle()` buttons. Plain-style glyph buttons, icon-labeled `Menu`s, hover-only affordances, and reaction/emoji controls all qualify: without user-visible text, the hover tooltip is the only discoverable name for sighted users and the label the only name for VoiceOver. Add both at the call site when creating the control, not as a follow-up pass.
- For selectable list rows such as sidebar items, settings tabs, and diff file lists, use the `.appSelectableRow(...)` modifier from `Components/SelectionRowBackground.swift` rather than a `Button` with `.plain` style; it bundles the content shape, tap gesture, press highlight, selection traits, and row background in one call.
    - **A grid card whose detail opens a contextual pane takes `appSelectableCard(...)` from `Components/SelectableCardBackground.swift`** — the card is the click target and marks itself selected while its pane is open. Put its secondary actions in an `AppOverflowMenu`, never a footer button row, which doubles the card's height.
        - **Mirror those rows onto the card's own `.contextMenu`**, built from one row list and mounted outside `appSelectableCard(...)` so the whole card answers a right-click. An empty row list suppresses the menu, so a card with no actions needs no gate.
        - A card that opens a pane but is never *selected* by it takes the `appOutlinedCard(...)` sibling instead, whose doc comment owns that split.
- **A card grid that pairs up when wide takes its columns, column-count flip, and reflow crossfade from `Components/AdaptiveCardGrid.swift`** — a hand-rolled `onGeometryChange` threshold snaps the reflow unanimated mid-pane-slide and drifts from the shared breakpoint.
- Markdown rendering is local SwiftUI `Text`/layout code; keep clickable rows free of nested hit-test blockers.
- **Keep `body` off the compiler's type-check budget.** Swift solves an expression as a whole, so a long modifier chain resolves every generic overload in it together with the hierarchy underneath. Presentation modifiers (`confirmationDialog` / `alert` / `sheet`) and observers (`onChange` / `task` / `overlay`) are both common offenders, and past the wall-clock budget the compiler hard-errors with `unable to type-check this expression in reasonable time`.
    - **Lift modifier groups out of `body`.** Move each group into a `func …<Content: View>(_ content: Content) -> some View` helper, its own type-check scope, and keep chain order identical so modifier semantics do not shift. `Sidebar/SidebarView+Dialogs.swift` and `Chat/Transcript/Scrolling/ChatView+Transcript.swift` are the references. Share one `sidebarPresentationBinding`-style optional-to-`Bool` bridge instead of an inline `Binding(get:set:)` closure pair per dialog.
    - **Measure, and read local numbers as a lower bound.** `TYPECHECK_BUDGET_MS=400 ./scripts/build.sh` lists every body over that many milliseconds and fails if any exist. The same symbols measured ~7x higher on CI than locally, and the ratio varies by code shape, so scale before comparing against the 3000 CI enforces — or read the numbers off a CI run.

## Render Cost

This section owns the cross-surface render-cost rules; `PullRequests/`, `Archived/`, and `Scheduled/` reference it rather than restating it.

- **Hoist every view-model read above a `GeometryReader`.** Its closure re-runs on each geometry change — every frame of a window resize or the right pane's slide — so a read left inside it repeats whatever shaping it triggers per frame. Pair the hoist with memoizing that shaping in the view model (see `Alveary/ViewModels/AGENTS.md`).
- **Reset a search-driven scroll with `ScrollPosition`, never `.id(searchQuery)` on the scroll view.** Keying by the query rebuilds the whole subtree and discards `LazyVGrid`/`LazyVStack` state on every keystroke; `SkillsScreen` and `MCPScreen` hold a `@State ScrollPosition` and call `scrollTo(edge: .top)` from `onChange` instead. Keying by a *discrete* selection (`PullRequestsScreen`, `ScheduledTasksScreen` filter tabs) is fine — those change once per click.
- **A screen `MiddlePane` switches over restores its scroll offset through `restoresScrollOffset(_:position:token:)`**, whose `ScrollOffsetStore` lives on the screen's root-lived view model. That `switch` compiles to `_ConditionalContent`, so every screen is torn down and rebuilt on each sidebar selection change; keeping them mounted instead would leave every screen's `.task` refresh running behind whatever the user is looking at. Every screen that `switch` mounts adopts it.
    - **Never hold that `ScrollPosition` in the screen's own `@State`.** `.scrollPosition(_:)` writes the live position back per scroll frame, so screen-owned state re-evaluates the screen's `body` on every one; the modifier owns it privately, and a screen that must *also* drive the scroll view passes its binding in and drops its own `.scrollPosition(_:)` call.
    - Pass the filter tab as `token` on a tabbed screen so a switch still starts at the top; the store's own doc comment owns the rest.
- **Give list rows and pane children an `Equatable` conformance that excludes their closures.** A parent that re-runs per frame otherwise rebuilds every row. Exclude a closure when its captures are reference types, `@State`/`@FocusState` storage, or values already compared — and say which in the `==` doc comment.
    - **Never compare a `@Binding` there.** A binding's projected read is main-actor computed, so a `nonisolated ==` reads across isolation and Swift 6 warns. Take the value as a plain `let` plus a change closure and rebuild the binding in `body`. Type that closure `@MainActor` so it still satisfies `Binding.init(get:set:)`'s `@Sendable` setter, and give the rebuilt binding an explicitly typed computed property so it stays off `body`'s type-check budget.

## Status Dot Colors

Cross-surface mapping for status dots and chips: `SidebarThreadRow.statusColor`, plus the conversation-tab and terminal-session chips' `statusIndicator: TabChipStatusIndicator` values.

- **Blue** = waiting on the user (`.waitingForUser`) — both a blocked provider process and a transcript decision the runtime cannot see, which `ConversationDecisionAttention` supplies.
    - A collapsed sidebar section header or project row shows the same blue through `SidebarWaitingAttentionDot` while it hides such a thread, standing in for the row's own dot — never another colour, and never the busy spinner.
- **Green** = done / success (`.unread`, `.succeeded`). Inline transcript tool rows are the muted shape-only exception — they render through `transcriptInlineToolRowColor` with no trailing success/error glyphs (see `Alveary/Views/Chat/Blocks/Tools/AGENTS.md`).
- **Red** = error (`.error`, `.failed`). **Orange** = user-cancelled (`.cancelled`). **Secondary** = inert (`.stopped`, `.archived`) and draft pull requests (`PullRequestStatus.draft`).
- **Purple** = merged pull requests (`PullRequestStatus.merged`), reserved so merged cannot read as green "success" or red "closed" beside open and closed on the same surface.
- **Working states carry no color.** `.busy` and `.running` render the shared gray ring spinner (`.secondary`); the spinning shape is the signal, so it stays neutral next to inert gray dots.
- **A new status-dot surface follows this mapping — do not pick colors per surface.** Cases that mean the same thing share a color across enums, so a `.busy` thread and a `.running` terminal session match despite the differing case names.

## Focus And Keyboard Coordination

**This section is the single source of truth for cross-surface focus and keyboard rules**, and applies wherever a view introduces a new `@FocusState`, `.onKeyPress`, or `.keyboardShortcut`. A nested scope that touches focus points here with a "READ FIRST" callout instead of restating these rules, and keeps only its own specifics — the sidebar's traversal order, for one.

- The sidebar `List` (`Alveary/Views/Sidebar/SidebarView.swift`) owns an `@FocusState var isKeyboardFocused` so its `.onKeyPress` fires after mouse interaction. Cross-surface release to the composer is bundled into `claimSidebarFocus()`, which calls `composerFocusRelay.handle?.release()` *before* setting `isKeyboardFocused = true`. The native composer publishes a `ChatComposerFocusHandle` through `.focusedSceneValue(\.chatComposerFocus, ...)` (key in `Alveary/Views/Input/ChatComposerFocus.swift`).
    - **An expensive view never declares the `@FocusedValue` itself** — focused-value re-resolution re-runs every declaring view once per frame of any presentation or removal animation. The sidebar reads the handle through `SidebarFocusBridge`'s relay, whose doc comment owns the mechanism; give a new expensive reader the same one-line bridge parent instead of a direct declaration.
- **Call `claimSidebarFocus()` from every explicit user-action site that should make the sidebar the active keyboard surface**: the `selectedSidebarItem` `.onChange`, expansion toggles, and every row-tap action. Its doc comment owns why row taps cannot be folded into that change handler, and why the release must never route through `.onChange(of: isKeyboardFocused)`.
- Thread-creation commands (⌘N, the sidebar project row `+` button, the project context-menu "New Thread") want the opposite of sidebar focus — the user intends to start typing immediately:
    - Call `appState.requestComposerFocus()` *before* mutating `appState.selectedSidebarItem`. It sets `pendingComposerFocusToken`; while that token is non-nil the sidebar's `.onChange(of: selectedSidebarItem)` skips its `claimSidebarFocus()` call, and `claimSidebarFocus()` clears the token so an explicit sidebar action in between cancels the stale request.
    - The composer passes that token to `BlockInputView.focusEditor()` as a plain `requestFirstResponder: UUID?`, retrying briefly because window attachment can span several render passes on a new thread, then clears it through `onFocusRequestConsumed`.
- **Do not claim composer focus by writing to a `@FocusState` binding.** The production composer routes programmatic focus through `requestFirstResponder` tokens and BlockInputKit focus APIs. New production focus paths must use `ChatComposerFocusHandle` or the token-driven BlockInput path.
- `syncFocusIfNeeded()` in `Alveary/Views/Components/TextInput/AppTextEditor+AppKitCoordinator.swift` may claim AppKit first responder when the focus binding is `true`, but must never force-resign when it becomes `false` — a symmetric resign branch races with click-to-focus and can leave the composer non-interactive. Releasing is the claiming surface's job, as above.
- Attach modifier-key shortcuts (⌘W, ⌘1..9) with `.keyboardShortcut()` on buttons that stay in the window hierarchy, or register them from the scene with `.commands { CommandGroup(...) }`. Both dispatch through the responder chain and are focus-independent, so they fire even when the sidebar has just grabbed `@FocusState`. Never bury a shortcut-bearing button in a conditionally-rendered branch (gated on `hasVisibleChatContent`, say) — the shortcut disappears with the branch.
- A non-modifier `.onKeyPress` on a new surface (arrow keys in a transcript, say) conflicts with the sidebar's focus grab and needs its own coordination. Follow the sidebar/composer pattern: publish a `FocusedSceneValue`, consume it from whichever sibling should release, and release on takeover.
