# Pull Requests Screen

These instructions cover the pull-request browsing UI under `Alveary/Views/PullRequests/`.

- **Reuse the shared pane chrome.** The header is hand-rolled (tab chips + search + refresh + filter menu) at `PaneHeaderLayout.height` with `.bar` background and `AppSeparatorHairline(surface: .paneHeader)`; content padding reuses `PaneHeaderLayout.leadingInset`/`.trailingInset` like Scheduled and Archived.
- **Cards draw their own fill.** Rows live in a `ScrollView`, so `PullRequestRow` renders its own card background; `.appSelectableRow` still supplies gesture and accessibility, but its selection chrome goes through `listRowBackground`, which only renders inside a `List`.
- **Rows are two lines.** Title over the avatar/author/repo/branch attribution line on the left; relative age over the +/- stats on the right; the status glyph stays vertically centered on the far left. Attribution texts hug their content — fixed `frame(maxWidth:)` reservations read as phantom columns.
- **List arrows follow visual order.** The screen's scroll content is `.focusable()`; Up/Down call `selectAdjacentRow(in:forward:)` with rows in visual order (Reviewing = pending section then previous) and scroll the new selection into view. Row clicks claim the same `@FocusState` so arrows work immediately after a click.
- **Status icons are tinted Primer Octicons.** Each status renders its own template glyph tinted whole, matching GitHub: open pull-request glyph green, draft glyph secondary, merge glyph purple, closed (x-badged) glyph red. Merged purple comes from the `PullRequestMergedColor` asset (Primer's `#8250DF` light / `#A371F7` dark) because system `.purple` reads neon in dark mode. No status-dot overlays; color meaning follows the Status Dot Colors table in `Alveary/Views/AGENTS.md`, and `accessibilityName` carries the state for non-color users.
- **Keep ages deterministic.** Relative ages come from `compactRelativeAge(from:relativeTo:)` fed by `viewModel.referenceDate`, so snapshots inject a fixed clock. Snapshot fixtures keep `authorAvatarURL` nil so the letter placeholder renders instead of fetching over the network.
- **Sections come from `visibleSections(for:)`.** Reviewing splits into "Pending review" (review requested — a re-request counts as pending) above "Previously reviewed"; the All tab buckets each row exactly once into "Authored" / "Pending review" / "Previously reviewed" with Authored winning ties; the Authored tab stays a flat untitled list. Section headings use the sidebar's subtle style (`.subheadline` semibold, `.tertiary`). Keyboard order is the flattened section order.
- **Filters are multi-select sets.** `selectedStatuses` / `selectedRepositories` — empty means unconstrained; `PullRequestsFilterPopover` renders checkbox rows with "All" rows that clear their group, and `normalizeRepositoryFilter()` prunes vanished repositories while keeping surviving selections. Rows hide their repository text only when the filter narrows to exactly one repository (`showsRepositoryInRows`). Keep the filter control a `.popover`, never a `Menu` — menus dismiss on the first click, which fights multi-select; snapshot the popover content view directly (live popover hosts crash, see `AlvearyTests/AGENTS.md`).
- **Tab and filters persist through `AppSettings`.** The view model restores `pullRequestsSelectedTab` / `pullRequestsStatusFilters` / `pullRequestsRepositoryFilters` in `init` and writes them only on explicit user actions (`selectFilter(_:)`, filter toggles/clears) — `normalizeRepositoryFilter()` never persists, so a repository absent from one fetch stays selected for the next launch. The tab is VM-owned state (`selectedFilter`), not screen `@State`.
- **Never surface task cancellation as an error.** Leaving the screen cancels the `.task` refresh; `refresh()` swallows `CancellationError` and checks `Task.isCancelled` before applying wrapped service failures, so no banner or unavailable state appears.
- **Comments render remote images.** `AppMarkdownText` shows standalone images as blocks and remote images sharing a line with text inline (Codex `![P1](shields.io/…)` badges next to bold headings), loading through the shared `AppMarkdownImageStore`. Comment snapshot fixtures must inject a preloaded store via `\.appMarkdownImageStore` or keep bodies image-free.
- **Sanitize GitHub HTML before markdown rendering.** `PullRequestMarkdown.sanitized(_:)` rewrites the common tags GitHub allows (`<details>`/`<summary>`, `<p>`, `<br>`, `<b>`, `<em>`, `<code>`, comments) into markdown, leaving fenced code blocks untouched. Every PR body, activity entry, and diff-thread comment renders through it.
- **Detail pane follows the contextual-pane session contract.** `PullRequestPane` renders `viewModel.paneSessions[target]` only; `PullRequestsViewModel` owns activation, generation-guarded async detail/diff loads, and the deactivate-then-dismiss close flow (see `Alveary/ViewModels/AGENTS.md`). Rows open the pane through `requestDetails(_:)`, and row highlight derives from `activePaneTarget`.
- **Page PR diffs by whole files.** `PullRequestDiffFilePaging` owns the policy: render a prefix window of parsed files ("Show N more files" grows it) and seed `collapsedDiffFileIDs` for files over the changed-line threshold. Pass the windowed prefix into `FlattenedDiffPreview` — prefix slicing keeps `fileCollapseID` indices stable. Do not add virtualization; the row-model window is what bounds memory.
- **Reviews submit as one pending batch.** Inline comments accumulate in the session's `PendingReviewDraft` (in-memory only, dropped on quit) and submit together with the overall comment through `submitReview(event:)` — one `POST .../reviews` call, GitHub-style. Validation: `.requestChanges` needs an overall comment, `.comment` needs an overall comment or one inline comment, `.approve` always submits. Approve and Request changes only appear for other people's PRs (`summary.isAuthored`, double-checked against the detail's `viewerLogin`) — GitHub rejects them on your own PR — and the footer's `effectiveEvent` forces `.comment` if a stale verdict selection survives the gating. On success the pending batch stays rendered (with `isSubmitting` keeping the footer disabled) until the refetched detail lands, then both swap in one session write via `loadDetail(onFinish:)` — never clear the draft before the refetch or the comments blink out. Failure keeps the batch and surfaces `submissionError`. The Changes tab feeds existing non-outdated review threads plus pending comments into `DiffCommentAnnotations`; a pending comment replaces any prior pending comment on the same anchor.
- **Submitted comments follow GitHub permissions, not authorship.** Thread comments carry `databaseId`, GraphQL `id`, and `viewerCanUpdate`/`viewerCanDelete`; the three-dot menu appears when either permission holds (repo collaborators can act on other people's comments, including bots) and offers only the permitted actions. Edit swaps the comment's body for the shared editor inline in its thread (`.editRemote`, "Update comment") rather than opening a composer row below it; delete arms a session-owned confirmation (`pendingRemoteCommentDeletion`). Remote edits never touch the pending batch, and action failures without an open composer surface as a banner atop the Changes tab (`composerError`).
- **Remote comment actions live in `PullRequestsViewModel+RemoteComments.swift` and are optimistic like everything else.** Edit rewrites the comment body locally and closes the composer before the PATCH; failure restores the old body and reopens the composer with the attempted text. Delete removes the comment (and an emptied thread) before the DELETE; failure reinserts it via `restoreThreadComment`. Neither refetches on success — the local state is already exact.
- **Comment composing is BlockInputKit.** The inline diff composer and the review footer's overall comment share `PullRequestCommentEditor` + `PullRequestCommentDraftBox` (a per-session `BlockInputMemoryDocumentStore` plus a cheap `isEffectivelyEmpty` flag). Markdown serializes only at save — never per keystroke, which would reconfigure the editor mid-typing — and Save enablement reads the flag. Placeholders: "Leave a comment" for new/reply, "Edit this comment" for edits. Composer-only features (completions, slash commands, drops) stay off, matching the Settings `AGENTS.md` editor host. `PullRequestCommentEditor` sizes through `BlockInputEditor.sizeThatFits` alone — no `onPreferredHeightChange` + `.frame(height:)` state. The callback round trip applies the height a frame after the AppKit editor has already grown, which reads as a glitchy vertical jump on mount and on line add/remove; `sizeThatFits` reports the clamped preferred height synchronously in the same layout pass. (The Settings editor host keeps the callback pattern only because its fixed-height ScrollView case misbehaved with `sizeThatFits`.) **Cmd+Return submits and Escape cancels** through `BlockInputConfiguration.keyboardShortcuts` — the editor's `onSubmit`/`onCancel` run the host's Save/Submit and Cancel actions behind the same guards as the buttons, and plain Return stays a newline because comments are multi-line.
- **Comment actions are optimistic.** Reactions, thread replies, and thread resolution mutate `session.detail` immediately (`PullRequestModels+Optimistic.swift`) and revert on failure — reactions apply the inverse toggle, replies remove the placeholder and reopen the composer with the text intact, resolution flips back. Only a successful reply refetches (to swap the placeholder for the server copy with real ids); reactions and resolution never refetch.
- **Pending comments and reply placeholders are attributed to the viewer.** The detail query's top-level `viewer` field supplies `viewerLogin`/`viewerAvatarURL`; the Changes tab and the optimistic reply both use them (falling back to "You" on a stale detail) so local comments show the same identity GitHub would.
- **Rows sort by recency.** `visibleRows(for:)` orders by `updatedAt` descending — the date each row displays top-right — with `displayKey` breaking ties, client-side so every tab and section inherits it. Status does not participate (an explicit reversal of the earlier status-first order).
- **Overview shows GitHub's Reviewers list, not the decision string.** `makeReviewers` composes pending requests (question mark) with each past reviewer's latest verdict (green check / red bubble), excluding the PR author. Re-request (`arrow.clockwise`, POST `requested_reviewers`) appears only for *human* reviewers with a submitted review — bots/apps never get it (the endpoint rejects them and GitHub hides it too), and a pending request hides it until the reviewer re-reviews. While a re-request round trip runs, `reRequestsInFlight` disables that reviewer's button; failures surface in `session.reviewersError` as a banner inside the Reviewers section, not the Changes-tab `composerError`. Body-less `COMMENTED` reviews are also hidden from the timeline — they are inline-comment carriers whose content renders in threads.
- **Reactions mirror GitHub's fixed palette on every comment surface.** Issue comments, review bodies, and review-thread comments (Files and the Overview timeline alike) render non-empty reaction groups as toggle chips (viewer-reacted = accent outline) plus a circled smiley opening the eight-emoji picker popover. Toggles run `toggleReaction(subjectID:content:viewerHasReacted:)` — GraphQL mutations against the subject's node id — optimistically, never refetching. Pending local comments have no reactions.
- **Comment chrome is shared.** `PullRequestCommentChrome.swift` owns the avatar+login+Bot-pill author row (`PullRequestCommentAuthorRow`, vertically centered), the `Bot` badge (GraphQL author `__typename == "Bot"`), and `PullRequestCommentBody` (sanitized markdown + `CommentReactionBar`); Timeline entries and thread comments compose these instead of hand-rolling headers. The bar itself is the generic `Components/CommentReactionBar.swift`. `PullRequestAvatarView` draws a subtle adaptive circle (`secondary.opacity(0.2)`, GitHub-style) behind loaded images so transparent bot logos stay legible on both themes.
- **Threads reply and resolve like GitHub.** The Changes-tab thread footer offers Reply (opens the shared composer in `.reply` mode; saving POSTs `pulls/{number}/comments/{rootID}/replies` immediately — replies never join the pending batch) and Resolve/Unresolve (`resolveReviewThread`/`unresolveReviewThread` mutations via the thread's node id), each followed by a detail refetch. Resolved threads collapse to a header row with an expand chevron; resolution changes reset the manual expansion so resolving collapses and unresolving expands.
- **There is no Activity tab — the Overview appends the conversation timeline.** The Overview orders header, description (and its reaction bar, with no divider after the header), Reviewers, Checks, then — behind a divider — `PullRequestPaneActivitySection`: issue comments, review cards, bare status rows, and review threads in one chronological stream; threads date by their root comment and their cards link to the Changes tab (`PullRequestPaneTab.files`, displayed as "Changes"). Bare rows cover draft/ready, closed/reopened/merged (tinted octicons), pushed commits (`detail` = "sha headline"), force pushes, and review requested/removed (`detail` = reviewer); `GitHubPullRequestsService+Timeline.swift` maps the GraphQL `timelineItems` types and drops unrecognized ones. The section renders only when it has content, and row glyphs render in a fixed 16pt slot — SF symbols vary in width while octicons are fixed frames (ready-for-review uses the `EyeOcticon` asset, not the wide SF `eye`), so an unslotted mix misaligns the avatar column. Card headers carry a glyph only for review verdicts (green check / red x); plain comment and review cards dropped the chat bubble as redundant beside the author row.
