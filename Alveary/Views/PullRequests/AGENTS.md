# Pull Requests Screen

These instructions cover the pull-request browsing UI under `Alveary/Views/PullRequests/`.

> **READ FIRST:** Focus and keyboard rules are centralized in **Focus And Keyboard Coordination** in `Alveary/Views/AGENTS.md`; the list-arrow focus bullet below stacks on top of that contract.

## Entry Points And Gating

- **`AppSettings.pullRequestsEnabled` gates the whole integration.** It hides the sidebar row — the only entry point, so turning it off removes the screen and its `.task` refresh — *and* the thread toolbar's linked-pull-request button. The toggle lives in the Git settings tab; the screen's `onOpenGitSettings` is the route back. See `Alveary/Views/Sidebar/AGENTS.md` for the top-level-row geometry the gating obeys.
- **The detail pane has a second entry point: a thread's or project's linked pull requests.** `PullRequestLinksPopover` (from the toolbar button in `Alveary/App/ContentView+PullRequestToolbarButton.swift`) lists the selection's `OwnedPullRequestLink` rows and hands a stored `PullRequestSummary` to the same `requestDetails(_:origin:)` the screen's rows use, with `PullRequestPaneOrigin(owner:)` built from the *selection*. Pane *scoping* is not owner-aware — see `Alveary/App/AGENTS.md` for origin scoping and `Alveary/ViewModels/AGENTS.md` for the link store.
    - **The Overview's linked-owners section is the reverse direction.** `PullRequestPaneLinkedOwners` `@Query`s link-holding threads and projects and filters them through `PullRequestLinkedOwnerLookup` (see `Alveary/Data/AGENTS.md`), so it renders in the detail's first frame off local columns and hides itself when nothing links the pull request. Rows select their owner through `\.pullRequestLinkedOwnerOpenAction`, injected at the pane's mount because the pane reaches neither `AppState` nor a `ModelContext`; the action carries a `PullRequestLinkOwner` and `ContentView` re-resolves it. Its title names only the kinds present ("Linked threads" / "Linked projects" / "Linked threads and projects") and the glyph alone separates them — `folder` and `bubble.left.and.bubble.right`, matching the sidebar project row and the `list_threads` tool row — so do not add a kind badge.
    - **Every snapshot host of the Overview or the pane needs `assertMacModelSnapshot`**, since that section queries SwiftData; an empty container leaves it unrendered and keeps the unrelated baselines pixel-identical.
    - **The popover is one component for every count.** Linked rows over a paste-a-URL field. A left click opens the pane only when exactly one pull request is linked — zero or several go to the popover — and a secondary click always opens it, so another can be linked without unlinking first (removing is a row action).
    - **A project's rows aggregate its child threads.** `Project.aggregatedPullRequestLinks` lists the project's own links first, then live child threads' links by `linkedAt`, deduped with the project's copy winning; child rows render a thread `sourceLabel` after the display key. Every row keeps its true owner and mutations route there — unlink removes the *thread's* link, pasting links to the selection itself, and status write-back lands on the rendered row's owner.
    - **Links carry a status snapshot, so the popover and toolbar never fetch to render** (opening a link refreshes it). A network call behind the button would flicker the glyph on every selection change; the aggregate stays plain property reads with a `linkedPullRequestsJSON` nil-check so only link-holding threads pay a JSON decode.

## List Screen

- **Reuse the shared pane chrome.** The header is a `ResponsivePaneHeader` (tab chips + search + refresh + filter popover button); content padding reuses `PaneHeaderLayout.leadingInset`/`.trailingInset`. Both icon buttons stay inline at every width — they are already at the shared 30pt footprint, so only the chips and search give way. This is the widest of the five headers, so it reaches the ladder's lower rungs first.
- **Cards draw their own fill.** Rows live in a `ScrollView`, so `PullRequestRow` renders its own card background; `.appSelectableRow` still supplies gesture and accessibility, but its selection chrome renders only inside a `List`. `PullRequestRowCardBackground` is where the fill lives, reading press, pending-selection, and hover from `AppSelectableRowState` — see `Alveary/Views/Components/AGENTS.md`. Do not move those reads onto `PullRequestRow`; the row would resolve the environment from above the modifier and paint nothing until its model published.
- **Keep row inputs equal across passes.** `PullRequestRow` and `PullRequestsSectionedList` are `Equatable` and take an `activeDetailID` rather than an `isSelected` closure, `visibleSections(for:)` is memoized and resolves once per `PullRequestsScreen` body pass rather than inside the scroll content, and `referenceDate` is stored on the view model. Each of those was a value that differed on every render, which made a click repaint every visible row before its own highlight could land.
    - The hoist-above-`GeometryReader` rule this follows lives in **Render Cost** in `Alveary/Views/AGENTS.md`.
- **Rows are two lines.** Title over the avatar/author/repo/branch line on the left; relative age over +/- stats on the right; the status glyph vertically centered far left. Attribution texts hug their content — fixed `frame(maxWidth:)` reservations read as phantom columns.
- **Titles render inline markdown everywhere they appear**, since GitHub titles routinely carry backticked identifiers. Single-line surfaces (rows, the links popover) take `AppMarkdownInlineLabel`; the pane header wraps and takes `AppMarkdownInlineParagraph`; the transcript widgets take `AppKitMarkdownInlineString`. **Every one of them opts out of mention detection** and builds its accessibility label from `plainText(from:detectingFileMentions: false)` — see `Alveary/Views/Components/Markdown/AGENTS.md` for why. Filtering still matches the raw title, so a query spanning a backtick will not hit; that is deliberate, because the user types what they see.
- **List arrows follow visual order.** The scroll content is `.focusable()`; Up/Down call `selectAdjacentRow(in:forward:)` in visual order and scroll the selection into view. Row clicks claim the same `@FocusState` so arrows work immediately after a click.
- **Status icons are tinted Primer Octicons**, matching GitHub: open green, draft secondary, merged purple, closed red. Merged purple comes from the `PullRequestMergedColor` asset (Primer's `#8250DF` light / `#A371F7` dark) because system `.purple` reads neon in dark mode. Color meaning follows the Status Dot Colors table in `Alveary/Views/AGENTS.md`; `accessibilityName` carries the state for non-color users.
- **Keep ages deterministic.** Relative ages come from `compactRelativeAge(from:relativeTo:)` fed by `viewModel.referenceDate`, so snapshots inject a fixed clock. Snapshot fixtures keep `authorAvatarURL` nil so the letter placeholder renders instead of fetching.
- **Sections come from `visibleSections(for:)`.** Reviewing splits "Pending review" (review requested — **a re-request counts as pending**) above "Previously reviewed"; the All tab buckets each row exactly once with Authored winning ties; Authored stays flat and untitled. Headings use the sidebar's subtle style; keyboard order is the flattened section order.
- **Rows sort by recency.** `visibleRows(for:)` orders by `updatedAt` descending with `displayKey` breaking ties, client-side so every tab and section inherits it. **Status does not participate** — an explicit reversal of the earlier status-first order.
- **Filters are multi-select sets.** `selectedStatuses` / `selectedRepositories`, empty meaning unconstrained; `PullRequestsFilterPopover` renders checkbox rows with "All" rows that clear their group, and `normalizeRepositoryFilter()` prunes vanished repositories while keeping survivors. Rows hide repository text only when the filter narrows to one repository (`showsRepositoryInRows`). Keep *this* filter a `.popover`, never a `Menu` — menus dismiss on first click, which fights multi-select — and snapshot the popover content view directly (live popover hosts crash; see `AlvearyTests/AGENTS.md`). The rule is scoped to the status/repository button; the compact tab dropdown beside it is single-select and is a `Menu` by design.
- **Tab and filters persist through `AppSettings`.** The view model restores `pullRequestsSelectedTab` / `pullRequestsStatusFilters` / `pullRequestsRepositoryFilters` in `init` and writes them only on explicit user actions — `normalizeRepositoryFilter()` never persists, so a repository absent from one fetch stays selected for the next launch. The tab is VM-owned (`selectedFilter`), not screen `@State`.
- **Never surface task cancellation as an error.** Leaving the screen cancels the `.task` refresh; `refresh()` swallows `CancellationError` and checks `Task.isCancelled` before applying wrapped failures.

## Detail Pane And Overview

- **The detail pane follows the contextual-pane session contract.** `PullRequestPane` renders `viewModel.paneSessions[target]` only; `PullRequestsViewModel` owns activation, generation-guarded async loads, and the deactivate-then-dismiss close flow (see `Alveary/ViewModels/AGENTS.md`). Rows open through `requestDetails(_:)`; row highlight derives from `activePaneTarget`.
- **The pane and its tabs are `Equatable`, and new pane children must stay that way.** `ResizableRightPane` re-runs its body on every resize-drag frame and every pane-session write, handing down a fresh dismiss closure, so without equality the whole timeline rebuilt each time. Take the session by value and exclude closures from `==` — the `.id(renderedPresentation)` keying means a closure that would mean something different arrives with a teardown, not a comparison. Route a new child's actions through the view model rather than adding a stored closure.
- **Both tabs stay mounted once visited**, through `KeepAliveTabContainer` (see `Alveary/Views/Components/AGENTS.md` for its rules) — that is what preserves each tab's scroll offset and keeps the Changes tab's prepared diff rows from rebuilding behind a "Preparing diff preview…" spinner on every return. Do not restore this to a `switch` over `selectedTab`. Scroll state is per pane identity by design: a different pull request, or a reopened pane, is a new `.id` and starts at the top.
- **Page PR diffs by whole files.** `PullRequestDiffFilePaging` renders a prefix window of parsed files ("Show N more files" grows it) and seeds `collapsedDiffFileIDs` for files over the changed-line threshold; prefix slicing keeps `fileCollapseID` indices stable. Do not add virtualization — the row-model window bounds memory.
- **The description edits inline, gated on `viewerCanUpdate`** (permission, not authorship). The Overview's meta line carries an Edit-only `PullRequestCommentActionsMenu` (GitHub cannot delete a description). Editing swaps the body for `PullRequestActivityCommentEditor` with `minimumVisibleLineCount: 4` (comments stay at 2) and saves through `session.isEditingDescription` to `PATCH repos/{owner}/{repo}/pulls/{number}`, optimistically with revert on failure. An **empty body still saves** — clearing a description is legitimate — and `PullRequestDetail.bodyMarkdown` is `var` for that optimistic swap.
- **Sanitize GitHub HTML before markdown rendering.** `PullRequestMarkdown.sanitized(_:)` rewrites the common tags GitHub allows (`<details>`/`<summary>`, `<p>`, `<br>`, `<b>`, `<em>`, `<code>`, comments) into markdown, leaving fenced code blocks untouched; every PR body, activity entry, and diff-thread comment renders through it.
- **Comments render remote images.** `AppMarkdownText` shows standalone images as blocks and same-line images inline, loading through the shared `AppMarkdownImageStore`; clicking a loaded block opens the app image preview modal (`ContentView+RightPane.swift` injects `\.appMarkdownImagePreviewAction`). Comment snapshot fixtures inject a preloaded store via `\.appMarkdownImageStore` or keep bodies image-free.
- **Overview shows GitHub's Reviewers list, not the decision string.** `makeReviewers` composes pending requests (question mark) with each past reviewer's latest verdict, excluding the PR author. Re-request (`arrow.clockwise`, POST `requested_reviewers`) appears only for *human* reviewers with a submitted review — the endpoint rejects bots and GitHub hides it too — and a pending request hides it. `reRequestsInFlight` disables the button mid-round-trip; failures land in `session.reviewersError` as a Reviewers-section banner, not `composerError`.
- **The Overview follows its timeline's bottom.** `TimelineBottomFollowing` (`PullRequestPane+OverviewScrolling.swift`) pins the scroll to the end when an entry is appended *and* the reader is already parked there; scrolling up opts out. Two traps, both regression-tested: **content growing beneath a follower is not them scrolling away** — the reading carries content height too, or the first appended row silently disables every later one; and **the scroll must outlive the data change** — armed in `onChange` *and* re-run from the geometry reading that reports the grown content, which also makes it ordering-immune. `0 -> N` is the first detail landing, not an append, and must not bury the header. The modifier is lifted out of `body` (type-check budget).
- **There is no Activity tab — the Overview appends the conversation timeline.** Order: header, description (plus reaction bar, no divider after the header), linked owners, Reviewers, Checks, then behind a divider `PullRequestPaneActivitySection` — issue comments, review cards, bare status rows, and review threads chronologically; thread cards link to the Changes tab (`PullRequestPaneTab.files`, displayed "Changes").
    - Threads nest under the review they were submitted with: `PullRequestActivityEntry.entries(from:)` groups by `reviewNodeID` and `PullRequestActivityReviewGroupView` indents behind an L-shaped rail. A body-less carrier review *with* threads renders as the group header; threads with unknown reviews stay standalone, dated by root comment, kept in fetched order for deterministic siblings.
    - Bare rows cover draft/ready, closed/reopened/merged (tinted octicons), pushed commits, force pushes, and review requested/removed; `GitHubPullRequestsService+Timeline.swift` maps the GraphQL `timelineItems` types and drops unrecognized ones. Merging emits a `closed` event beside `merged`, so `visibleTimelineEvents(_:)` drops closures dated at or after the merge — never all of them, because close-then-reopen-then-merge has a legitimate earlier close. Bare rows stay one ellipsized line.
    - Row glyphs render in a fixed 16pt slot — SF symbols vary in width while octicons are fixed frames (ready-for-review uses `Octicon.eye24`, not the wide SF `eye`) — so an unslotted mix misaligns the avatar column. Card headers carry a glyph only for review verdicts.

## Comments And Threads

- **Comment chrome is shared.** `PullRequestCommentChrome.swift` owns `PullRequestCommentAuthorRow` (avatar+login+`Bot` pill, from GraphQL `__typename == "Bot"`), the tinted `PullRequestCommentBadge` capsule ("Pending", "Outdated"), and `PullRequestCommentBody` (sanitized markdown + `CommentReactionBar`, the generic `Components/CommentReactionBar.swift`). `PullRequestAvatarView` draws a subtle `secondary.opacity(0.2)` circle behind images so transparent bot logos stay legible.
- **Comment composing is BlockInputKit.** The inline diff composer and the review footer share `PullRequestCommentEditor`, a thin `AppMarkdownEditor` wrapper, with `PullRequestCommentDraftBox` as this feature's name for `AppMarkdownDraft`. The shared rules — commit-point serialization, transition-only flag publishes, line-count sizing — live in `Alveary/Views/Components/TextInput/AGENTS.md`. What is specific here: two visible lines default (max ten), mount-time focus relies on BlockInputKit's deferred window-attach handling (`PullRequestCommentEditorFocusTests`), and Cmd+Return submits / Escape cancels behind the same guards as the buttons, with plain Return staying a newline.
- **Never wrap `PullRequestCommentEditor` in a drop modifier.** `dropDestination`/`onDrop` on it (or an ancestor between it and its host) re-propose sizes and silently collapse it by a visible line. Apply `pullRequestAttachmentDropTarget(isEnabled:onDrop:)` to the host's outer container and re-verify editor snapshots after touching the chain.
- **Pending and submitted comments are addressed differently — branch on `isPending` at every entry point.** Pending edits/deletes go over GraphQL by node id (`composerPendingCommentNodeID`); submitted ones over REST by `databaseId` (`composerRemoteCommentID`). Both tabs make the split (`openRemoteCommentEditor`/`requestDeleteRemoteComment` on Changes; `openThreadCommentEditor(_:)`/`requestDeleteThreadComment(_:)` on the Overview); missing it silently PATCHes `pulls/comments/{id}` for a pending comment. Deleting a pending comment skips the confirmation dialog — nothing is published, and `PendingRemoteCommentDeletion` is REST-only. The three-dot menu gates on whichever id its actions need.
- **Submitted comments follow GitHub permissions, not authorship.** Comments carry `databaseId`, GraphQL `id`, and `viewerCanUpdate`/`viewerCanDelete`; the shared `PullRequestCommentActionsMenu` appears when either permission holds and offers only permitted actions, on both tabs. Edit swaps the body for the shared editor inline ("Update comment"); delete arms a session-owned confirmation (`pendingRemoteCommentDeletion`, whose `kind` picks the REST endpoint) in one dialog on `PullRequestPane`. Remote edits never touch the pending batch; failures without an open composer surface as `composerError` banners. Review cards get the same menu gated on the review's `viewerCanUpdate`, Edit only — GitHub cannot delete a submitted review — via `composerReviewID` and `updateReview` (`PUT pulls/{number}/reviews/{id}`).
- **Remote comment actions live in `PullRequestsViewModel+RemoteComments.swift` and are optimistic.** Edit rewrites locally and closes the composer before the PATCH; failure restores and reopens with the attempted text. Delete removes (and an emptied thread) before the DELETE; failure reinserts via `restoreThreadComment`/`restoreIssueComment`. Neither refetches on success. Issue-comment edits track through `composerIssueCommentID` (no diff anchor) to `issues/comments/{id}`; timeline thread-comment edits reuse `composerRemoteCommentID` with a nil anchor so the same edit renders on both tabs. Review summary edits go through `updateReviewBody`.
- **Comment actions are optimistic.** Reactions, replies, and resolution mutate `session.detail` immediately (`PullRequestModels+Optimistic.swift`) and revert on failure. Only a successful reply refetches (to swap the placeholder for the server copy); reactions and resolution never do.
- **Optimistic comments are attributed to the viewer** via the detail query's `viewer` field (`viewerLogin`/`viewerAvatarURL`, falling back to "You" on a stale detail).
- **Reactions mirror GitHub's fixed palette on every comment surface**: non-empty groups as toggle chips (viewer-reacted = accent outline) plus a circled smiley opening the eight-emoji picker. Toggles run `toggleReaction(subjectID:content:viewerHasReacted:)` optimistically against the subject's node id, never refetching. Pending local comments have no reactions.
- **Threads reply and resolve like GitHub — on both tabs.** The shared `PullRequestThreadActionsFooter` offers Reply (POSTs `pulls/{number}/comments/{rootID}/replies` immediately — replies never join the pending batch) and Resolve/Unresolve (`resolveReviewThread`/`unresolveReviewThread` by node id); a successful reply refetches, resolution never does. Changes opens `openThreadReplyComposer(at:thread:)` with a diff anchor; the Overview opens the anchorless overload and renders `PullRequestActivityCommentEditor` inline, replacing the footer — `isReplyingInline` matches root comment id plus nil anchor so each tab shows only its own editor. The optimistic placeholder appends to `detail.reviewThreads`; failure removes it and reopens the editor. A resolved thread collapses its whole conversation to `PullRequestResolvedThreadHeader` with an expand chevron; resolution changes reset manual expansion.
- **Timestamps are compact relative ages with absolute hovers.** `compactRelativeAge` renders through the shared `PullRequestTimestampLabel`, whose `.help` and accessibility label carry the absolute date from `PullRequestTimestampFormatting`'s one cached `DateFormatter` — never build a formatter (or resolve a `FormatStyle`) per render. The Changes tab's recycled rows go further: `DiffLineComment` carries preformatted `relativeAge`/`absoluteTimestamp` strings computed once at annotation-build time. Pane snapshot fixtures must inject a fixed `now` just after the fixture dates.

## Attachments

- **Attachments upload through the `gh-image` extension, never a token.** GitHub publishes no API for comment attachments — the web flow authenticates only with the `user_session` browser cookie, and a `gh` token is ignored outright. `GitHubAttachmentUploadService` shells out to `gh image --repo owner/repo -- <files>` and parses one markdown reference per stdout line, keeping that full-account cookie out of Alveary. A missing extension surfaces as a toast carrying the install command; **do not add a cookie-reading path here**.
- **Uploads are view-model-owned and placeholder-driven.** `PullRequestsViewModel+Attachments.swift` inserts a plain-text `Uploading <name>…` line per file immediately, then swaps placeholders for real links *in order* so duplicate filenames resolve. Failure withdraws placeholders, keeps everything typed, and toasts. The upload runs in an unstructured `Task` on the root-lived view model so pane closure cannot cancel it, and `attachmentUploadsInFlight` is keyed by destination (`.composer` / `.reviewSummary`) rather than the discardable session. Save/Submit stay disabled while an upload runs so a placeholder can never post.
- **Uploads seed the image caches; panes register their repository.** Each `GitHubAttachmentUpload` reaches the injected `attachmentImageSeeder` *before* placeholders are replaced — the fresh asset is still session-gated on GitHub's side, so rendering must come from local bytes (`AppMarkdownImageStore.seedRemoteImage`). `requestDetails` calls `attachmentImageRepositoryRegistrar` so `GitHubAttachmentImageURLResolver` can mint signed URLs for that repository's markdown; see `Alveary/Services/Git/AGENTS.md`.
- **A `sessionUnavailable` failure opens the access-guidance sheet, not a toast** — the remedy is a privacy grant or browser sign-in. The failure lands in `PullRequestsViewModel.attachmentAccessRequest`; `PullRequestsScreen` presents `PullRequestAttachmentAccessSheet` from a lifted `.sheet(item:)` helper. The sheet walks both remedies — Full Disk Access for Safari via `GitHubAttachmentAccessGuide` (see `Alveary/Services/Git/AGENTS.md`) or signing in to GitHub in Chrome — polls the Safari cookie-store probe each second for a green "Access granted" cue, and offers Try Again. The request captures the repository so `retryAttachmentUpload()` works after the pane is gone. Paragraph `Text`s keep `fixedSize(horizontal: false, vertical: true)` or the layout compresses them into truncation.

## Review Submission

- **A comment reveals itself through the view model, not a closure.** Both the Overview's "Show in Changes" and a transcript jump call `requestCommentScroll(to:)`; `PullRequestPane` observes the request, selects the Changes tab, and `FlattenedDiffPreview` scrolls to `comment:<anchor.key>` once its rows exist. Do not widen `onOpenFiles` to carry the anchor — pane children route actions through the view model, and the closure is excluded from `==` on purpose (`PullRequestsViewModelTests+RenderStability`). A jump landing mid-load re-runs `revealDiffFile` when the diff state changes, and the scroll gives up once the diff is loaded without the row, because a force-push can strand an anchor.
    - **Watch the request with `task(id:)`, never `onChange`.** A jump into a *closed* pane arms the scroll inside the same call that opens it, so the token is already set when the pane first mounts; a change handler never fires, and the pane sits on Overview with the Changes tab unmounted — no tab switch, no rows, no scroll. The same holds for anything else keyed to a request that can precede the view.
- **Inline comments post immediately as pending review comments; only the summary is local.** Saving one creates the viewer's PENDING review on GitHub if needed and attaches the comment, so it survives quitting (see `Alveary/Services/Git/AGENTS.md` for the mutation set and `Alveary/ViewModels/AGENTS.md` for the optimistic flow). `PendingReviewDraft` holds only `overallComment` / `isSubmitting` / `submissionError` — matching github.com. Pending comments arrive as ordinary `detail.reviewThreads` entries flagged `isPending`; the Changes tab feeds only the detail's non-outdated threads into `DiffCommentAnnotations`, nothing local merged in — the diff is the one surface that cannot place an outdated thread, since `FlattenedDiffPreview` emits a comment row only from a rendered line and an outdated anchor either matches nothing or lands on unrelated code. The Overview shows them with the "Outdated" pill and the host tools list them, so do not "fix" this by re-deriving either from this filter. **The one exception is a pull request with a review proposal pending** — the comment joins that review's staged comments instead, and nothing merged in becomes "nothing but them" (below).
- **Submitting finishes the pending review rather than opening a second one.** `submitReview(event:)` calls `submitPendingReview` when `detail.pendingReviewNodeID` is set, falling back to a summary-only `POST .../reviews` only with no draft. Validation: `.requestChanges` needs an overall comment; `.comment` needs an overall comment or one pending comment (`detail.pendingCommentCount`, also the footer's count note); `.approve` always submits. Approve and Request changes only appear for other people's PRs (`PullRequestReviewFooterAuthorship`, below) — GitHub rejects them on your own — and `effectiveEvent` forces `.comment` if a stale verdict survives the gating. Comments render straight from `session.detail`, so they persist through the reclassifying refetch; a failure loses nothing.
- **The orange "Pending" pill is the unsubmitted marker on both tabs**, from GitHub's `PENDING` comment state, rendered through the shared `PullRequestCommentBadge` (`DiffCommentThreadRow` on Changes, `PullRequestReviewThreadView` on the Overview, which also draws "Outdated"). A pending thread suppresses what GitHub does not offer until submission: no `PullRequestThreadActionsFooter` (the Overview's footer gate needs an explicit `!thread.isPending` guard) and no reaction bar. `makeReviews` drops the viewer's draft, so pending threads land as standalone Overview timeline entries — do not filter them out.
- **"Proposed" is its orange sibling, and the two are different states.** "Pending" is the viewer's server-side draft; "Proposed" is a review proposal's staged comment, living only in Alveary's envelope until the review is submitted. Same tint because both are unpublished, and mutually exclusive by construction (`isProposed` implies `!isPending`, on both `DiffLineComment` and `PullRequestComment`). **Both tabs render them** — the Changes tab in the diff, the Overview as threads at the timeline's end, dated by the proposal's `createdAt`.
    - **Overview threads are synthesized per render, never written into `detail.reviewThreads`.** That array is GitHub's record, and a synthetic entry would reach everything trusting it — `pendingCommentCount` and the submit gates included. `PullRequestReviewProposalCoordinator.stagedThreads(...)` builds them; `hasContent(detail:proposedCommentCount:)` counts them, so a quiet pull request whose only activity is a waiting review still shows one.
    - **A staged comment's one action is Delete, on all three surfaces** — both pane tabs and the transcript's review-proposal card — through `PullRequestCommentActionsMenu` with `onEdit: nil`. No confirmation: nothing is published, exactly as deleting an unpublished pending comment skips it. Editing in place is a deliberate absence — remove and re-add.
    - **The transcript is AppKit and cannot mount that menu, so it reads its parts.** `PullRequestCommentActionsMenu`'s statics (glyph, point size, hit target, name, row titles and symbols) and `PullRequestCommentRevealAction` (icon, tint, both titles) exist for exactly that; add to them rather than respelling a title or metric on either side. The reveal tint is `AppAccentIcon`, not a bare `Color.accentColor` — at caption size the plain accent washes out in light mode.
    - **While a proposal is pending, composing edits *that* review, not GitHub's draft.** `saveComposerComment` stages into the envelope through `PullRequestReviewProposalCoordinator.addStagedComment`; a comment written to the viewer's draft would be published by the same Submit yet never reach the transcript card, so the two surfaces would disagree about what the review says. No optimistic placeholder — the envelope write is synchronous and the merged annotations re-derive from it. A refusal reopens the composer with its text, like every other composer failure here.
    - **Submit then routes through the coordinator**, so the staged comments and the viewer's own draft comments publish as one review and the card resolves as confirmed. The footer's summary outranks the proposal's body (`confirm(bodyOverride:)`) and falls back to it when untouched; detaching is free, because a cleared envelope stops resolving. **Accepted:** starting a new agentic review from the footer meanwhile creates a competing proposal from another conversation, and the newest wins — noted, not guarded.
    - **Which staged comments render follows the pull request, not the route.** `PullRequestsViewModel.pendingReviewProposal(for:)` scans the proposal coordinator's presentations for the target's identifier, so the toolbar, the links popover, the list, and a transcript jump all show the same thing; the newest `createdAt` wins when two conversations hold proposals for one pull request. It resolves on every read, so confirming or rejecting anywhere drops the comments with no observer to keep in sync. **The pane stores no attachment** — only `pendingCommentScrollTarget`, which is the jump's scroll and nothing more.
    - **`PullRequestPaneFiles` takes its `target` explicitly** rather than reading `activePaneTarget`, so it resolves for the session it was handed — which is also what lets a snapshot host render the tab without opening a pane.
    - Merging is `PullRequestReviewProposalCoordinator.appendStagedComments(_:to:viewerLogin:viewerAvatarURL:)`, shared with the transcript card's own preview. Both surfaces show the same review, so neither may grow its own copy.
- **Review cards without a summary body are bare headers** — no body, reactions, or menu (`showsCardBody` / `actionableReview`), matching GitHub's verdict rows; commented/pending cards read "commented", not "reviewed". Body-less `COMMENTED` reviews with no threads are hidden as empty shells.

## Footer And State Changes

- **A written review outranks the stored pick.** With staged comments waiting, `effectiveReviewKind` forces Submit review — starting a second agentic thread would be the wrong default, and a review's proposal would supersede the comments on screen. The caret still reaches both agentic options, so this changes the default rather than removing them, mirroring `effectiveEvent` and `effectiveStateAction`. **The footer's comment count is exactly what Submit would publish** — the viewer's GitHub draft plus any staged comments — summed once in `PullRequestsViewModel.submittableCommentCount(for:session:)` and read by the note, the Submit enablement, and `submitReview`'s own guard, so the button cannot offer a submit the guard then silently refuses. The note drops the word "pending" once staged comments are in it: that is GitHub's word for the draft alone, and a staged comment wears the "Proposed" pill.
- **The trailing button is always a `SplitActionButton`: Submit review, Agentic review, or Address feedback.** `PullRequestReviewFooterAction` has no availability policy — every option applies to every pull request, and `propose_pr_review` validates the verdict when the agent proposes one. Both agentic options call `PullRequestsViewModel.startAgenticThread(kind:)` (see `Alveary/Services/PullRequests/AGENTS.md`) and share one busy flag and one banner, so a pull request cannot grow two agentic threads at once; failures render as a third footer banner beside `stateChangeError`.
    - **Starting one shows `isBusy`, not `disabled`.** The wait is short now — navigation no longer waits on GitHub — but it still spans provider resolution, and a greyed pill read as "unavailable" rather than "working". Only failures that happen *before* navigation reach the banner; the deferred half toasts, because navigation has already unmounted this footer.
    - **Authorship picks the default, and there are two stored picks.** `PullRequestReviewFooterAuthorship` resolves the summary/detail ladder once for both readers — the verdict gating and the footer default — and routes to `AppSettings.pullRequestOwnFooterActionKind` (Address feedback) or `pullRequestOthersFooterActionKind` (Agentic review). `.unknown` reads the others' key, the safer side while the detail is in flight.
    - **The selection is seeded `@State`, not a `body` read.** The footer is a memoization boundary whose `==` excludes settings, so a settings read in `body` would not re-render on change anyway. Authorship can settle *after* the seed, so an `onChange` re-seeds — but never over a pick made in this session, which `hasPickedReviewKind` guards. A different pull request remounts the footer and re-seeds for free.
- **The footer's collapsed row is the state button beside Submit review.** `PullRequestStateAction.available(for:)` owns the policy and returns empty — leaving the single trailing "Submit review..." button — when the detail has not loaded, `viewerCanUpdate` is false, or the PR is merged. Otherwise the two buttons split the row evenly with `ContextualPaneLayout`'s action spacing and minimum width. Close PR wears destructive red (`PullRequestStateAction.isDestructive`) as the only state change that throws work away; the other actions stay secondary, and the loading stand-in follows the same rule so color never changes when the detail lands. Reopen disables when `headRefExists` is false with a note naming the branch — reopening without it is a 422. **The pending-comment count sits above the buttons** (the split row has no leading room), and the state button never appears while a review is being written.
- **Open and draft pull requests get a `SplitActionButton`; closed keeps a plain one.** `available(for:)` returns actions **default-first** — a draft yields `[markReady, close]`, open `[close, markDraft]`, closed one action. The split's emphasis follows the *selected* action; the menu keeps the select-only contract (see `Components/AGENTS.md`) with the pick in `selectedStateKind` resolved through `effectiveStateAction`, whose first-available fallback retires a stale option once the PR changes state — the same guard `effectiveEvent` applies to a stale verdict. Both draft directions drop out when `detail.nodeID` is nil, because each mutation is addressed by node id.
- **The row keeps its even split while the detail loads.** `PullRequestStateAction.placeholder(for:)` renders a disabled stand-in titled from the session summary's status whenever `session.detail` is nil, titled like the eventual default so the label does not change under the pointer. Merged gets no stand-in; a viewer without write permission briefly sees the stand-in before the button disappears. An identifier-opened pane has no summary to title one with (see `Alveary/ViewModels/AGENTS.md`), so it shows the lone Submit review button until its detail lands — and withholds Approve / Request changes meanwhile, because authorship is still unknown and GitHub rejects a verdict on your own pull request.
- **State changes apply optimistically, then refetch.** `PullRequestsViewModel+StateChanges.swift` funnels close, reopen, and both draft directions through `performStateChange(optimisticStatus:mutate:)`: it sets the expected status on the pane session *and* its list row (`applyStatus(_:toRow:)`, the only writer of `items` outside a refresh), then reloads the detail so the settled status replaces the optimistic one (a reopened draft comes back `.draft`). Resolve what the mutation needs *before* entering it — `markPullRequestReadyForReview()` and `convertPullRequestToDraft()` read the node id up front so a nil one cannot apply an optimistic status for a request that never runs. `isChangingState` guards re-entry; failures land in `session.stateChangeError` as a dismissible banner and leave the status untouched.

## Chrome And Layout

- **Everything the pane draws on its own background ends on the 16pt content column.** The scroll views span the full pane width — `PullRequestPane` insets only the tab row, and the Changes tab folds the pane inset into `FlattenedDiffPreview`'s `horizontalContentInset` — so the pane title, tab chips, `headerSection`'s diff stats, bare-row timestamps, card edges, diff code surface, and footer button all land on `ContextualPaneLayout.horizontalInset`. Do not re-add the diff preview's own 6pt inset on top of it; that put the Changes tab 6pt deeper than every sibling while its call site claimed to match them.
    - **Its glyphs center on the trailing lane instead** — the header's close button, the tab row's Open-on-GitHub button, the description's Edit menu, linked-owner chevrons, reviewer verdict icons, Checks arrows, and the Changes tab's file-collapse carets, through `contextualPaneTrailingGlyphLane()` and `collapseCaretAxis`. See **Pane Insets And Chrome** in `Alveary/Views/Components/AGENTS.md`, which owns the rule. `testPullRequestPaneTrailingColumn` guards the header/tab-row seam; the Overview baselines guard the row glyphs.
    - **Accepted:** the description's Edit menu is interactive and ends 16pt from the scroll edge, inside the 28pt clearance — but well past the 11pt that measured clean, so clicks should survive. Chosen over floating one control off a column every neighbour sits on; do not "fix" it by re-padding `headerSection`, which is what held the whole header 12pt in.
- **A control inside a *card* is inset from its card, not from the pane.** `AppScrollIndicatorLayout.interactiveTrailingClearance` (28pt) is what the timeline cards' 16pt content inset plus 12pt interior padding already comes to, so their `⋯` menus clear the scroller for free. Changes-tab cards land controls at 36pt (16pt content inset + 8pt card outset + the Overview-matched 12pt interior trailing); see `Alveary/Views/DiffViewer/AGENTS.md`.
    - Do not push clearance down into `PullRequestCommentActionsMenu` — it would double-inset every card, and the same menu is used off-card on the meta row. That off-card use needs no lane modifier either: the ellipsis is trailing-aligned inside the menu's own 24pt hit frame, which already lands it on the axis.
