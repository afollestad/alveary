# Pull Requests Screen

These instructions cover the pull-request browsing UI under `Alveary/Views/PullRequests/`.

- **`AppSettings.pullRequestsEnabled` gates the whole integration.** It hides the sidebar row — the only entry point to this screen, so turning it off removes the screen entirely, and its `.task` refresh is the only background work here, which stops with the unmount — *and* the thread toolbar's linked-pull-request button. The toggle lives in the Git settings tab's `Pull requests` section, and the screen's own `onOpenGitSettings` is the route back to it. See `Alveary/Views/Sidebar/AGENTS.md` for the top-level-row geometry rules that gating obeys.
- **The detail pane has a second entry point: a thread's or project's linked pull requests.** `PullRequestLinksPopover` (opened from the toolbar button in `Alveary/App/ContentView+PullRequestToolbarButton.swift`) lists the selection's `OwnedPullRequestLink` rows and hands a stored `PullRequestSummary` to the same `requestDetails(_:origin:)` the screen's rows use, with the origin built from the *selection* (`PullRequestPaneOrigin(owner:)`). Nothing about the pane itself is owner-aware — see `Alveary/App/AGENTS.md` for the origin scoping and `Alveary/ViewModels/AGENTS.md` for the link store.
    - **The popover is one component for every count.** Linked rows over a paste-a-URL field; with nothing linked it is just the field. A left click opens the pane only when exactly one pull request is linked — zero or several go to the popover — and a secondary click always opens it, so another can be linked without unlinking first. Removing is a row action, which is why the single-link case still needs the secondary click.
    - **A project's rows aggregate its child threads.** `Project.aggregatedPullRequestLinks` lists the project's own links first, then live (non-draft, non-archived) child threads' links by `linkedAt`, deduped with the project's copy winning; child rows carry a thread `sourceLabel` the row renders after the display key. Every row keeps its true owner, and mutations route there — unlink from the project view removes the *thread's* link, pasting a URL links to the selection itself, and the pane's status write-back lands on the rendered row's owner.
    - **Links carry a status snapshot, so the popover and toolbar never fetch to render.** Opening a link refreshes it. Keep it that way: the popover must stay paint-instantly, and a network call behind the button would make the glyph flicker on every selection change — the aggregate stays plain property reads too, with a `linkedPullRequestsJSON` nil-check so only link-holding threads pay a JSON decode.
- **Reuse the shared pane chrome.** The header is hand-rolled (tab chips + search + refresh + filter menu) at `PaneHeaderLayout.height` with `.bar` background and `AppSeparatorHairline(surface: .paneHeader)`; content padding reuses `PaneHeaderLayout.leadingInset`/`.trailingInset` like Scheduled and Archived.
- **Cards draw their own fill.** Rows live in a `ScrollView`, so `PullRequestRow` renders its own card background; `.appSelectableRow` still supplies gesture and accessibility, but its selection chrome goes through `listRowBackground`, which only renders inside a `List`.
- **Rows are two lines.** Title over the avatar/author/repo/branch attribution line on the left; relative age over the +/- stats on the right; the status glyph stays vertically centered on the far left. Attribution texts hug their content — fixed `frame(maxWidth:)` reservations read as phantom columns.
- **List arrows follow visual order.** The screen's scroll content is `.focusable()`; Up/Down call `selectAdjacentRow(in:forward:)` with rows in visual order (Reviewing = pending section then previous) and scroll the new selection into view. Row clicks claim the same `@FocusState` so arrows work immediately after a click.
- **Status icons are tinted Primer Octicons.** Each status renders its own template glyph tinted whole, matching GitHub: open pull-request glyph green, draft glyph secondary, merge glyph purple, closed (x-badged) glyph red. Merged purple comes from the `PullRequestMergedColor` asset (Primer's `#8250DF` light / `#A371F7` dark) because system `.purple` reads neon in dark mode. No status-dot overlays; color meaning follows the Status Dot Colors table in `Alveary/Views/AGENTS.md`, and `accessibilityName` carries the state for non-color users.
- **Keep ages deterministic.** Relative ages come from `compactRelativeAge(from:relativeTo:)` fed by `viewModel.referenceDate`, so snapshots inject a fixed clock. Snapshot fixtures keep `authorAvatarURL` nil so the letter placeholder renders instead of fetching over the network.
- **Sections come from `visibleSections(for:)`.** Reviewing splits into "Pending review" (review requested — a re-request counts as pending) above "Previously reviewed"; the All tab buckets each row exactly once into "Authored" / "Pending review" / "Previously reviewed" with Authored winning ties; the Authored tab stays a flat untitled list. Section headings use the sidebar's subtle style (`.subheadline` semibold, `.tertiary`). Keyboard order is the flattened section order.
- **Filters are multi-select sets.** `selectedStatuses` / `selectedRepositories` — empty means unconstrained; `PullRequestsFilterPopover` renders checkbox rows with "All" rows that clear their group, and `normalizeRepositoryFilter()` prunes vanished repositories while keeping surviving selections. Rows hide their repository text only when the filter narrows to exactly one repository (`showsRepositoryInRows`). Keep the filter control a `.popover`, never a `Menu` — menus dismiss on the first click, which fights multi-select; snapshot the popover content view directly (live popover hosts crash, see `AlvearyTests/AGENTS.md`).
- **Tab and filters persist through `AppSettings`.** The view model restores `pullRequestsSelectedTab` / `pullRequestsStatusFilters` / `pullRequestsRepositoryFilters` in `init` and writes them only on explicit user actions (`selectFilter(_:)`, filter toggles/clears) — `normalizeRepositoryFilter()` never persists, so a repository absent from one fetch stays selected for the next launch. The tab is VM-owned state (`selectedFilter`), not screen `@State`.
- **Never surface task cancellation as an error.** Leaving the screen cancels the `.task` refresh; `refresh()` swallows `CancellationError` and checks `Task.isCancelled` before applying wrapped service failures, so no banner or unavailable state appears.
- **Comments render remote images.** `AppMarkdownText` shows standalone images as blocks and remote images sharing a line with text inline (Codex `![P1](shields.io/…)` badges next to bold headings), loading through the shared `AppMarkdownImageStore`. Clicking a loaded image block opens the app image preview modal (`ContentView+RightPane.swift` injects `\.appMarkdownImagePreviewAction` at the pane mount), matching the chat transcript. Comment snapshot fixtures must inject a preloaded store via `\.appMarkdownImageStore` or keep bodies image-free.
- **The description edits inline, gated on `viewerCanUpdate`.** The detail query fetches the pull request's own `viewerCanUpdate` (permission, not authorship — same rule as comment menus), and the Overview's meta line carries an Edit-only `PullRequestCommentActionsMenu`; GitHub cannot delete a description. Editing swaps the rendered body for the shared `PullRequestActivityCommentEditor` with `minimumVisibleLineCount: 4` — descriptions hold more than comments, which stay at 2 — and saves through `session.isEditingDescription` in `dispatchImmediateComposerSendIfNeeded()` to `PATCH repos/{owner}/{repo}/pulls/{number}`. It applies optimistically and reverts on failure like every other remote edit, and unlike a comment an **empty body still saves**, because clearing a description is legitimate. `PullRequestDetail.bodyMarkdown` is `var` for exactly that optimistic swap.
- **Attachments upload through the `gh-image` extension, never a token.** GitHub publishes no API for comment attachments: the web drag-and-drop flow (`/upload/policies/assets` → presigned S3 → finalize) authenticates *only* with the `user_session` browser cookie, and a `gh` token is ignored outright (the endpoint answers 422 identically with a token, with `Bearer`, and with no auth at all). `GitHubAttachmentUploadService` shells out to `gh image --repo owner/repo -- <files>` and parses one markdown reference per stdout line, which keeps that full-account cookie out of Alveary — the extension reads it from the browser's own encrypted cookie store. A missing extension surfaces as a toast carrying the install command; do not add a cookie-reading path here.
- **Uploads are view-model-owned and placeholder-driven.** `PullRequestsViewModel+Attachments.swift` inserts a plain-text `Uploading <name>…` line per file immediately (GitHub's own feedback), then swaps each placeholder for its real link, matching files to placeholders *in order* so duplicate filenames resolve correctly. Failure withdraws the placeholders, keeps everything typed, and toasts. The upload runs in an unstructured `Task` on the root-lived view model, so closing the pane or leaving the screen cannot cancel it, and `attachmentUploadsInFlight` is keyed by destination (`.composer` / `.reviewSummary`) rather than stored on the session, which is discarded on dismissal. Save/Submit stay disabled while an upload runs so a placeholder can never post.
- **Uploads seed the image caches; panes register their repository.** A successful upload passes each `GitHubAttachmentUpload` to the injected `attachmentImageSeeder` *before* placeholders are replaced — the fresh asset is still session-gated on GitHub's side, so rendering must come from the local bytes (`AppMarkdownImageStore.seedRemoteImage`), and the draft editor loads its image block the moment the reference lands in the text. `requestDetails` calls `attachmentImageRepositoryRegistrar` so `GitHubAttachmentImageURLResolver` can mint signed URLs for attachment images in that repository's markdown (private repos, fresh assets); see `Alveary/Services/Git/AGENTS.md`.
- **A `sessionUnavailable` failure opens the access-guidance sheet, not a toast.** The remedy is a privacy grant or a browser sign-in, which a toast cannot walk through: the failure lands in `PullRequestsViewModel.attachmentAccessRequest`, and `PullRequestsScreen` presents `PullRequestAttachmentAccessSheet` from it (a lifted `.sheet(item:)` helper, keeping `body` off the type-check budget). The sheet walks both remedies — Full Disk Access for Safari via `GitHubAttachmentAccessGuide` (see `Alveary/Services/Git/AGENTS.md`), or signing in to GitHub in Chrome — polls the Safari cookie-store probe each second to flip a green "Access granted" cue, and offers Try Again. The request captures the repository so Retry works after the pane (or its session) is gone; `retryAttachmentUpload()` re-enters the private repository-carrying `attachFiles` overload. Paragraph `Text`s keep `fixedSize(horizontal: false, vertical: true)` or the enclosing layout can compress them into truncation.
- **Never wrap `PullRequestCommentEditor` in a drop modifier.** The editor answers `BlockInputEditor.sizeThatFits` against the ambient proposal, and both `dropDestination` and `onDrop` on it (or on an ancestor between it and its host) re-propose sizes and silently collapse it by a visible line. Apply `pullRequestAttachmentDropTarget(isEnabled:onDrop:)` to the host's outer container, and re-verify the editor snapshots after touching that chain.
- **Sanitize GitHub HTML before markdown rendering.** `PullRequestMarkdown.sanitized(_:)` rewrites the common tags GitHub allows (`<details>`/`<summary>`, `<p>`, `<br>`, `<b>`, `<em>`, `<code>`, comments) into markdown, leaving fenced code blocks untouched. Every PR body, activity entry, and diff-thread comment renders through it.
- **Detail pane follows the contextual-pane session contract.** `PullRequestPane` renders `viewModel.paneSessions[target]` only; `PullRequestsViewModel` owns activation, generation-guarded async detail/diff loads, and the deactivate-then-dismiss close flow (see `Alveary/ViewModels/AGENTS.md`). Rows open the pane through `requestDetails(_:)`, and row highlight derives from `activePaneTarget`.
- **Page PR diffs by whole files.** `PullRequestDiffFilePaging` owns the policy: render a prefix window of parsed files ("Show N more files" grows it) and seed `collapsedDiffFileIDs` for files over the changed-line threshold. Pass the windowed prefix into `FlattenedDiffPreview` — prefix slicing keeps `fileCollapseID` indices stable. Do not add virtualization; the row-model window is what bounds memory.
- **The footer's collapsed row is the state button beside Submit review.** `PullRequestStateAction.available(for:)` owns the policy and returns an empty list — leaving the single trailing "Submit review..." button — when the detail has not loaded, `viewerCanUpdate` is false, or the pull request is merged (GitHub offers no state change on a merged PR). Otherwise the two buttons split the row evenly with `ContextualPaneLayout`'s action spacing and minimum width, matching the other detail panes' footers. Close PR wears the destructive red (`PullRequestStateAction.isDestructive`) because it is the only state change that throws work away; Reopen PR, Mark ready for review, and Mark as draft stay secondary, and the loading stand-in follows the same rule so the color does not change when the detail lands. Reopen disables when `headRefExists` is false and the note above the buttons names the branch ("The `feat/x` branch has been deleted.") — reopening without the branch is a 422. The pending-comment count moved above the buttons for the same reason: the split row has no leading room. The expanded composer row keeps its own Attach/Cancel/Submit trailing group; the state button never appears while a review is being written.
- **Open and draft pull requests get a `SplitActionButton`; closed keeps a plain one.** `available(for:)` returns actions **default-first**, so a draft yields `[markReady, close]` and an open pull request `[close, markDraft]`, while closed yields one action and stays a plain button. The primary side always leads with the likelier action, so the split's emphasis follows the *selected* action — Close PR keeps its destructive red on an open PR, and promoting Mark as draft through the menu drops it to secondary. The menu keeps the component's select-only contract — picking the other action re-labels the primary side and a second click runs it (see `Components/AGENTS.md`) — with the pick held in `selectedStateKind` and resolved through `effectiveStateAction`, which falls back to the first available action. That fallback is what retires the stale option once the PR changes state, the same guard `effectiveEvent` applies to a stale review verdict. Both draft directions drop out when `detail.nodeID` is nil, because each mutation is addressed by node id.
- **The row keeps its even split while the detail loads.** `PullRequestStateAction.placeholder(for:)` renders a disabled stand-in titled from the list row's already-known status (`session.summary.status`) whenever `session.detail` is nil, so the footer never paints a lone trailing button and then snap to two halves. It is titled like the eventual default — a draft reads "Mark ready for review", not "Close PR" — so the label does not change under the pointer. Merged gets no stand-in, and write permission is unknown until the detail lands, so a viewer without it briefly sees the stand-in before the button disappears.
- **State changes apply optimistically, then refetch.** `PullRequestsViewModel+StateChanges.swift` funnels close, reopen, and both draft directions through one `performStateChange(optimisticStatus:mutate:)`: it sets the expected status on the pane session *and* its list row (`applyStatus(_:toRow:)`, the only writer of `items` outside a refresh), then reloads the detail so GitHub's own timeline row lands in the Overview and the settled status replaces the optimistic one (a reopened draft comes back `.draft`, not `.open`). Resolve whatever the mutation needs *before* entering it — `markPullRequestReadyForReview()` and `convertPullRequestToDraft()` both read the node id up front, so a nil one cannot apply an optimistic status for a request that never runs. `isChangingState` guards re-entry and disables the button; failures land in `session.stateChangeError` as a dismissible footer banner and leave the status untouched.
- **Inline comments post immediately as pending review comments; only the summary is local.** Saving one creates the viewer's PENDING review on GitHub if needed and attaches the comment, so it shows on github.com and survives quitting (see `Alveary/Services/Git/AGENTS.md` for the mutation set and `Alveary/ViewModels/AGENTS.md` for the optimistic flow). `PendingReviewDraft` therefore holds only `overallComment` / `isSubmitting` / `submissionError` — matching github.com, whose "Finish your review" box is likewise not persisted until submit. Pending comments arrive as ordinary `detail.reviewThreads` entries flagged `isPending`, so the Changes tab feeds *only* the detail's non-outdated threads into `DiffCommentAnnotations`; nothing local is merged in.
- **Submitting finishes the pending review rather than opening a second one.** `submitReview(event:)` calls `submitPendingReview` when `detail.pendingReviewNodeID` is set and falls back to a summary-only `POST .../reviews` only when there is no draft. Validation: `.requestChanges` needs an overall comment, `.comment` needs an overall comment or one pending comment (`detail.pendingCommentCount`, which is also the footer's "N pending comments" note), `.approve` always submits. Approve and Request changes only appear for other people's PRs (`summary.isAuthored`, double-checked against the detail's `viewerLogin`) — GitHub rejects them on your own PR — and the footer's `effectiveEvent` forces `.comment` if a stale verdict selection survives the gating. The comments render straight from `session.detail`, so they stay on screen through the refetch that reclassifies them as submitted; a failure loses nothing (they are already on GitHub) and surfaces `submissionError`.
- **The orange "Pending" pill is the unsubmitted marker on both tabs.** It comes from GitHub's `PENDING` comment state — exactly "written but not yet sent with Submit review..." — and renders through the shared `PullRequestCommentBadge` in `PullRequestCommentChrome.swift`, used by `DiffCommentThreadRow` on Changes and `PullRequestReviewThreadView` on the Overview (which also draws "Outdated" with it). A pending thread suppresses what GitHub does not offer until submission: no `PullRequestThreadActionsFooter` (the Overview's footer gate is satisfied by a pending thread, so it needs an explicit `!thread.isPending` guard) and no reaction bar. Because `makeReviews` drops the viewer's draft, pending threads have no visible carrier review and land as standalone Overview timeline entries — do not filter them out.
- **Pending and submitted comments are addressed differently — branch on `isPending` at every entry point.** A pending comment edits and deletes over GraphQL by node id (`composerPendingCommentNodeID`), a submitted one over REST by `databaseId` (`composerRemoteCommentID`). Both tabs must make that split: `openRemoteCommentEditor` / `requestDeleteRemoteComment` on Changes, `openThreadCommentEditor(_:)` / `requestDeleteThreadComment(_:)` on the Overview. Missing it silently PATCHes `pulls/comments/{id}` for a pending comment. Deleting a pending comment skips the confirmation dialog — nothing is published yet, and `PendingRemoteCommentDeletion` is REST-only. The three-dot menu gates on whichever id its actions need, so an optimistic comment still awaiting GitHub's answer offers none.
- **Submitted comments follow GitHub permissions, not authorship.** Thread comments and top-level issue comments carry `databaseId`, GraphQL `id`, and `viewerCanUpdate`/`viewerCanDelete`; the shared three-dot menu (`PullRequestCommentActionsMenu` in `PullRequestCommentChrome.swift`) appears when either permission holds (repo collaborators can act on other people's comments, including bots) and offers only the permitted actions — on the Changes tab's thread rows *and* the Overview timeline's comment cards and thread comments. Edit swaps the comment's body for the shared editor inline (`.editRemote` on Changes, `PullRequestActivityCommentEditor` on the timeline, both "Update comment") rather than opening a composer row below it; delete arms a session-owned confirmation (`pendingRemoteCommentDeletion`, whose `kind` picks the REST endpoint) presented by one dialog on `PullRequestPane`, shared by both tabs. Remote edits never touch the pending batch, and action failures without an open composer or inline editor surface as a banner on both tabs (`composerError`). Review cards (the "reviewed"/"approved" timeline entries) get the same menu gated on the review's `viewerCanUpdate`, but with Edit only — GitHub cannot delete a submitted review — tracked through `composerReviewID` and saved via `updateReview` (`PUT pulls/{number}/reviews/{id}`).
- **Remote comment actions live in `PullRequestsViewModel+RemoteComments.swift` and are optimistic like everything else.** Edit rewrites the comment body locally and closes the composer before the PATCH; failure restores the old body and reopens the composer with the attempted text. Delete removes the comment (and an emptied thread) before the DELETE; failure reinserts it via `restoreThreadComment`/`restoreIssueComment`. Neither refetches on success — the local state is already exact. Issue-comment edits track through `composerIssueCommentID` (no diff anchor) and hit `issues/comments/{id}`; thread-comment edits opened from the timeline reuse `composerRemoteCommentID` with a nil anchor, so the same edit renders inline on both tabs. Review summary edits follow the same optimistic shape through `updateReviewBody`.
- **Comment composing is BlockInputKit.** The inline diff composer and the review footer's overall comment share `PullRequestCommentEditor` + `PullRequestCommentDraftBox` (a per-session `BlockInputMemoryDocumentStore` plus a cheap `isEffectivelyEmpty` flag). Markdown serializes only at save — never per keystroke, which would reconfigure the editor mid-typing — and Save enablement reads the flag. Placeholders: "Leave a comment" for new/reply, "Edit this comment" for edits. The editor defaults to two visible lines (max ten), and its initial top inset plus mount-time focus rely on BlockInputKit's deferred window-attach focus handling — regression-covered by the editor snapshots and `PullRequestCommentEditorFocusTests`. Composer-only features (completions, slash commands, drops) stay off, matching the Settings `AGENTS.md` editor host. `PullRequestCommentEditor` sizes through `BlockInputEditor.sizeThatFits` alone — no `onPreferredHeightChange` + `.frame(height:)` state. The callback round trip applies the height a frame after the AppKit editor has already grown, which reads as a glitchy vertical jump on mount and on line add/remove; `sizeThatFits` reports the clamped preferred height synchronously in the same layout pass. (The Settings editor host keeps the callback pattern only because its fixed-height ScrollView case misbehaved with `sizeThatFits`.) **Cmd+Return submits and Escape cancels** through `BlockInputConfiguration.keyboardShortcuts` — the editor's `onSubmit`/`onCancel` run the host's Save/Submit and Cancel actions behind the same guards as the buttons, and plain Return stays a newline because comments are multi-line.
- **Comment actions are optimistic.** Reactions, thread replies, and thread resolution mutate `session.detail` immediately (`PullRequestModels+Optimistic.swift`) and revert on failure — reactions apply the inverse toggle, replies remove the placeholder and reopen the composer with the text intact, resolution flips back. Only a successful reply refetches (to swap the placeholder for the server copy with real ids); reactions and resolution never refetch.
- **Optimistic comments are attributed to the viewer.** The detail query's top-level `viewer` field supplies `viewerLogin`/`viewerAvatarURL`; the pending-comment placeholder and the optimistic reply both use them (falling back to "You" on a stale detail) so a comment shows the same identity GitHub would before the server copy swaps in.
- **Rows sort by recency.** `visibleRows(for:)` orders by `updatedAt` descending — the date each row displays top-right — with `displayKey` breaking ties, client-side so every tab and section inherits it. Status does not participate (an explicit reversal of the earlier status-first order).
- **Overview shows GitHub's Reviewers list, not the decision string.** `makeReviewers` composes pending requests (question mark) with each past reviewer's latest verdict (green check / red bubble), excluding the PR author. Re-request (`arrow.clockwise`, POST `requested_reviewers`) appears only for *human* reviewers with a submitted review — bots/apps never get it (the endpoint rejects them and GitHub hides it too), and a pending request hides it until the reviewer re-reviews. While a re-request round trip runs, `reRequestsInFlight` disables that reviewer's button; failures surface in `session.reviewersError` as a banner inside the Reviewers section, not the Changes-tab `composerError`. Body-less `COMMENTED` reviews with no attached threads are hidden from the timeline as empty shells; one carrying threads renders as the group header its threads nest under (inline-only review submissions have no top-level comment at all).
- **Reactions mirror GitHub's fixed palette on every comment surface.** Issue comments, review bodies, and review-thread comments (Files and the Overview timeline alike) render non-empty reaction groups as toggle chips (viewer-reacted = accent outline) plus a circled smiley opening the eight-emoji picker popover. Toggles run `toggleReaction(subjectID:content:viewerHasReacted:)` — GraphQL mutations against the subject's node id — optimistically, never refetching. Pending local comments have no reactions.
- **Timestamps are compact relative ages with absolute hovers.** Overview timeline rows, thread comments, and the Changes tab's thread comments render `compactRelativeAge` ("now", "5m", "3h", "2d") through the shared `PullRequestTimestampLabel`, whose `.help` tooltip and accessibility label carry the absolute date and time from `PullRequestTimestampFormatting`'s one cached `DateFormatter` — never build a formatter (or resolve a `FormatStyle`) per render. The Changes tab's lazily recycled rows go further: `DiffLineComment` carries preformatted `relativeAge`/`absoluteTimestamp` strings computed once at annotation-build time, so scroll-back-in never formats. Relative ages read `viewModel.referenceDate`; pane snapshot fixtures must inject a fixed `now` just after the fixture dates or ages render nondeterministically.
- **Review cards without a summary body are bare headers.** No body, no reaction affordance, no three-dot menu (`showsCardBody` / the body gate in `actionableReview`) — matching GitHub's verdict rows and "commented" carrier headers; commented/pending review cards read "commented", not "reviewed". Reactions that somehow exist on a body-less review still render.
- **Trailing interactive chrome must clear the scroll indicator, on one shared column.** Both tabs' scroll views span the full pane width (`PullRequestPane` applies `contextualPaneHorizontalInsets()` to the tab row only; the Changes tab folds the pane inset into `FlattenedDiffPreview`'s `horizontalContentInset` so its scroll bars sit flush with the pane edge too), so measure a control from the scroll view's trailing edge — which equals the pane's. Controls end at `AppScrollIndicatorLayout.interactiveTrailingClearance` from that edge (the measured lane-plus-slop boundary — see `Alveary/Views/Components/AGENTS.md`). The timeline cards' 16pt content inset plus 12pt card padding lands exactly on it; the Overview's `headerSection` pads its trailing edge by the difference so the diff stats and the description Edit menu align with the card menus below (padding only the menu floated it off the stats column — rejected). Changes-tab cards land controls at 42pt (22pt content inset + 8pt card outset + the Overview-matched 12pt interior trailing) — well clear of the 17pt lane (see `Alveary/Views/DiffViewer/AGENTS.md`). Do not push clearance down into `PullRequestCommentActionsMenu`: it would double-inset every card. The column is also *optical*: the menu's ellipsis is trailing-aligned inside its hit frame so the glyph's right edge equals the frame's trailing edge by construction. The tab row's Open-on-GitHub button does **not** sit on this column — it aligns with the pane's *icon* column instead (the header close button above and the Changes tab's file collapse carets below, ~26pt glyph inset), because a glyph landing between those icons but on the menu column read as misaligned. Its trailing pad bakes in the measured SF glyph interior inset, and the `testPullRequestPaneTrailingColumn` baseline guards the seam. Non-interactive trailing elements (timestamps, reviewer state icons) can sit in the lane freely.
- **Comment chrome is shared.** `PullRequestCommentChrome.swift` owns the avatar+login+Bot-pill author row (`PullRequestCommentAuthorRow`, vertically centered), the `Bot` badge (GraphQL author `__typename == "Bot"`), the tinted `PullRequestCommentBadge` capsule ("Pending", "Outdated"), and `PullRequestCommentBody` (sanitized markdown + `CommentReactionBar`); Timeline entries and thread comments compose these instead of hand-rolling headers. The bar itself is the generic `Components/CommentReactionBar.swift`. `PullRequestAvatarView` draws a subtle adaptive circle (`secondary.opacity(0.2)`, GitHub-style) behind loaded images so transparent bot logos stay legible on both themes.
- **Threads reply and resolve like GitHub — on both tabs.** The shared `PullRequestThreadActionsFooter` (in `PullRequestCommentChrome.swift`) offers Reply (saving POSTs `pulls/{number}/comments/{rootID}/replies` immediately — replies never join the pending batch) and Resolve/Unresolve (`resolveReviewThread`/`unresolveReviewThread` mutations via the thread's node id); a successful reply refetches, resolution never does. Both tabs route through the same composer state: Changes opens `openThreadReplyComposer(at:thread:)` with a diff anchor and renders the composer row in the diff, the Overview opens `openThreadReplyComposer(_ thread:)` anchorless and renders `PullRequestActivityCommentEditor` (saveTitle "Reply") inline in the thread, replacing the footer while open — `isReplyingInline` matches on root comment id plus nil anchor, so each tab shows only its own reply editor. The optimistic placeholder appends to `detail.reviewThreads`, so it appears inside the Overview's nested hierarchy immediately; failure removes it and reopens the editor where it was opened. Resolution is per thread, and on both tabs a resolved thread collapses its whole conversation — replies included — to the shared `PullRequestResolvedThreadHeader` with an expand chevron; resolution changes reset the manual expansion so resolving collapses and unresolving expands.
- **The Overview follows its timeline's bottom.** `TimelineBottomFollowing` (in `PullRequestPane+OverviewScrolling.swift`) pins the scroll to the end when an entry is appended *and* the reader is already parked there, so a closed/reopened/ready row or a reply reveals itself instead of landing below the fold; scrolling up opts out until they return. Two traps, both regression-tested: **content growing beneath a follower is not them scrolling away** — it moves the end below the viewport and reads identically to scrolling up from the distance alone, so the reading carries the content height too and growth keeps an existing follower following (treating it as opting out let the first appended row silently disable every later one); and **the scroll has to outlive the data change** — scrolling from `onChange` alone runs against the pre-growth layout and stops short, so the request is armed there *and* re-run from the geometry reading that reports the grown content, which also makes it immune to the two callbacks' ordering. `0 -> N` is the first detail landing, not an append, and must not bury the header. The modifier is lifted out of `body` to keep the scroll observers off its type-check budget.
- **There is no Activity tab — the Overview appends the conversation timeline.** The Overview orders header, description (and its reaction bar, with no divider after the header), Reviewers, Checks, then — behind a divider — `PullRequestPaneActivitySection`: issue comments, review cards, bare status rows, and review threads in one chronological stream; thread cards link to the Changes tab (`PullRequestPaneTab.files`, displayed as "Changes"). Threads nest under the review card they were submitted with, GitHub-style — `PullRequestActivityEntry.entries(from:)` groups them by the thread's `reviewNodeID` (the root comment's `pullRequestReview { id }`) and `PullRequestActivityReviewGroupView` indents them behind an L-shaped connecting rail (vertical line with a horizontal foot marking where the group ends). A body-less carrier review *with* threads renders as the group header (inline-only submissions have no top-level comment); threads whose review is unknown stay standalone, dated by their root comment and kept in fetched order so equal-date siblings render deterministically. Bare rows cover draft/ready, closed/reopened/merged (tinted octicons), pushed commits (`detail` = "sha headline"), force pushes, and review requested/removed (`detail` = reviewer); `GitHubPullRequestsService+Timeline.swift` maps the GraphQL `timelineItems` types and drops unrecognized ones. Merging emits a `closed` event next to the `merged` one, so `visibleTimelineEvents(_:)` drops closures dated at or after the merge — never all of them, because a close-then-reopen-then-merge history has a legitimate earlier close. Bare rows stay one ellipsized line: commit phrases carry the full headline and would otherwise wrap. The section renders only when it has content, and row glyphs render in a fixed 16pt slot — SF symbols vary in width while octicons are fixed frames (ready-for-review uses the `EyeOcticon` asset, not the wide SF `eye`), so an unslotted mix misaligns the avatar column. Card headers carry a glyph only for review verdicts (green check / red x); plain comment and review cards dropped the chat bubble as redundant beside the author row.
