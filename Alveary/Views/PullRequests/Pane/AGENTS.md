# Pull Request Detail Pane

These instructions cover `Alveary/Views/PullRequests/Pane/` — `PullRequestPane`, its Overview and Changes tabs, the conversation timeline, and the pane's own chrome and layout. The review footer it renders is `Alveary/Views/PullRequests/Review/`; the comment surfaces both tabs share, including the markdown sanitizer, are `Alveary/Views/PullRequests/Comments/`.

**Keep a rule here only when the code that would violate it is not the code that documents it.** Mechanism whose only reader is its own file belongs in a doc comment: `TimelineBottomFollowing`, `PullRequestDiffFilePaging`, `PullRequestActivityEntry`, and `PullRequestOverviewSection` each carry theirs.

## Detail Pane And Overview

- **The detail pane follows the contextual-pane session contract.** `PullRequestPane` renders `viewModel.paneSessions[target]` only; `Alveary/ViewModels/PullRequests/Pane/AGENTS.md` owns generation-guarded async loads, and `Alveary/ViewModels/AGENTS.md` the activation and deactivate-then-dismiss close flow. Rows open through `requestDetails(_:)`; row highlight derives from `activePaneTarget`.
- **The pane and its tabs are `Equatable`, and new pane children must stay that way.** `ResizableRightPane` re-runs its body on every resize-drag frame and every pane-session write, handing down a fresh dismiss closure, so without equality the whole timeline rebuilt each time. Take the session by value and exclude closures from `==` — the `.id(renderedPresentation)` keying means a closure that would mean something different arrives with a teardown, not a comparison. **Route a new child's actions through the view model rather than adding a stored closure.**
    - **A comment reveals itself the same way.** Both the Overview's "Show in Changes" and a transcript jump call `requestCommentScroll(to:)`; `PullRequestPane` selects the Changes tab and `FlattenedDiffPreview` scrolls to `comment:<anchor.key>`. Do not widen `onOpenFiles` to carry the anchor — the closure is excluded from `==` on purpose (`PullRequestsViewModelTests+RenderStability`). The scroll gives up once the diff is loaded without the row, because a force-push can strand an anchor.
    - **Watch that request with `task(id:)`, never `onChange`.** A jump into a *closed* pane arms the scroll inside the same call that opens it, so the token is already set when the pane first mounts; a change handler never fires and the pane sits on Overview with the Changes tab unmounted. The same holds for anything else keyed to a request that can precede the view.
- **Both tabs stay mounted once visited**, through `KeepAliveTabContainer` (see `Alveary/Views/Components/AGENTS.md`) — that is what preserves each tab's scroll offset and keeps the Changes tab's prepared diff rows from rebuilding behind a "Preparing diff preview…" spinner on every return. **Do not restore this to a `switch` over `selectedTab`.** Scroll state is per pane identity by design: a different pull request, or a reopened pane, is a new `.id` and starts at the top.
- **The description edits inline, gated on `viewerCanUpdate`** (permission, not authorship), through an Edit-only `PullRequestCommentActionsMenu` in its section heading's accessory slot — GitHub cannot delete a description. The editor opens at `minimumVisibleLineCount: 4` where comments stay at 2. An **empty body still saves**, because clearing a description is legitimate, which is why `PullRequestDetail.bodyMarkdown` is `var`.
- **Overview shows GitHub's Reviewers list, not the decision string** — the list search does not fetch `reviewDecision` at all (`Alveary/Services/PullRequests/GitHub/AGENTS.md` owns why). `makeReviewers` composes pending requests with each past reviewer's latest verdict, excluding the author. Re-request appears only for *human* reviewers with a submitted review — the endpoint rejects bots and GitHub hides it too — and a pending request hides it. Failures land in `session.reviewersError` as a Reviewers-section banner, not `composerError`.
- **There is no Activity tab — the Overview appends the conversation timeline.** Order: header, then linked owners, Reviewers, Checks, and Description (plus reaction bar) — all four through `PullRequestOverviewSection`, no divider anywhere among them — then behind a divider `PullRequestPaneActivitySection`: issue comments, review cards, bare status rows, and review threads chronologically. **The short metadata sections stay above the description** so review state survives a long body, and the description stays last so it runs into the timeline. Thread cards link to the Changes tab (`PullRequestPaneTab.files`, displayed "Changes").
    - Threads nest under the review they were submitted with, indented behind an L-shaped rail. A body-less carrier review *with* threads renders as the group header; threads with unknown reviews stay standalone, dated by root comment, kept in fetched order for deterministic siblings.
    - `GitHubPullRequestsService+Timeline.swift` maps the GraphQL `timelineItems` types and drops unrecognized ones. Bare rows stay one ellipsized line.
    - **Row glyphs render in a fixed 16pt slot** — SF symbols vary in width while octicons are fixed frames (ready-for-review uses `Octicon.eye24`, not the wide SF `eye`) — so an unslotted mix misaligns the avatar column. Card headers carry a glyph only for review verdicts.

## Chrome And Layout

- **Everything the pane draws on its own background ends on the 16pt content column.** The scroll views span the full pane width — `PullRequestPane` insets only the tab row, and the Changes tab folds the pane inset into `FlattenedDiffPreview`'s `horizontalContentInset` — so the pane title, tab chips, `headerSection`'s diff stats, bare-row timestamps, card edges, diff code surface, and footer button all land on `ContextualPaneLayout.horizontalInset`. Do not re-add the diff preview's own 6pt inset on top of it; that put the Changes tab 6pt deeper than every sibling while its call site claimed to match them.
    - **Its glyphs center on the trailing lane instead**, through `contextualPaneTrailingGlyphLane()` and `collapseCaretAxis`. See **Pane Insets And Chrome** in `Alveary/Views/Components/Panes/AGENTS.md`, which owns the rule. `testPullRequestPaneTrailingColumn` guards the header/tab-row seam; the Overview baselines guard the row glyphs.
    - **Accepted:** the description's Edit menu, on its section heading, is interactive and ends 16pt from the scroll edge, inside the 28pt clearance — but well past the 11pt that measured clean, so clicks should survive. Chosen over floating one control off a column every neighbour sits on.
- **The tab row's divider is drawn by each tab, not by `tabRow`.** Both tabs stay mounted with their own scroll offsets, so `pullRequestPaneTabDivider(isScrolled:)` — whose doc comment owns why — rides each tab's own top edge and appears only once that tab's content has scrolled under the chips.
- **A control inside a *card* is inset from its card, not from the pane.** `AppScrollIndicatorLayout.interactiveTrailingClearance` (28pt) is what the timeline cards' 16pt content inset plus 12pt interior padding already comes to, so their `⋯` menus clear the scroller for free. Changes-tab cards land controls at 36pt (16pt content inset + 8pt card outset + the Overview-matched 12pt interior trailing); see `Alveary/Views/DiffViewer/Preview/AGENTS.md`.
    - Do not push clearance down into `PullRequestCommentActionsMenu` — it would double-inset every card, and the same menu is used off-card on the Description heading. That off-card use *does* owe the lane, as `controlWidth: hitTargetSize.width`.
