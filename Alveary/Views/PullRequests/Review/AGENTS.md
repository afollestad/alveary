# Pull Request Review

These instructions cover `Alveary/Views/PullRequests/Review/` — `PullRequestPaneReviewFooter` and the policy types behind it (`PullRequestReviewFooterAction`, `PullRequestReviewFooterAuthorship`, `PullRequestStateAction`): what Submit publishes, which agentic option leads, and which state changes GitHub allows.

**This scope owns the review workflow wherever it renders, not just the footer.** Pending and proposed comments, review cards, and which threads reach the Changes tab are review semantics, so they are ruled here even though `Alveary/Views/PullRequests/Pane/` draws them; that scope owns the surface those rules land on.

**Keep a rule here only when the code that would violate it is not the code that documents it.** Mechanism whose only reader is its own file belongs in a doc comment: `effectiveReviewKind`, `submittableCommentCount`, `commentCountNote`, `PullRequestStateAction.available(for:)`/`.placeholder(for:)`/`.isDestructive`, the seeded-`@State` properties on the footer, and `performStateChange` each carry theirs.

## Review Submission

- **Inline comments post immediately as pending review comments; only the summary is local.** `PendingReviewDraft` holds `overallComment` / `isSubmitting` / `submissionError` and nothing else — matching github.com. `Alveary/Services/PullRequests/GitHub/AGENTS.md` owns the mutation set and `Alveary/ViewModels/PullRequests/Review/AGENTS.md` the optimistic flow.
    - **The Changes tab feeds only *non-outdated* threads into `DiffCommentAnnotations`, and nothing local is merged in.** The diff is the one surface that cannot place an outdated thread — `FlattenedDiffPreview` emits a comment row only from a rendered line, and an outdated anchor either matches nothing or lands on unrelated code. The Overview shows them with the "Outdated" pill and the host tools list them, so do not re-derive either from this filter.
- **Submitting finishes the pending review rather than opening a second one.** Validation: `.requestChanges` needs an overall comment; `.comment` needs an overall comment or one pending comment; `.approve` always submits. A pending proposal's body counts as that comment through `resolvedReviewSummary`, which is `confirm`'s own precedence — read it in both submit gates, or a proposed verdict disables Submit over a body `confirm` supplies. Approve and Request changes appear only for other people's pull requests — GitHub rejects them on your own — and `effectiveEvent` forces `.comment` if a stale verdict survives that gating. Comments render straight from `session.detail`, so they persist through the reclassifying refetch and a failure loses nothing.
- **The orange "Pending" pill is the unsubmitted marker on both tabs**, from GitHub's `PENDING` comment state, through the shared `PullRequestCommentBadge`. A pending thread suppresses what GitHub does not offer until submission: no `PullRequestThreadActionsFooter` (the Overview's gate needs an explicit `!thread.isPending` guard) and no reaction bar. `makeReviews` drops the viewer's draft, so pending threads land as standalone Overview timeline entries — do not filter them out.
- **"Proposed" is its orange sibling, and the two are different states.** "Pending" is the viewer's server-side draft; "Proposed" is a review proposal's staged comment, living only in Alveary's envelope until the review is submitted. Same tint because both are unpublished, and mutually exclusive by construction (`isProposed` implies `!isPending`, on both `DiffLineComment` and `PullRequestComment`). **Both tabs render them.**
    - **Overview threads are synthesized per render, never written into `detail.reviewThreads`.** That array is GitHub's record, and a synthetic entry would reach everything trusting it — `pendingCommentCount` and the submit gates included.
    - **A staged comment's one action is Delete, on all three surfaces** — both pane tabs and the transcript's review-proposal card — with `onEdit: nil` and no confirmation, since nothing is published. Editing in place is a deliberate absence: remove and re-add.
    - **The transcript is AppKit and cannot mount `PullRequestCommentActionsMenu`, so it reads its parts.** That menu's statics and `PullRequestCommentRevealAction`'s exist for exactly that; add to them rather than respelling a title or metric on either side.
    - **While a proposal is pending, composing edits *that* review, not GitHub's draft.** A comment written to the viewer's draft would be published by the same Submit yet never reach the transcript card, so the two surfaces would disagree about what the review says. No optimistic placeholder — the envelope write is synchronous and the merged annotations re-derive from it.
    - **Submit routes through the proposal coordinator**, so staged comments and the viewer's own draft publish as one review; `Alveary/ViewModels/PullRequests/Review/AGENTS.md` owns that flow, and `confirm`'s own doc comment owns the `bodyOverride` precedence. **Accepted:** starting a new agentic review from the footer meanwhile creates a competing proposal from another conversation, and the newest wins — noted, not guarded.
    - **A pending proposal owns the footer's verdict, not the footer.** `selectedReviewEvent`/`selectReviewEvent` route the picker to the coordinator, so this pane and the transcript card edit one review rather than each submitting its own.
    - **Which staged comments render follows the pull request, not the route**, so the toolbar, the links popover, the list, and a transcript jump all show the same thing. It resolves on every read, so confirming or rejecting anywhere drops the comments with no observer to keep in sync. **The pane stores no attachment** — only `pendingCommentScrollTarget`.
    - **`PullRequestPaneFiles` takes its `target` explicitly** rather than reading `activePaneTarget`, so it resolves for the session it was handed — which is also what lets a snapshot host render the tab without opening a pane.
    - Merging is `PullRequestReviewProposalCoordinator.appendStagedComments(...)`, shared with the transcript card's own preview. Both surfaces show the same review, so neither may grow its own copy.
- **Review cards without a summary body are bare headers** — no body, reactions, or menu (`showsCardBody` / `actionableReview`), matching GitHub's verdict rows; commented/pending cards read "commented", not "reviewed". Body-less `COMMENTED` reviews with no threads are hidden as empty shells.

## Footer And State Changes

- **The trailing button is always a `SplitActionButton`: Submit review, Agentic review, or Address feedback.** `PullRequestReviewFooterAction` has no availability policy — every option applies to every pull request, and `propose_pr_review` validates the verdict when the agent proposes one. Both agentic options call `startAgenticThread(kind:)` (see `Alveary/Services/PullRequests/AGENTS.md`).
    - **Spawning never navigates.** The footer stays put and the button carries the state: its route's face spins and dims until that thread's first turn ends. The Overview's Linked threads row is the way into the spawned thread — which is also why the link has to land while this pane is still mounted.
    - **Tracking is per route, not per pull request.** `session.workingAgenticKinds` mirrors the app-scoped `PullRequestAgenticThreadActivity`; a running review leaves Address feedback live, and the caret stays clickable so it can be reached. Two runs on one *route* are what is refused.
    - **Three failure surfaces, and they are not interchangeable.** A missing project is the modal (the fix is outside this pane), other pre-spawn failures are the banner, and anything after the thread exists toasts — the deferred half can outlive a pane the user closes.
    - **Authorship routes to one of two stored picks** — `AppSettings.pullRequestOwnFooterActionKind` (Address feedback) or `pullRequestOthersFooterActionKind` (Agentic review) — and `.unknown` reads the others' key, the safer side while the detail is in flight.
- **The state button never appears while a review is being written**, and `PullRequestStateAction.available(for:)` owns every other case of its absence. The two buttons otherwise split the row evenly with `ContextualPaneLayout`'s action spacing and minimum width, which is why **the pending-comment count sits above them** rather than beside. Reopen disables when `headRefExists` is false with a note naming the branch — reopening without it is a 422.
    - The menu keeps the select-only contract (see `Alveary/Views/Components/AGENTS.md`), and both draft directions drop out when `detail.nodeID` is nil, because each mutation is addressed by node id.
    - **An identifier-opened pane has no summary to title a stand-in with** (see `Alveary/ViewModels/PullRequests/Links/AGENTS.md`), so it shows the lone Submit review button until its detail lands — and withholds Approve / Request changes meanwhile, because authorship is still unknown and GitHub rejects a verdict on your own pull request.
- **A state change writes the pane session *and* its list row.** `Alveary/ViewModels/PullRequests/AGENTS.md` owns `applyStatus(_:toRow:)` as the only writer of `items` outside a refresh; `performStateChange` carries the rest.
